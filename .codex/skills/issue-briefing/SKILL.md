# 问题整理

把「用户这样说」变成「执行 AI 照着做也不会跑偏」的计划文档。

这份技能代表 Plan 阶段。输出是问题、证据、原因、修改方案、边界和验收标准，不是代码修改。
一篇文档只放一个问题，并成为可独立领取、独立执行、独立验收的任务单元。

所有 Agent 共用一套结构：`task-v1`。标题固定、字段固定、标记固定，不自行改名或加新小节。
新文档从 `docs/问题整理/_模板.md` 复制，写完用检查脚本验证。
如果用户指定了别的目录，在那个目录优先复用同名 `_模板.md`；没有就照本技能的模板写。

只读检查不算改代码。`codegraph` 的查询和索引、浏览器核对、跑现有测试都可以；
只有写产品文件才算越过 Plan 阶段。用户明确要求开始实施后，才进入改代码流程。
写问题文档时也要遵守项目规则，编辑只用 `apply_patch`，不要用 PowerShell 写文件。

## Plan 阶段只做计划和核对

1. 对话期间禁止直接修改产品代码、配置、依赖、测试或构建产物。可以读代码、查调用链、
   跑只读检查、在浏览器核对现状，但不能「顺手修一下」。计划涉及的测试也只能读和运行，不能改。
2. 只写问题整理目录里的文档和引用资料。默认是 `docs/问题整理/`；用户指定了目录就按用户的位置。
3. 用户补充、否定、追问或给出新截图时，先更新问题文档，再回复。不要只在聊天里解释答案。
   用户追问「为什么改这里」时，把核对结果补进「问题原因」和「修改方案」，不要只回一句原因。
4. 文档要同步维护：原话、现状证据、问题原因、修改方案、验收标准、待确认项和状态。
5. 已确认的结论写进正文；被推翻的旧结论要删掉或标成「已废弃」，不能留下两套互相矛盾的方案。
6. 用户明确说「按这个计划执行」「可以改代码了」后，Plan 阶段结束，再按确认后的文档进入实施流程。
   计划阶段和完成阶段都使用固定标题 `## 修改方案`，用头部状态区分是否已确认。
   即使已经确认方案，本技能默认仍只负责文档；用户明确要求开始改代码后，才把这一条交给实施任务。

用户催「先修一下」时，如果计划还没确认，也只更新文档，并说明还缺什么确认。
用户只是补充截图、指出原因或讨论做法时，不要提前把状态改成 `已完成`；
要等验收项全部通过、执行记录写实后才改。

## 一次只处理一个问题

多个 Agent 可能同时处理这个目录里的不同问题。每次只围绕用户当前说的那一个问题工作：

1. 开始前先看当前文档头部的状态和负责人：`已完成` 就直接用完成记录，不重查；
   别人负责的 `进行中` 不重复做，除非用户明确交给你。
2. 只打开、检查和修改这一篇问题文档；需要时再读它的总目录，用来更新这一行状态。
3. 不主动遍历、审核、修复或格式化其它问题文档，也不重查别人已经标记为「已完成」的问题。
4. 发现别的问题有明显错误时，只在回复里提一句，不顺手改。
5. 当前问题需要合在一起改代码时，仍在同一篇文档里写清关联关系，不合并成「大杂烩文档」。
6. 总目录的清单和待确认汇总只在当前问题相关时改一行，不重写整张表。
7. 总目录里列出别的问题，不代表要逐篇打开核实；只信已有状态，不重新排查。

「为什么你改这处」这类追问，先核对当前文档的因果链。证据不够时只补查这一条，不扩大到其它问题。

## 一篇文档就是完整任务单元

每篇问题文档必须让另一个 Agent 不看聊天记录也能独立开工。至少写清：

- 用户原话、目标、现状与期望；
- 复现步骤、证据、问题原因和把握程度；
- 修改方案、参考代码的完整文件路径（必要时写到函数或类名）、相关资源路径；
- 验收标准、不能动的内容、风险和验证命令；
- 执行状态、负责人和完成标记。

路径写仓库相对路径，例如 `packages/ui/src/components/ProjectCluster.vue`；
图片写相对于该文档的路径，例如 `images/01-画布列表行尾-现状.png`。
没有参考代码或图片时，明确写「无」，不要留空。

头部统一三行，顺序不能变：

```text
- 状态：待确认
- 负责人：未领取
- 完成时间：—
```

文件名统一为 `两位编号-短标题.md`，标题统一为 `# 编号 · 问题标题`；
同一目录里编号不能重复。新问题先看该目录现有最大编号，再顺延。
同一批里不同 Agent 新增任务时，先取号再写文件；发现编号已被占用就换下一个，
不覆盖别人的文件，也不把不同问题塞进同一篇。

统一任务结构 `task-v1` 的正文顺序固定为：

```text
头部：状态 / 负责人 / 完成时间
你的原话 → 要解决的问题 → 范围与位置 → 现在 vs 期望
→ 问题原因 → 修改方案 → 验收标准 → 不能动
→ 假设与待确认 → 执行指令 → 图片 → 执行记录
```

只能使用这些二级标题。不要写「背景」「相关文件」「补充说明」等自造小节；
有额外信息就放进对应固定小节。新问题一律从 `_模板.md` 开始，不手搓空文档。

## 先做判断

- 用户发来多条问题、截图、抱怨或整改要求，想先理清方向时，使用本技能。
- 只有一个明确的小改动，且用户没有要求先整理计划时，按普通任务处理，不必套用本技能。
- 默认写入 `docs/问题整理/`；用户指定了目录就按用户的位置。
- 如果用户要求「先整理，再马上修」，仍先完成文档并确认方向；本技能不负责改代码。
- 用户连续补充、纠正或追问时，继续留在 Plan 阶段更新文档，不切到实现。

## 对话中持续修订

用户每发来一条新消息，按这个顺序处理：

1. 先确定它属于哪一篇问题；已经存在就更新那一篇，不另开重复条目。
2. 把新信息写进固定位置：
   - 「你的原话」保留第一次的描述，后续补充用引用块追加，并写日期或轮次；
   - 新证据、复现步骤、日志和截图；
   - 问题原因：写清是已确认、推测还是待验证；
   - 修改方案：写清改哪里、为什么这样改、影响面和怎么验证；
   - 验收标准、不能动和待确认项。
3. 已回答的「待确认」从汇总里移除，转成正文里的已确认结论；新出现的问题补进去。
4. 更新 `README.md` 里的状态、建议顺序和待确认汇总。
5. 重新读一遍受影响的文档，删掉与新回答冲突的旧内容。
6. 回复用户：改了哪几篇、关键结论有什么变化、还差什么确认。

只改当前问题这一篇，不要顺手整理其它文档。更新总目录时也只改对应这一行和必要的关系说明。

这里说的「哪几篇」指用户这一轮明确提到的问题；即使一次给了多条，也各用独立文档。

## 处理一批问题

1. 先把用户这次发来的全部内容读完，再开始编号。不要看到第一句就写第一条。
2. 按「用户最终想看到什么结果」拆问题，不按句子数量拆。
3. 一个文件只放一个可独立验收的结果。不要把几个不相关的目标塞进同一篇。
4. 把「我猜的解决办法」和「我真正想解决的问题」分开写。两者冲突时，先指出冲突。
5. 找出问题之间的顺序、依赖和冲突，写进总目录。
6. 一次整理多条时，每篇都从 `_模板.md` 生成，所有文件保持同一个 `task-v1` 结构。

拆分完成后，后续每轮只进入当前那一篇；只有用户一次明确要求整理多条时，才批量新建或更新多篇。

## 把模糊要求变成可核对的标准

遇到形状、大小、颜色、位置、数量、顺序、文字或交互这类要求，必须落到能检查的属性。

例如「把按钮改成椭圆形」不能直接照抄。至少要分清：

- 胶囊形：左右完全圆角，上下保持直边。
- 几何椭圆：宽高不等时形成真正的椭圆轮廓。
- 只改外形，还是连大小、颜色、文字、悬停效果一起改。

如果两种解释做出来明显不一样，就写进「待确认」，一次性问清楚。
能根据上下文确定的，写成明确假设，不要反复打断用户。

## 先只读核对位置

问题涉及这个代码仓库时，只做只读核对：

1. 先执行 `codegraph status`。
2. 没有索引就先 `codegraph init`，再 `codegraph index`。
3. 用 codegraph 找页面、组件、样式和调用路径，不用 `grep` 代替。
4. 能在浏览器或截图里核对现状时，先核对；核对不了就写「位置待确认」。

不要把自己猜的文件名写成已经确认的事实；也不要为了验证想法去改代码。

## 找原因和提出修改方案

每个要修的问题都要有两块内容：问题原因和修改方案。

问题原因：

- 先复现，再收集证据：页面路径、操作步骤、日志、截图和相关调用路径。
- 只写有证据的结论；还没验证的明确写「推测」。
- 找不到根因时写「待排查」，不要用猜测填空。

修改方案：

- 写清准备改哪些文件、改什么行为、为什么这样改。
- 写清影响面、风险和验证方式。
- 有多个合理做法时，列出推荐方案和取舍，放进「待确认」，不要替用户拍板。
- 方案只写进文档，不在这一阶段实施。

## 文件结构

```text
docs/问题整理/
├─ README.md                 ← 总目标、问题清单、建议顺序、待确认汇总
├─ _模板.md                  ← 新问题的模板
├─ images/
│  ├─ 01-按钮-现状.png
│  └─ 01-按钮-期望.png
├─ 01-按钮改成椭圆形.md
└─ 02-设置页保存失效.md
```

文件名用两位数编号加短标题。图片名也带相同编号。

一个问题的正文、参考代码说明和图片资料都归在这一篇文档里；不要在文档之间复制大段内容。
问题之间只保留必要的链接，方便执行者跳转。

Plan 阶段仍需要更新文档；创建和修改这些文档只用 `apply_patch`，不要用 PowerShell 写文件。
这一条只约束文档编辑，不是改产品代码的许可。

## 每篇问题写什么

```markdown
# 01 · 按钮改成椭圆形

- 状态：待确认
- 负责人：未领取
- 完成时间：—

## 你的原话

原样保留第一次的描述，不改写用户的意思。

> 补充（2026-11-03）：后续补充写在这里；没有补充时删掉这一行。

## 要解决的问题

用用户能看懂的话，写清最终想得到什么结果。

## 范围与位置

- 页面：示例设置页
- 参考代码：`packages/ui/src/components/ExampleButton.vue:12`
- 相关资源：`images/01-按钮-现状.png`
- 关联问题：无

## 现在 vs 期望

| | 现在 | 期望 |
| --- | --- | --- |
| 外形 | 正方形按钮 | 胶囊形按钮 |
| 大小 | 40 × 40 | 保持 40 高，宽度随文字 |

## 问题原因

- 状态：已确认
- 复现步骤：打开页面，按钮显示为 40 × 40 的正方形。
- 证据：示例组件把 `border-radius` 写死为 8px，宽度写死为 40px。
- 根因：按钮样式只适合方形尺寸，没有给文字留出横向空间。

## 修改方案

- 改哪里：示例按钮组件的样式。
- 怎么改：把圆角改成左右全圆角，宽度改成随文字自适应，并保留最小高度 40px。
- 为什么这样改：这样得到的是胶囊形，不会变成几何椭圆。
- 风险 / 影响面：只影响这个按钮，不改点击行为和其它页面。
- 验证方式：在亮色、暗色和窄屏下各看一次，确认文字不被挤压。

## 验收标准

- [ ] 按钮外形是胶囊形，不是正方形，也不是几何椭圆
- [ ] 高度、文字、颜色和悬停效果不变

## 不能动

- 不改按钮点击行为
- 不改其它页面的按钮

## 假设与待确认

- 假设：用户说的「椭圆」是胶囊形。若要做几何椭圆，需要重新确认。
- 待确认：无

## 执行指令

只改这个按钮的外形为胶囊形；保持高度、文字、颜色、点击行为和悬停效果不变；
改完在真实页面里核对亮色、暗色和窄屏。

## 执行记录

- 改动文件：
- 验证命令与结果：
- 完成时间：
- 代码提交（可选）：
```

固定字段说明：

| 位置 | 字段 | 填什么 |
| --- | --- | --- |
| 头部 | 状态 | `等补充` / `待确认` / `进行中` / `已完成` |
| 头部 | 负责人 | 未领取时写 `未领取`；领取后写 Agent 名 |
| 头部 | 完成时间 | 未完成写 `—`，完成后写真实时间；负责人领取时不动这一行 |
| 范围与位置 | 参考代码 | 仓库相对路径，必要时带行号或函数名；没有写 `无` |
| 范围与位置 | 相关资源 | 图片等资料路径；没有写 `无` |
| 范围与位置 | 页面 / 关联问题 | 页面写用户看得到的位置；没有关联写 `无` |
| 现在 vs 期望 | 表格 | 至少一行「现在 → 期望」；没有可见差异时不能留空 |
| 问题原因 | 状态 | `已确认` / `推测` / `待排查`（不得留空） |
| 执行记录 | 改动文件 | 实际改动的完整文件路径，多个用「、」分隔 |
| 执行记录 | 验证命令与结果 | 真实跑过的命令和结果；没跑写 `未运行` |
| 执行记录 | 完成时间 | 与头部一致的真实时间 |
| 执行记录 | 代码提交 | 可选；填 commit hash，没有就删掉这一行 |

新问题只改「你的原话 / 要解决的问题 / 范围与位置 / 现在 vs 期望 / 问题原因 /
修改方案 / 验收标准 / 不能动 / 假设与待确认 / 执行指令 / 图片」这些小节，
「执行记录」留空，等实施时再填。

模板里的「待补充 / 待排查 / 待确认 / 未开始 / 未运行」只是占位，不是答案。
交付给用户前必须换成真实内容；检查器会把空字段和占位报出来。

旧文档暂时不符合 `task-v1` 时，只在正在处理的那一篇里按本结构补齐；
不要为了统一格式批量重写别的问题文档。

没有图片时，这一节写「本问题没有图片」。

「执行指令」是计划确认后的执行摘要，不是现在就开始改代码的许可。
要短、直接、能独立使用，不要只写「优化一下」「改好看点」。

## 图片处理

- 把截图和参考图放进 `images/`，用相对路径引用，例如 `images/01-标签-现状.png`。
- 图片已经在 `images/` 或由用户提供了可访问路径时，直接引用；不要用 PowerShell 复制文件。
- 每张图都写说明：这是现状、期望还是参考；要重点看哪里。
- 不要只靠图片表达要求；文字里也要写清可核对的标准。
- 没有图片时写「本问题没有图片」；用户说会补图但还没给时，写「待补图」，并把状态设为「等补充」。
- 图片名和问题编号对应，找不到归属的图片不要硬塞进某篇问题。

## 更新总目录

`README.md` 至少包含：

- 这批问题共同要解决什么。
- 问题清单：编号、标题、状态、优先级或建议顺序、文件链接。
- 哪些问题互相依赖，哪些会改到同一处。
- 所有「待确认」问题汇总。
- 每个问题的状态要和正文一致；已经回答的待确认项要及时移出。

状态只用：`等补充`、`待确认`、`进行中`、`已完成`。
总目录的问题表也固定为四列：`编号 | 问题 | 状态 | 文件`，表头不要改名。

## 执行完成时打标记

确认计划后，实施者在**当前问题文档**里完成收尾，不重开另一篇总结：

1. 领取时把头部状态改成 `进行中`，把「负责人」改成自己的 Agent 名；不要领两条没关系的任务。
2. 全部验收项通过后，逐条把 `- [ ]` 改成 `- [x]`。
3. 在「执行记录」里写改动文件、验证命令与真实结果、完成时间；没有跑的命令不要写成已通过。
4. 头部状态改成 `已完成`，填完成时间。
5. 同步总目录对应那一行的状态；只改这一行。

标记为 `已完成` 的文档就是完成凭据。后续 Agent 遇到同一问题，先看这一篇的完成记录；
除非用户明确要求复查或发现回归，否则不重新排查、不重复改代码。

如果执行中发现根因或方案不对，先停下，把状态退回 `待确认` 或改成 `进行中`，
在「执行记录」里写清卡点和证据，再更新「问题原因 / 修改方案」；不要用一版错误代码掩盖。

## 写完检查

当前问题已有文档时，先照 `task-v1` 补齐当前这一篇，再跑检查。
旧文档不符合结构时，只补当前这一篇，不动其它篇。

1. 一个不了解前情的人，只看这篇文档能不能直接动手。
2. 每个验收标准都能在页面上看到「过」或「不过」。
3. 原文、真实目标、假设和待确认没有混在一起。
4. 图片链接存在，说明写清了看什么。
5. 没有把没查过的文件、接口或行为写成事实。
6. 每个问题都有「问题原因」和「修改方案」；未验证的原因标成「推测」。
7. 用户最新的补充已经写进文档，聊天里没有只存在于回复里的结论。
8. 当前这一篇自带了参考代码路径、资源路径、状态和完成记录；没有的写「无」。
9. 没有为了「顺便统一」去扫描或修改别的问题文档。
10. 只检查当前这一篇：

```bash
python -X utf8 .codex/skills/issue-briefing/scripts/check_issue_docs.py "docs/问题整理/01-按钮改成椭圆形.md"
```

只有用户明确要求整体体检时，才把参数换成 `docs/问题整理` 检查整个目录。

脚本报错就修文档，再重跑。通过后，向用户报告：整理了几条、最关键的分歧是什么、建议先做哪一条、改了哪些文档。
