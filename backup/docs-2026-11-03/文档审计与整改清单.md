# 文档审计与整改清单

日期：2026-10-18。范围：`docs/` 下与插件开发、架构、API 手册相关的文档。只读审计，未修改旧文档。

## 总体判断

文档的问题不是“少”，而是**同一个概念有三套说法，且部分说法已过时**：

- 教程说 7 篇，入口写 9 篇，实际 01-09 共 9 篇；
- `docs/代码开发/00-总览与架构.md` 写“21 个插件”“24 个成品插件”，实际 36 个；
- 旧设计文档里还有 `canvas-core-v2`、`nodeStore` 服务名等已删除的东西；
- 节点注册 API 有 `ctx.nodes.register` 与 `registerNodeType` 两条路，字段名一个叫 `size`、一个叫 `defaultSize`，教程只讲一条；
- “加图片”没有统一入口，教程只教 `ctx.get('image')`，没有讲资源库与字段；
- “读上游”完全没有文档，导致每个插件自由发挥。

这次新增的四份文档用于补齐规范；旧文档按下表整改，不要重复新增同义文档。

## 文档合并建议

1. **“怎么写插件”只保留一个入口**：`docs/plugin-dev/index.md`。所有专题（服务、事件、配置、热重载）从它链接；不要再在 `docs/代码开发/` 写同义教程。
2. **“API 手册”与“规范”分开**：`docs/代码开发/` 讲 API 怎么用；`docs/插件开发规范.md` 讲必须怎么做。API 手册不重复硬规则，只链接。
3. **设计提案不混入现状**：`docs/design/*-proposal.md` 开头必须写“未实现/部分实现”；现状只在 `00-总览与架构.md`。
4. **历史追记归档**：`docs/STATUS.md` 只保留最近 30 天与“当前有效结论”；更早的移入 `docs/archive/`。

## 建议的文档修改顺序

1. 修 `docs/STATUS.md` 冲突标记与顶部摘要（否则所有人先读到坏文档）。
2. 修 `AGENTS.md` 的插件数与验证命令描述。

4. 给 `03-services-inject.md`、`07-into-canvas.md` 加“不要按插件名调用”“节点要声明 produces/consumes”。
5. 更新 `00-总览与架构.md` 的数字与架构图。
6. 给节点注册、doc、连接校验三篇加“上游契约”链接。
7. 最后处理 `docs/goal/` 与历史设计文档。

## 文档验收标准

- 同一个概念只有一个权威定义，其他文档只链接。
- 每份教程示例都能在仓库里找到对应源码，且字段名与源码一致。
- 文档里出现的插件数、包名、服务名，能被 `codegraph` 或 `package.json` 验证。
- 设计提案明确标“未实现”，不写成现状。
