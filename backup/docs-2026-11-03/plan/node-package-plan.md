# 可视化节点包（导出 / 导入）· 规范

> 2026-10-13 起草，**当天已全部实现并真机验证**（见 docs/STATUS.md 五～七续）。
> 下面保留的是**设计原稿**：实现与草案在几处收敛了（都就地标了"实际怎样"），
> 读的时候以标注为准。
> 一句话：把「可视化节点 + 它依赖的后台脚本」打成一个包，能带走、能拖回来、能收藏。

## 一、为什么要它

现在节点和脚本是**分家**的：节点的界面代码住在画布数据里，脚本住在服务器目录里。
换台机器、或者重开一个画布，节点能带过去、脚本带不过去 —— 那个节点就成了空壳。

打成包之后就变成"一件东西"：导出带走、拖回来就能用、还能收藏进资产库反复用。

## 二、包里装什么

一个 ZIP（后缀 `.mcnode`），四份：

| 文件 | 内容 |
|---|---|
| `manifest.json` | 包格式版本、包名、导出时间、每个脚本的 sha256 |
| `node.json` | 节点本体：type、size、data（含**依赖声明**，见第六节） |
| `ui.html` | 节点的界面代码（就是 `data.uiHtml`） |
| `scripts/<名字>.mjs` | **只带这个节点用到的**脚本，不是整个目录 |

**第一版不带媒体素材**（用户 2026-10-13 拍板："目前不需要，后期再说"）。

## 三、出口：导出 / 收藏（**只打包，不判断版本**）

位置：**节点右键菜单**，与现有的「加入资产库」并排。

| 菜单项 | 干什么 |
|---|---|
| 导出节点包 | 打包 → 下载一个 `.mcnode` |
| 收藏到资产库 | 打包 → 打开「上传资产」弹窗，由用户选保存位置（见第四节） |

**这两项都不做版本判断**（用户 2026-10-13 口径）：
收藏只是"把这个节点当前的样子原样打包存档"，是一次快照 —— 不碰机器上任何脚本。
版本判断发生在**从库里拖回画布**那一刻（见第七节）。

打包本身是**后台**做的（脚本内容在服务器上，前端拿不到）：前端调一次打包接口拿字节。

## 四、收藏 = 走现有的「上传资产」弹窗

用户口径：**不是直接收藏**，而是打开那个上传弹窗，**由用户自己选保存位置、填名字、打标签**。

接线：

1. 右键「收藏到资产库」→ 调后台打包 → 拿到包字节；
2. 打开 `AssetUploadDialog` 并**预填**这一项（就像现在画布图片走 `prefill` 那样）；
3. 用户改名字 / 选文件夹 / 挑标签 → 保存 → 走 `POST /api/assets?name=&folderId=` 落库。

弹窗要配合改三件小事：

- **接住 `.mcnode`**：现在只收图片/视频/音频，要多认一种；
- **图标**：`.mcnode` 显示"节点包"的图标，不是通用文件图标；
- **标签多一项**：标签清单现在是 `角色 / 场景 / 物品 / 风格 / 音效`（`ASSET_TAGS`，
  `LeftDrawer.vue` / `AssetManageDialog.vue` / `composables/ui.ts` **三处同源**，一起改），加一个 `节点`。

后台那边：资产类型 `kind` 现在由扩展名猜（`kindOfName`），`.mcnode` 会落到 `other`。
要显式给它一个 `node-package` —— 否则左侧抽屉不知道它是"能拖出节点的东西"。

## 五、打包这件事要给 AI 一个 MCP 工具

用户口径：**打包功能要提供一个 MCP 工具**（Agent 也要能打包、能存库）。

新工具（与现有 `canvas_ui_guide / write / update / read` 同一族）：

```
canvas_ui_package({ canvasId, nodeId, name?, folderId? })
  → { ok, assetId, url, scripts: [{ name, bytes, sha256 }], size }
```

- 不传 `folderId` → 存进个人资产库根；传了 → 存进那个文件夹；
- 返回的 `url` 就是库里那一项的地址；
- 这样 AI 写完界面和脚本后，能顺手把成品**收进库**，不必等人去点右键。

导出下载仍走右键（那是一次文件下载，不是 MCP 能表达的）。

## 六、依赖声明（AI 写，后台强制）

节点 `data` 里加字段：

```json
"uiScripts": { "scale": { "sha256": "…" }, "crop": { "sha256": "…" } }
```

- **由 AI 写**（写界面的同时声明），这条规定写进 MCP 手册 `canvas_ui_guide`；
- 是**打包的唯一依据**：包里带哪些脚本就读它；
- 也是**运行时的凭据**：调 `/api/task/call` 时后台按 `canvasId` + `nodeId` 读出声明，
  核对"这次要跑的脚本在不在声明里"。不在 → 403，并明确告诉 AI"这个节点没有声明脚本 X"。

  **校验是两级，不是三级**（2026-10-13 按用户口径实现后收敛，别再照旧稿说"三级"）：
    ① 按 canvasId + nodeId 把节点读出来（拿声明）；
    ② 看声明里有没有这次要跑的脚本名 —— 子进程在这两步**之后**才起。
  声明里的 `sha256` 是**打包/导入时**用来判"本机那份与包里那份是不是同一个"的，
  **不参与调用授权**：加它只会让"改一次脚本就得重签一次声明"，收益却是零
  （能改脚本文件的人本来就能改节点数据）。

地基：**没有它，包不知道该带什么、后台也不知道该不该放行。**

## 七、入口：导入（**版本判断在这里**）

三条路，落到同一件事：

1. **从资产库拖到画布** ← 用户点名的"这一步才检查版本"
2. **把 `.mcnode` 从文件系统拖到画布**
3. **从右键菜单标记**：把文件系统里的包"标记进资产库"（只上传存档，不落地、不判断版本），
   之后走第 1 条

左侧抽屉拖到画布**已有现成机制**（`application/x-mini-canvas-asset` 那条 MIME + 宿主捕获阶段接 drop）。
节点包是它的延伸：多一个类型，落点从"建媒体节点"改成"还原节点 + 落脚本 + 判断版本"。

## 八、版本：升级时**三处一起改名**（用户 2026-10-13 拍板）

### 8.1 判定

拖到画布落地时，逐个脚本与本机同名文件比对：

| 情况 | 结果 |
|---|---|
| 同名 + 内容一样（sha256 相同） | 用本机那份，不写、**不升版本** |
| 同名 + 内容不同 | **冲突** |
| 本机没有 | 直接写入，**不升版本** |

**只要有一个冲突 → 整包升版本**。不搞"一半改名一半不改"。

### 8.2 升级时改哪三处（一处不能漏）

用户口径：**标题、依赖声明、脚本文件，三处一起改名**，脚本用 `_v??.mjs` 形式。

以 v2 为例：

| 改什么 | 从 | 到 |
|---|---|---|
| ① 脚本文件 | `scale.mjs` | `scale_v2.mjs` |
| ② 依赖声明（节点 data） | `{ "scale": … }` | `{ "scale_v2": … }` |
| ③ 界面代码里的引用 | `name: "scale"` | `name: "scale_v2"` |
| ④ 节点标题 | `视频可视化` | `视频可视化_v2` |

（`_v2` 已被占用就找 `_v3`、`_v4`，往上找第一个空位。用户 2026-10-13 口径：
标题一律用**下划线、不带空格** —— 与脚本名同一套写法，一眼看得出是一对。）

产物就是用户那句：**一个全新的 V2 节点系统** —— 自带一整套自己的脚本，
与原来那个 v1 节点各跑各的，谁都不碰谁。

**为什么整套一起改**：一个节点的界面和它的脚本是**配套的一套东西**。
只改一半就会出现"v2 的界面调着 v1 的脚本"，看着能跑、实际行为是混的 —— 那种问题最难查。

### 8.3 资产库里的重名

存进库时若同名已有一份 → **自动加版本后缀**（`视频可视化的包` → `视频可视化的包 v2`），
不覆盖已有那份：库里存的都是能用的东西，不该被无声顶掉。

## 九、后台接口

```
POST /api/node-packages/build    { canvasId, nodeId }
  → 包字节（application/zip）
      纯打包，不落盘、不判断版本。导出下载 / 收藏弹窗都用它。

POST /api/node-packages/save     { canvasId, nodeId, name, folderId, tags? }
  → { ok, asset }       打包 + 直接存进资产库（MCP 工具走这条）

POST /api/node-packages/inspect  包字节
  → { ok, manifest, node, plan: { action: 'as-is' | 'bump', version, renames: [...] } }
      只体检：先告诉用户"这个包装下去会怎样、会不会升成 v2、哪些脚本要改名"

POST /api/node-packages/import   { 包字节, confirm }
  → { ok, node, version, written: [...], skipped: [...], renamed: [...] }
      node 回给前端 → 前端按它建节点
```

安全照抄现成规矩（`routes/serverPlugins.ts` 那套）：**导入脚本 = 往服务器放可执行代码**，
要 `confirm: true` + 同源检查。

**但落地时不再多弹一次确认**（用户 2026-10-13 拍板：「拖进来直接使用，不用点确认」）。
理由：拖包进来这个动作本身就是意图，再弹一次只是多一步点击；而真正拦风险的关口是
**同源检查**（只有本机页面能调）与**版本隔离**（有冲突就整包升版本，不动本机已有脚本），
这两条都在，所以「不弹确认」不等于「没护栏」。

## 十、左侧抽屉里那一行长什么样（我上次没说明白的那点）

我上次问的"抽屉里长什么样"，指的是：**收藏进去之后，左侧列表里那一行怎么显示**。
比如现在图片显示成一张缩略图 + 名字；节点包没有缩略图，所以得定：

- 图标：一个"节点包"的图标（区分于通用文件）
- 主文字：包的名字（用户在上传弹窗里填的）
- 悬停：显示"含 N 个脚本 · 3 天前"

我先按这样定，不占用你的决策。

## 十一、右键菜单的入口（2026-10-13 已实现）

右键菜单现在支持**用斜杠表达层级**（与设置面板同一套写法）：

| 注册时怎么写 | 菜单里长什么样 |
|---|---|
| `group: '资源库/节点'`, `title: '绘画流程'` | 资源库 ▸ 节点 ▸ 绘画流程 |
| `group: '资源库'`, `title: '节点/绘画流程'` | 同上（项名里写斜杠也认） |
| `group: '节点'`, `title: '复制一份'` | 平铺一行（**老写法行为不变**） |

于是"资源库里的节点包"将来可以**直接注册进右键的二级菜单**（每个包一项，挂在
`节点包` 分组下、分类可以再接一层斜杠），不必另造一套 UI。左侧抽屉那条拖拽路
仍是主路径（见第六节），右键这条是快捷入口。

## 十二、落地顺序（**2026-10-13 已全部做完**，见 docs/STATUS.md 五续）

1. **依赖声明 + 后台强制校验**（地基，单独一份规范）
2. 打包 + 导出（`build` 接口、右键两项、`canvas_ui_package` 工具）
3. 导入（`inspect` + `import` 接口、三条入口、版本化三处改名）
4. 资产库那一类（`kind: node-package`、`节点` 标签、抽屉显示与拖拽）

前两步做完就能"手动传包"；后两步是体验。
