# 画布插件上下文与依赖边界规格

日期：2026-09-27  
状态：可拆任务；实现范围见配套执行计划  
依据：2026-09-26 架构审查、2026-09-27 插件作者最终形态草稿、当前代码与项目状态记录

## 问题

插件系统已经有注册节点、区域、主题、命令、快捷键、工具、UI 组件和能力包的机制，但插件作者要在多个包和上下文入口之间切换。逻辑插件通常从 canvas-base 取类型，同时仍直接依赖 canvas-data、kernel 或 canvas-render；Vue 组件还会直接使用 VueFlow、默认主题组件和宽大的渲染上下文。

同一注册动作也可能经过通用注册场和兼容注册表两条路径。它们的 order、remove、source 和回收语义不完全相同，导致作者很难判断注册的条目在哪里、卸载后是否真的消失。

结果是：包名看起来分层，插件的真实依赖和接口事实源却仍有重叠；默认主题也被业务插件当作共享组件库，难以替换。

## 目标

让插件作者有一个短小、类型明确、可扩展的编程入口：

- 逻辑插件只需直接依赖 canvas-base，即可声明服务依赖、注册节点/区域/主题/插槽/命令/快捷键/配置和工具。
- 有 Vue 组件的插件可以使用稳定的渲染契约；业务组件不需要直接知道 VueFlow 的实例 API，也不需要依赖默认主题包。
- 节点组件通过 needs 获取共享能力；专属数据通过 props；文档读写通过类型明确的服务。
- 一次注册只建立一条权威记录；id、source、order、手动撤销和插件卸载使用相同语义。
- 插件卸载或主题替换后，UI 和能力立即随注册状态变化，且不存在兼容表中的残留条目。
- 数据层、画布注册契约和渲染实现之间维持单向依赖；基础契约不依赖 Vue、VueFlow 或具体 UI 第三方库。

## 用户故事

1. 作为插件作者，我希望只导入一个稳定的作者 SDK 类型入口来获得 Context、服务和注册契约，这样逻辑插件不必逐个认识 kernel 和 canvas-data 的内部类型。
2. 作为插件作者，我希望服务名能决定 ctx.get 的返回类型，这样常见服务不需要手写泛型或结构断言。
3. 作为插件作者，我希望仍可通过模块声明扩展自己提供的服务类型，这样 SDK 不必预先知道所有业务插件。
4. 作为插件作者，我希望注册节点类型时所有被类型允许的字段都能保留下来，这样图标、尺寸、连接约束和类型能力不会静默丢失。
5. 作为插件作者，我希望一次注册节点就能声明它的基础内容和尺寸，这样不必理解多张内部表。
6. 作为插件作者，我希望把组件挂到十个区域词中的任意位置，这样可以添加工具栏、状态、进度和编辑浮层。
7. 作为插件作者，我希望区域组件只拿到自己声明的 needs，这样通用能力可以复用，组件专属数据仍保持本地。
8. 作为插件作者，我希望把快捷键写在命令上，这样不必另学一个快捷键注册系统。
9. 作为插件作者，我希望可以注册画布级插槽、UI 组件和外部工具，这样插件能增加画布内容而不要求宿主逐项改代码。
10. 作为插件作者，我希望注册得到的条目能报告 id、来源和顺序，并随插件卸载自动撤销，这样排查覆盖和热卸载更直接。
11. 作为主题作者，我希望主题槽能被别的主题实现替换，且卸载替代主题后默认实现自动恢复。
12. 作为主题作者，我希望默认主题只提供主题实现和设计系统组件，不被业务插件当作公共运行库，这样新主题可以独立实现兼容契约。
13. 作为组件插件作者，我希望通过命名 UI 目录取按钮、下拉和端口等标准组件，这样更换主题时不用修改业务组件的导入。
14. 作为组件插件作者，我希望使用稳定的画布 Flow 能力完成缩放、坐标转换和节点视觉更新，这样 VueFlow 版本和实例细节留在渲染实现中。
15. 作为组件插件作者，我希望知道渲染桥何时可用；未挂载或宿主已停止时得到明确状态或错误，这样不会把 no-op 当成成功。
16. 作为宿主作者，我希望能在同一插件系统中装配画布数据和渲染实现，这样 headless 宿主不必加载 Vue。
17. 作为维护者，我希望 canvas-data 可在没有 Vue/VueFlow 的 Node 环境独立使用，这样云端和工具链不必依赖界面层。
18. 作为维护者，我希望 theme-default 可被替换且业务插件无直接依赖，这样插件依赖图保持单向。
19. 作为维护者，我希望兼容层与新注册场有一致的 observable behavior，这样可以按包逐批迁移而不丢行为。
20. 作为画布用户，我希望现有画布存档、连线能力、主题设置、撤销历史和插件行为在接口整理时保持兼容。
21. 作为画布用户，我希望更换主题不会重置节点数据、设置或插件注册，这样视觉实现可以独立调整。
22. 作为维护者，我希望端口几何默认值只有一个明确来源，并由浏览器回归证明，这样命中区域不会随装配路径变化。
23. 作为维护者，我希望已有注册场、能力包、surface 自省和节点区域机制被复用，这样不会再造第二套插件系统。

## 实施决策

1. 保留 kernel 的插件形状、生命周期、依赖装载、事件、作用域回收和 Registry 原语。此工作扩展作者契约，不重做内核注册场底座。
2. 把 canvas-base 定位为作者 SDK：集中导出插件类型、CanvasServices 类型映射、现有画布注册类型和渲染契约的纯结构类型。它不提供 Vue/VueFlow 运行时、CanvasHostHandle 或默认主题组件。
3. 逻辑插件继续使用现有的 name、inject、Config、apply(ctx) 形状。新增 Context 类型应以扩展兼容方式提供，不要求一次重写所有插件。
4. kernel 已有 Services 扩展接口和 tryGet。工作是让 get/tryGet 用服务名关联这份映射，并在 canvas-base 集中声明内置画布服务；未知服务仍保留模块声明扩展能力。运行时依赖仍由 inject 表达，get 仍用于可选访问，不以类型声明替代装载依赖。
5. 保留现有 ctx.nodes/theme/commands/slots/settings/tools、ctx.registryOf、UI 目录、节点区域和 needs 能力包。工作重点是统一底层事实源、类型和回收语义，不新增平行的 component、shortcut 或 capability API。
6. 快捷键继续作为命令的 keys 字段，由宿主统一分发；组件区域继续使用 ctx.nodes.attach 与 ctx.selectionRegion.attach。
7. 主题、节点区域及其兼容注册表必须有一个写入事实源。旧 NodeRegistry/ThemeRegistry 可以在迁移期间做读取适配，但不能各自保留独立的写入状态。
8. defineNode 的输入类型与运行时透传字段一致。添加新节点字段时，注册链路只有一个权威字段定义，并有端到端测试证明字段到达消费方。
9. VueFlow 不进入 kernel 或纯数据包。组件消费端通过 canvas-render 的 Vue 桥接入口取得窄的 CanvasFlowApi；插件 apply(ctx) 不拿实时 VueFlow 实例，因为此时 canvas surface 尚未挂载。原始 useVueFlow 只在渲染实现内部或明确的 escape hatch 使用。
10. Render facade 使用明确的生命周期状态，至少能区分等待 VueFlow 实例、实例已接入、DOM 锚点就绪和已销毁。不同能力可在不同阶段就绪；尚未就绪的命令不能静默 no-op，状态和失败方式在契约测试中固定。
11. 逻辑插件通过 canvas-base 取得框架和画布契约类型；只在源码直接使用运行时工具/纯计算包时声明对应依赖。组件插件可以声明 Vue 与稳定 render contract 为 peer dependency，并按需依赖其业务库。“只依赖 canvas-base”描述作者 API/类型入口，不要求把插件自身所用的 Vue、媒体库或业务库移除。
12. theme-default 只作为默认主题适配器与设计系统目录提供方。业务插件不能直接依赖 theme-default 获取组件；共享语义组件通过类型明确的目录契约消费。
13. canvas-foundation 是有门槛的后续包拆分候选，不是第一步搬家。先验证它能减少 canvas-data 的画布语义依赖、维持单向依赖和旧入口兼容；未达成则保持现有包并收敛接口。
14. 端口几何 86 与 10 的差异按行为变更处理。代码任务只在期望值被明确选择后开始；此前不得把其中一值当作默认答案写入实现。
15. 不改变画布文档格式、节点数据、连接规则、撤销历史、快捷键优先级、插件名称和既有存档兼容性。

## 测试决策

- 好的测试从插件或宿主可见的入口验证结果，不断言私有实现细节；兼容适配器测试关注两种读取路径是否一致。
- canvas-base：用编译期 fixture 写一个只导入 SDK 的逻辑插件；验证已知服务名推导、扩展服务声明及 defineNode 字段端到端透传。
- canvas-data/画布注册能力：经真实 Context 注册主题和节点区域，检查 order、覆盖、手动 remove、同 id 替换、scope unload 后的可见条目与渲染选择。
- canvas-render：以真实 VueFlow 宿主和可控挂载生命周期验证组件侧 facade 从等待、实例接入、DOM 就绪到停止的状态；未就绪调用必须明确失败，停止后不得继续调用旧实例。plugin apply(ctx) 不应能在 VueFlow 尚未挂载时误用该组件桥。
- plugin-theme-default：以真实主题注册链验证默认壳/边/背景/UI 目录可装载；主题组件拿到 typed 服务和 render facade；越出宿主时 fail-fast 行为明确。
- 业务插件：至少选择一个节点插件、plugin-multi-select 和一个逻辑插件验证新依赖方向与热卸载。
- 端到端：用浏览器验证主题替换后节点与工具栏正常渲染；卸载主题或复用组件提供者时，不出现旧组件；UI/快捷键/节点行为继续生效。
- 回归：每个包运行已有 Vitest 与 typecheck；影响 Vue 组件时运行 vue-tsc；影响装配/渲染时运行 UI e2e。
- 可参考的现有测试：capabilities 注册/回收测试、uiCatalog 响应式替换测试、BaseNode 区域/能力渲染测试、CanvasSurface/host 整链测试和 UI e2e。

## 不包含

- 不触碰根目录 src/ 和 packages/canvas-core v1。
- 不重写 kernel、Registry、命令分发、UI 目录、能力包或十个 NodeRegion。
- 不把全量 VueFlow 类型和实例暴露到 canvas-base。
- 不重做节点视觉、色板、主题设置界面、端口交互体验或用户画布内容。
- 不一次性批量删除旧 Context、Vue 注入令牌、包出口或数据入口；兼容入口按 expand–migrate–contract 迁移。
- 不将所有第三方库都放进 canvas-base；Vue 与具体主题库仍可按 package role 作为 peer/implementation dependency。
- 不在端口预期值未确认时决定 portZoneWidth 的最终行为值。
- 不把 settingsPersist 或各插件内部服务收回作为本期阻塞项；它们是独立清理任务。

## 补充说明

当前已有的能力：通用 Registry/registryOf/state、nodes/theme/commands/slots/settings、十个区域词、ctx.nodes.attach、UI 目录、needs 能力包、命令快捷键和 ctx.surface()。新工作从这些事实出发，不重复建设。

一处审查表述需精确：theme-default 的 inject=[] 本身不必然是装载错误，因为插件 apply 只注册主题组件；真正需要声明和验证的是主题组件只能在合法 render host 中运行，及其 render/data contract 是否就绪。不要把组件使用环境误当作 apply 阶段服务依赖。
