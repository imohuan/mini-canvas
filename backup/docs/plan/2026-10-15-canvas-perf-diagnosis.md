# 画布卡顿诊断报告（节点多起来就卡）

日期：2026-10-15
诊断页面：http://127.0.0.1:8860/#/canvas/default
诊断方式：Chrome DevTools MCP（真实浏览器里跑、真实测帧）
状态：**分析完成；方案已与用户对齐（见 §八 修订记录）**

---

## 一、先说结论

你画布上现在有 **160 个节点**。拖动或缩放的时候，**每一帧要花 70 毫秒**——浏览器一秒钟只能画 14 张画。人眼看 60 张才顺，所以就是"一顿一顿"。

同一块画布，只要**少画一点东西**，就能立刻回到 60 张：

| 场景 | 每帧耗时 | 感觉 |
|---|---|---|
| 什么都不动（空闲） | 16.7 毫秒 | 顺 |
| 160 个节点全画 | **70.6 毫秒** | 卡 |
| 只画 24 个节点 | **16.7 毫秒** | 顺 |
| 把节点内容整体藏起来 | **16.7 毫秒** | 顺 |

一句话：**不是 JS 代码在算得慢，是浏览器每帧在重新"刷漆"刷得太多。**

## 二、你说的"只渲染可见节点"去哪了

### 结论

**它被上一轮开发主动删掉了**，不是你没找到开关——是现在根本没有这个开关了。

证据（运行时实测）：

- 画面里无论缩放到 20% 还是 200%，DOM 里**永远是 160 个节点**，一个都没少 → 剔除完全没生效。
- 设置面板里查不到这个键（`settings.has('onlyRenderVisibleElements')` 返回 `false`）。
- 代码里默认值被写死成 `false`。

### 那"冲突"是什么

就是**嵌套组**（把节点放进分组里）。

当时的原话（提交 `60a50bf5`，2026-09-17）：

> VueFlow 1.48 的视口剔除对 parentNode 子节点使用相对坐标判定可见性
> （getNodesInside 未合并父 computedPosition），导致嵌套组的子节点被
> 误判为视口外而"消失"。嵌套组支持依赖该选项关闭，故不再暴露进设置面板。

翻译一下：

- VueFlow 自己的"只渲染可见节点"，判断位置时只看**节点自己记的坐标**。
- 但分组里的子节点，记的是**相对父节点的坐标**（比如"我在分组左上角往右 20 像素"）。
- VueFlow 没把父节点的位置加上去算，于是子节点算出来在屏幕外面 → 被当成看不见 → **分组里的东西整体消失**。
- 为了不让分组里的节点消失，干脆把这个功能整个关掉、连开关一起摘了。

### 关键点：这个"冲突"是可以绕开的

因为**我们项目自己已经有一份"绝对坐标"了**。

渲染层里有个 `nodeLayout` 服务，它的 `getAllRects()` 给的是**已经算过父节点位移的绝对矩形**（分组里那几个跟随/对齐插件就是靠它算的）。

所以正确做法不是"用 VueFlow 的剔除"，而是**我们自己算哪些节点可见，再把结果喂给 VueFlow**。这样嵌套组的坐标由我们自己算对，不会再"消失"。

## 三、卡在哪里：五个原因，按影响大小排

### 原因 1（最大头）：每帧重绘的东西太多

**这是主因，比别的加起来都大。**

怎么证明的？我把节点里的内容整体"藏起来"（内容还在，只是不显示），**帧耗时立刻从 70.6 掉到 16.7 毫秒**。

也就是说：节点的**数量**本身不是问题，节点**画出来有多少笔画**才是问题。

### 原因 2：浏览器在每帧重新"高清重画"

Chrome 从 53 版开始有个规矩：**用代码改缩放大小时，里面的内容每一帧都要重新高清重画一次**，除非你告诉它"这块我要快速动"。

那句"我要快速动"就是 CSS 里的 `will-change: transform`。

实测（同一场景，只加这一行 CSS）：

| 加在哪 | 每帧耗时 |
|---|---|
| 不加（现状） | 约 96 毫秒 |
| 加在节点层 | **约 24.8 毫秒** |
| 加在画布变换层 | 约 29.8 毫秒 |

代价：放大看的时候会有点糊（因为变成了"一张放大的图"）。所以正确用法是**只在你拖动/缩放的时候加，松手就摘掉**。

### 原因 3：一个节点挂了一堆"装饰件"

现在 160 个节点，实际挂出来的是：

| 东西 | 数量 | 说明 |
|---|---|---|
| `moving-handle-button`（端口圆球） | **320 个** | 每个节点 2 个 |
| 带 `box-shadow`（阴影）的元素 | **324 个** | 其中 320 个就是上面那些圆球 |
| 带 `transition`（过渡动画）的元素 | **546 个** | 圆球占 320、缩放手柄占 96 |
| 带 `drop-shadow`（滤镜）的 SVG 图标 | **96 个** | 滤镜每帧都要重算，最贵 |
| `resize-handle`（缩放手柄） | 64 个 | |
| `.mini-map` 里的子元素 | 161 个 | 见原因 4 |

再乘上"每帧重新画一遍"，就是很实在的开销。

有一个细节值得记住：低细节档（`is-low-detail`）下，`v2-title` 和 `resize-handle` 是真的 `display:none`（不渲染）；但**端口圆球只是 `opacity:0`**——元素仍然在 DOM 里、仍参与样式与布局计算，只是不画出来。实测当前缩放 20%（低细节已生效）时，320 个圆球全部存在，每个带着两层 `box-shadow`。节点数上去以后，这个差别会变得重要。

### 原因 4：小地图是用 DOM 画的

`.mini-map` 里面有 **161 个子元素**——每帧跟着重绘一次。用 canvas 画就没这个成本。

### 原因 5：图片和视频都是"原图"，没有按档位降级

现在有 64 个 `<img>`（32 个图片节点 + 32 个视频节点的封面），**全部是原始尺寸的图**。

有意思的是：你们**已经把方案写好了**——`docs/plan/2026-10-14-media-thumbnail-lod-plan.md`（图片/视频三档缩略图）。但代码里搜不到落地痕迹（`mediaTier` / `tierUrlFor` / `thumbNameFor` 都没有），说明还没做。

### 另外还抓到一个（次要但真实）

第一次抓性能火焰图时，抓到视频节点解码触发的长任务：**58 毫秒、103 毫秒**各一次（`VIDEO.onseeked`）。多视频节点同时播放时会有额外开销。

## 四、怎么改（按优先级）

### P0：把"只渲染可见节点"找回来，但用我们自己的算法

**为什么最优先**：实测它一项就能救回 4 倍（70.6 → 16.7 毫秒）。这是唯一能根治"节点越多越卡"的办法——因为它的效果是"画的东西不随节点总数增长"。

**核心规则（与用户逐条对齐后的最终版，2026-10-15）：零例外，一条判定。**

```
渲染 ⇔ 节点矩形（绝对坐标）与「视口矩形 + 缓冲带」相交
```

所有节点——普通节点、分组父节点、被选中的、正在拖拽的——**一律走同一个判定**，不做任何特判。理由：

- **选中是状态，不是画面。** 选中集存在内核 Selection 里，选中框（SelectionFrame）算的是数据坐标（`nodeLayout.getNodeRect`），不依赖 DOM。已实测验证：把屏幕外 30 个节点全部从 DOM 隐藏，选中框坐标一字不变。因此"被选中但滚出屏幕"的节点不需要渲染来维持选中态——全选 160 个，就只渲染视口内的约 30 个，其余 130 个只留数据。
- **拖拽也不需要例外。** 用户纠正：多选拖一大组时，成员会散布在视口外，"正在拖的节点必然在屏幕里"不成立。正确理由是：**不需要渲染也能正常工作**——拖拽位置由数据驱动（VueFlow position / nodeLayout），缓冲带保证节点滚回视野时已经在渲染（用户确认项目已有这层预渲染能力）。
- **分组父节点自动符合判定，无需特判。** 子节点在分组框内部：子节点命中视口 ⇒ 包含它的分组框必然命中。父节点与子节点各自独立过相交测试即可（它们是独立盒子，藏一个不影响另一个的绘制）。

**实施要点**：

1. **别开 VueFlow 自带的剔除**（就是那个会吃掉分组子节点的）。它在库里的判定逻辑是：
   ```
   nodeToRect(node) → 只取 node.computedPosition，不合并父节点位移
   ```
   只要用分组就一定踩雷。

2. **自己算**。渲染层里已经有一半现成的——`CanvasSurface.vue` 里的 `visibleRect`（当前可视区）和 `collectVisibleNodes()`（按可视区筛节点），只是现在只给对齐辅助线用。

   要做的是：把它从"查的时候临时算"改成"算出可见节点 id 集合，接入 `nodesFromStore` 过滤渲染列表"。

3. **判定必须用绝对矩形**，也就是 `nodeLayout.getAllRects()`（`NodeLayoutService`）——它已经累加过父链位移（`absolutePosition`），分组子节点不会再被误判。这正好绕开了那个"冲突"。

4. **缓冲带是可配置项**（用户已拍板）：设置面板加 `visibleCullBuffer`，默认 300，范围 0–2000。缓冲的意义除了防拖动闪白，还承担"被剔除节点滚回视野时的预渲染窗口"——不可设 0 以下。

5. **设置开关**：剔除默认开；另加 `dragRapidMode`（拖拽快速模式 will-change）开关，默认开（用户已拍板）。

**要注意的坑**：

- 拖动/缩放**结束**（moveEnd）时强制刷新一次判定（否则松手瞬间有残留）。
- 拖拽/平移过程中判定更新走 rAF 节流，与现有 dragEmitRaf 同一套路。
- 节点从"未渲染"恢复为"渲染"时，实测尺寸（ResizeObserver 量测）有一小段空窗，落回 `type.defaultSize` 兜底；缓冲带覆盖了这个窗口，这也是缓冲不能为 0 的原因之一。

### P1：拖动时给画布加"快速模式"

配合 P0 一起上。在手势开始/结束时开关 `will-change: transform`，挂在节点层上。

好处：在"可见节点仍然有点多"的情况下再省一半时间（96 → 24.8 毫秒）。成本低，改动集中在渲染层一个地方。

### P2：给节点的装饰件减负

1. 96 个 SVG 的 `drop-shadow` 滤镜：换成不带滤镜的做法（描边/双层图形），或者只在**选中/悬停**时才加。滤镜是每帧重算的，静止看着好看，动起来最贵。
2. 320 个端口小圆球的 `box-shadow` + `transition`：低细节档下**让它们不渲染**（现在是"渲染了但看不见"，成本一样付）。
3. 546 个 transition：检查有没有可以挪到"只在需要时加"的。

### P3：小地图改成 canvas 画

161 个 DOM 元素改成一个 canvas。有现成参考：项目里已经有 `canvas.bg-canvas` 和 `canvas.ce-canvas` 两个 canvas 图层，说明这条路是通的。

### P4：把已经写好方案的缩略图分档落地

`docs/plan/2026-10-14-media-thumbnail-lod-plan.md` 那份方案本来就是为这个场景写的，实测数字也在里面（原生帧 14.8KB / 512 档 3.8KB / 160 档 1.5KB）。它和 P0 是互补的：

- P0 管"**画几个**"
- P4 管"**每个画多重**"

两个都做了，才能撑到几千个节点。

> **状态更新（2026-10-15）**：P4 已在另一条任务线（"图片视频换挡显示"）落地并经用户确认生效——页面实测 60 张图里 54 张在用分档缩略图，视频非播放态全部走帧图。**本计划不再包含 P4**，唯一衔接点：剔除上线后 `ImageContent.vue` / `VideoContent.vue` 里"可视区外不生成缩略图"的闸门判定会更准，但代码无需改动。

### P5：小地图改 canvas（DOM 版每帧跟随重绘 161 个子元素）

`.mini-map` 目前每个节点渲染一个小方块 DOM，共 161 个子元素，视口每帧变化都跟着重绘。改成一个 `<canvas>` 用 viewport 数据自绘方块与视口框；交互（点击跳转、拖动视口框）保留。这是独立改动，与 P0 不耦合。

## 五、改完怎么验证（别靠"感觉快了"）

这次诊断用的方法可以固化成可复现的验证：

1. 打开页面，确认窗口**在前台聚焦**（失焦的话浏览器会把 rAF 降到 1 FPS，测出来的数字全是假的——我这次就被坑过，一度测出 1016 毫秒/帧）。
2. 用脚本连续改动视口变换，同时数每一帧的耗时。
3. 看两个指标：
   - **空闲帧耗时**（应该约 16.7 毫秒）
   - **拖动帧耗时**（目标是 ≤ 16.7 毫秒，也就是 60 FPS）

实测基线（2026-10-15，160 节点）：

```
空闲:              16.7 ms/帧
拖动（现状）:      70.6 ms/帧   ≈ 14 FPS
拖动（只画24个）:  16.7 ms/帧   ≈ 60 FPS
```

节点数曲线（同一轮实测）：

```
20 个 → 16.7 ms
40 个 → 16.7 ms
80 个 → 24.8 ms
160 个 → 31.6 ms
```

**验收标准建议**：在 160 节点、拖动/缩放场景下，帧耗时进入 16.7–25 毫秒区间，并且**不再是线性跟着节点数涨**。

## 六、一句话总结

你画布慢的**主因不是代码写得不好，是"该藏的没藏"**：

浏览器每帧都在把 160 个节点、320 个端口圆球、96 个滤镜图标、64 张原图，从头到尾重新画一遍。

本来有个开关能让它只画看得见的那几个（实测能到 60 FPS），但因为**VueFlow 自己的算法在分组场景下有 bug**，上一轮开发把它整个摘掉了。

修法很清楚：**算法换成我们自己算**（项目里已经有正确的绝对坐标和可视区工具），开关加回来。这一项就能解决大半问题。

1. ~~"选中的节点必然在视口里"~~ —— 多选后可平移走，选中节点会在视口外。选中是数据态，不靠渲染维持。

3. ~~"分组父节点需要特殊保留"~~ —— 子节点在父框内，子命中⇒父必命中，自然满足判定，无需特判。
4. ~~"选中框需要节点在 DOM 里"~~ —— 实测：隐藏 30 个屏外节点，选中框坐标不变（框算数据坐标）。

2. **`nodeLayout.getAllRects()` 的绝对坐标已含父链位移**（`absolutePosition` 逐级累加）——分组判定的正确坐标源，别用 `node.position`（相对坐标）。
3. **`expandRect` / `rectsOverlap` 已存在**（`canvas-render/src/geometry/visibleArea.ts`，纯函数有单测），直接用。
4. **`syncFromStore` 与 `syncSelected` 是两条重灌路径**（`CanvasHost.vue`），剔除过滤要同时覆盖两条，否则"选中变化"会把被剔节点灌回来。
5. **节点尺寸来源**：实测(ResizeObserver) > `node.size`（落盘） > `type.defaultSize`。被剔节点重进视口时实测值有空窗，defaultSize 兜底——画面闪一帧旧尺寸，缓冲带掩盖。
6. **含 64 个未落盘 size 的节点**（text/audio 等）：它们完全依赖实测，剔除-恢复循环里尺寸闪变风险最大，测试要覆盖。
7. **VueFlow 对 `node.dragging` 有内部特殊处理**（getNodesInside 里的 `|| node.dragging`）——我们不用它的剔除，但自己实现时确认拖拽中节点位置走 VueFlow 内部更新路径，别被剔除过滤打断。
8. **`selection.set(all)` 全选是数据态**（`multiSelectPlugin.ts` selectAll），已验证剔除后选中框坐标不变——不要"顺手"改成基于渲染列表。
9. **settings key 全局平面命名、先声明者独占**——`visibleCullBuffer` / `dragRapidMode` 要检查没被其他插件先声明（历史上`onlyRenderVisibleElements` 的键曾经存在，持久化里可能残留旧值，resolve 需容忍并收敛）。
10. **window 失焦时 rAF 掉到 1 FPS**——所有基于 rAF 的测帧/节流验证必须先确认 `document.hasFocus()`，否则数据全是假象（本轮实测踩坑：一度测出假 1016ms/帧）。
11. **含分组的 z 层级是"逐级累加"**（getXYZPos），分组父被剔除后子节点的 zIndex 计算不能依赖父存在——子节点独立携带 zIndex。
12. **edge 为 0 的画布也要测**（当前 160 节点 0 边）；有边时边端点落在被剔节点上，`edgesFromStore` 的 alive 集要基于**数据全集**而不是渲染集，否则边被误删。

### 9.3 审核建议的新路线：优先验证 `hidden` 标记方案

VueFlow 的 NodeWrapper 对 `hidden: true` 的节点**跳过渲染但保留在内部 store**（vue-flow-core.mjs:9560）。若把剔除从"数组里删掉"改成"喂 hidden 标记"：

- ✅ 边解析不断（R1 消失）
- ✅ 原生多选拖拽不掉队（R2 消失）
- ✅ `updateNodeVisual` 不再 no-op（R4 消失）
- ✅ 重进视口不重挂（尺寸空窗/闪变缓解，E2 影响大减）

代价：节点组件实例仍存在（VueFlow 内部仍有全量 GraphNode 记录），省的是"渲染准备作业"，内存占用不省——对本场景（省帧时间）正好够用。

**行动项：实施前先花半天做一个 hidden 方案的帧耗时对比验证**（同样 160 节点、同测帧脚本），若与数组剔除收益相当，则按 hidden 路线实施，修改清单相应简化；若 hidden 仍有明显残耗（如 hidden 但仍参与 style/layout 的部分），再回到数组剔除 + 以下补充项。

#### 9.3.1 hidden 方案的机制确认（子代理二轮核对，2026-10-15）

两个决定性问题已从 vue-flow-core.mjs 源码确认：

1. **hidden 是真·不渲染**（不是 CSS 隐藏）：NodeWrapper 的 render 在 `node.hidden` 时直接 `return null`（vue-flow-core.mjs:9559），组件树不产生任何 DOM、不参与 style/layout/光栅化——**收益与数组剔除等价**。三处佐证：hidden 节点被 getNodesInside 跳过框选（mjs:3743）；EdgeWrapper 端点 hidden 时整条边不渲染且**不报 EDGE_MISSING**（mjs:8888，节点仍在 store，边解析不断）；getNodesBounds 有 includeHiddenNodes 选项（mjs:5688）。
2. **但 M-3（实测尺寸保护）在 hidden 路线下仍然必须做**：hidden 时没有 .vue-flow__node 元素 → 我们自己的 MutationObserver（useNodeMeasure.ts:108）在 sync 时发现元素消失 → `clearMeasuredSize(id)`。VueFlow 内部对 hidden 的处理管不到我们的测量。也就是说 64 个无落盘尺寸节点的"剔除期间尺寸丢失"问题与数组剔除路线完全相同。

**结论：hidden 路线的优势明确**（R1 边不断 / R2 原生拖拽不掉队 / R4 updateNodeVisual 不 no-op / 无重挂），**且渲染收益与数组剔除等价**。实施路线定为：**hidden 标记方案**（半天帧耗时对比验证只作为保险确认，预期通过）。M-3 保留为必做项。
