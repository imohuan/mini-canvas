# 插件形态与生命周期

> 来源：`packages/kernel/src/types.ts`（`PluginModule` / `PluginScope`）、`packages/kernel/src/pluginClass.ts`（`asPluginModule`）、
> `packages/kernel/src/service.ts`、`packages/kernel/src/Context.ts`（`plugin` / `start` / `drain` / `installPlugin` / `uninstallPlugin` / `canUninstall`）、`packages/kernel/src/fiber.ts`。

讲两件事：**一个插件能长成哪几种样子**、**插件从被装到被卸都经过哪些状态**。

---

## 1. 所有插件最终归一成一种对象：PluginModule

不管作者怎么传，内核内部都先把它看成下面这个对象（`packages/kernel/src/types.ts:282`）：

```ts
interface PluginModule<TConfig extends object = object> {
  name: string // 唯一名，必须给
  core?: boolean // 核心插件：拒绝动态热卸（见 §5.5）
  deps?: string[] // 依赖（老写法）
  inject?: string[] // 依赖（推荐写法，优先于 deps）
  Config?: ConfigSchema // 本插件的配置 schema（可选）
  setup?(ctx: PluginScope): void | (() => void) | Disposable // 老写法
  apply?(ctx: PluginScope, config?: TConfig): void | (() => void) | Disposable // 推荐
}
```

字段含义：

- **`name`**：插件唯一名，全内核不能重名（重名抛 `Duplicate plugin name`）。
- **`inject` / `deps`**：这份插件**必须等谁先就绪**。里面可以写两类名字：
  - 一个**服务名**（别的插件 `provide` / `inject` 提供的服务）；
  - 另一个**插件名**。
  依赖不满足就停在 PENDING，等提供方出现。
- **`Config`**：本插件的配置 schema（见《配置装配篇》）。
- **`apply`**：真正的注册函数。**`apply` 优先于 `setup`，`inject` 优先于 `deps`**；二者至少给一个。
- `apply(ctx, config)` / `setup(ctx)` 可以返回一个 cleanup 函数或带 `dispose()` 的对象，内核把它登记进插件自己的回收袋，**卸载自动调用**。

`runPlugin` 的判定顺序（`packages/kernel/src/Context.ts:127`）就是：`mod.apply` 有就调 `apply(ctx, config)`；否则有 `mod.setup` 就调 `setup(ctx)`；都没有则什么都不做。

## 2. 三种写法

### 2.1 对象形态（推荐）

`.ts` 里裸导出 `name / inject / Config / apply`：

```ts
// my-plugin.ts
import type { PluginScope } from '@mini-canvas/canvas-base'

export const name = 'my-plugin'
export const inject = ['doc'] // 可选：依赖的服务名 / 插件名
export const Config = {
  speed: { type: 'number', default: 1, min: 0, max: 10 },
}

export function apply(ctx: PluginScope, config: { speed: number }) {
  // ctx 是能力台，注册都自动回收
  ctx.nodes.register({ type: 'my', label: '我的节点', size: { w: 100, h: 80 } })
}
```

装配方把它装上去：

```ts
import * as myPluginModule from './my-plugin' // 上面那个文件（默认导出的四样就是插件模块）
ctx.plugin(myPluginModule, { speed: 3 }) // 第二个参是装配配置
await ctx.start()
```

### 2.2 类形态（`extends Service`）

把"一个类"直接当插件。类通常继承 `Service`，构造时 `super(ctx, name)` 顺手上架一个同名服务；
`new 类(ctx, config)` 就算把插件跑起来了（`asPluginModule` 的 `apply` 就是这一句，`packages/kernel/src/pluginClass.ts:72`）。

```ts
import { Service, type PluginScope } from '@mini-canvas/kernel'

export class GreeterService extends Service {
  static inject = [] as string[]
  static Config = { greeting: { type: 'string', default: 'Hi' } }
  constructor(ctx: PluginScope, config?: unknown) {
    super(ctx, 'greeter') // 上架服务名 'greeter'
    void config
  }
  greet(who: string) { return 'Hi ' + who }
}

// 装配：直接传类
ctx.plugin(GreeterService)
await ctx.start()
```

> 类形态归一规则（`packages/kernel/src/pluginClass.ts:53`）：只有 `extends Service` 的类走"类形态"这条路，
> `name` 取类静态 `provide`（是数组就取第一个）否则取类名，`inject` 取类静态 `inject`，`Config` 取类静态 `Config`，
> `core` 取类静态 `core`。构造里 `super(ctx, name)` 上架的服务随本插件回收。
>
> **注意**：类形态只读静态 `inject`，**不读静态 `deps`**。

不传 `name` 时也可以走静态 `provide` 字段：

```ts
class StaticNamed extends Service {
  static provide = 'staticName' // 构造不传 name 时取它
  constructor(ctx: PluginScope) { super(ctx) }
}
```

### 2.3 函数形态

一个**具名**函数也能当插件：函数名就是插件名，函数体当成 `apply(ctx, config)` 调用。

```ts
export function heartbeat(ctx: PluginScope) {
  ctx.on('ping', () => console.log('pong'))
}
ctx.plugin(heartbeat)
```

> **坑**：必须具名。匿名函数会抛 `[core] 函数形态插件需具名（不能是匿名函数），以便装配寻址/诊断。`
> 另外，函数形态插件的**返回值被直接丢弃**——它不被当成 cleanup（`packages/kernel/src/pluginClass.ts:89`）。要注册清理请用 `ctx.effect`。

## 3. Service 基类：往 ctx 上架一项能力

类形态的底座是 `Service`（`packages/kernel/src/service.ts:26`）。`super(ctx, name)` 内部调 `ctx.provide(name, this)`。

```ts
abstract class Service {
  readonly ctx: PluginScope
  readonly name: string
  constructor(ctx: PluginScope, name?: string)
}
```

- 不传 `name` 就取子类静态 `provide` 字段；再没有就抛 `[core] Service 需传 name 或给子类静态 provide 字段`。
- 上架的服务随所属插件回收：装 → `ctx.get` 有；卸 → `ctx.get` 返回 `undefined`。

## 4. 生命周期状态（两套名词要分清）

### 4.1 Lifecycle —— 业务生命周期（`ctx:lifecycle-change` 事件用）

`packages/kernel/src/types.ts:46` 的 `enum Lifecycle`：

```
装载：INSTALLING → ACTIVATING → ACTIVE
出错：INSTALLING / ACTIVATING → ERROR
卸载：ACTIVE → UNINSTALLING → UNINSTALLED
（枚举里还有一个 INSTALLED，但内核从不下发它 —— 见下面的说明）
```

> 说明：`INSTALLED` 这个枚举值存在，但 `Context.setLifecycle` 实际只下发
> `INSTALLING / ACTIVATING / ACTIVE / UNINSTALLING / UNINSTALLED / ERROR` —— **`INSTALLED` 从不被触发**。
> 监听 `ctx:lifecycle-change` 时以实际下发的这几个为准。

### 4.2 FiberState —— 插件运行时状态机（诊断主看这个）

`packages/kernel/src/fiber.ts:20` 的 `FiberState`（用字符串常量，方便展示和比较）：

```
PENDING → LOADING → ACTIVE
   ↘        ↘
  （缺依赖）  FAILED（apply / config 抛错）
卸载：ACTIVE / FAILED / PENDING → UNLOADING → DISPOSED（不可再启动）
```

| 状态 | 字符串 | 大白话 |
| --- | --- | --- |
| `PENDING` | `pending` | 已声明 / 在等所需服务 |
| `LOADING` | `loading` | `apply` / config 校验正在跑 |
| `ACTIVE` | `active` | 跑起来了，服务可用 |
| `FAILED` | `failed` | `apply` 或 config 校验抛错了 |
| `UNLOADING` | `unloading` | 清理中 |
| `DISPOSED` | `disposed` | 已卸载，不可再启动 |

**状态推进你基本不用手动做**，内核在 `start` / `install` / `uninstall` / `stop` 时自动推。
怎么查、怎么诊断卡在哪，看《Fiber 状态机与诊断篇》。

## 5. 冷启动 / 热装 / 热卸 / 热重载

| 操作 | 方法 | 只能用在哪 | 说明 |
| --- | --- | --- | --- |
| 冷启动装载 | `ctx.plugin(mod, config?)` | `start()` **之前** | 登记，等 `start()` 一起跑 |
| 启动 | `await ctx.start()` | state=`created` | 按依赖多轮激活 |
| 停机 | `ctx.stop()`（同步） / `await ctx.stopAsync()`（等异步清理） | state=`started` | 倒序卸光，可重新 start |
| 运行中热装 | `ctx.installPlugin(mod, config?): string` | `start()` **之后** | 返回插件名 |
| 运行中热卸 | `ctx.uninstallPlugin(name): boolean` | `start()` 之后 | `false` = 没卸到 |
| 热重载 | 先 `uninstallPlugin(name)` 再 `installPlugin(同名新实现)` | `start()` 之后 | 同 name 可装新实现 |

### 5.1 冷启动 `start()` 怎么跑

`start()` 做"确定性多轮激活"（`Context.drain`，`packages/kernel/src/Context.ts:312`）：

1. 反复扫所有插件，谁 `inject` 依赖**现在**满足了就激活它；
2. 依赖满足的判定是三条之一：是**已上架的服务名**、是**已配且 ACTIVE 的插件名**、或能力层内置服务名；
3. 激活顺序 = 插件登记顺序（确定性）；
4. 全跑完广播 `ctx:ready`。

所以依赖方先登记、提供方后登记也没关系：

```ts
ctx.plugin({ name: 'consumer', inject: ['greeter'], apply() { /* 一定在 greeter 之后跑 */ } })
ctx.plugin({ name: 'greeter-plugin', apply(c) { c.provide('greeter', {}) } })
await ctx.start() // 实际顺序：greeter-plugin → consumer
```

### 5.2 `start()` 时缺提供方会怎样？

**不报错**。缺依赖的插件安静停在 `pending`，`ctx:ready` 照常广播（`plugins` 里只有已激活的）。之后补上提供方，会被自动唤醒：

```ts
ctx.plugin({ name: 'c', inject: ['late-svc'], apply() {} })
await ctx.start() // 不抛错
ctx.fiber('c')?.stateName // 'pending'
ctx.installPlugin({ name: 'p', apply(c) { c.provide('late-svc', {}) } })
ctx.fiber('c')?.stateName // 现在 'active'（被唤醒）
```

### 5.3 热卸会"连坐"

卸掉一个插件后，内核会找"现在因它消失而不再满足声明依赖"的已激活插件，把它们也回收副作用并回退 `pending`
（保留登记，等服务恢复后自动重载）。传递链会一层层带下去（`Context.retractUnsatisfiedActives`）。

> 大白话：A 依赖 B 的服务。卸 B → A 立刻跟着下线；重新装回 B → A 自动重跑。依赖关系是活的。

### 5.4 热重载（HMR 用这个思路）

```ts
ctx.uninstallPlugin('p') // 卸旧实现
ctx.installPlugin({ name: 'p', /* ...新实现 */ }) // 装同 name 的新实现
```

同名能重装，是因为卸载时把旧登记清掉了；依赖它的插件会经历"回退 → 自动重载"。

### 5.5 核心插件拒绝动态卸载

插件可以声明 `core: true`（对象形态）或 `static core = true`（类形态）。被标记者 **`ctx.uninstallPlugin` 直接返回 `false`，
而且一次真副作用都不产生**：不 dispose fiber、不发 `ctx:plugin-uninstalled`、不连带回退依赖方。

调用方想区分"被拦"和"不存在"，用 `ctx.canUninstall(name)` 先问（只读）：

```ts
const verdict = ctx.canUninstall(name)
// { ok: true }
// { ok: false, reason: 'core' }        —— 核心插件不让卸
// { ok: false, reason: 'not-found' }   —— 没装过 / 已卸
// { ok: false, reason: 'not-started' } —— 内核还没 start
```

`ctx.stop()` / `ctx.stopAsync()` **不受这个守卫限制** —— 整体生命周期终结不是动态卸载，页面关闭时核心插件也要正常回收。

## 6. 插件在 `apply` 里再装子插件

插件里可以调 `ctx.plugin(childMod)`：运行时会自动走热装语义（不会因 state 不是 `created` 抛错），返回自身便于链式。
子插件**扁平并入根**的插件表 / 服务表。

```ts
ctx.plugin({
  name: 'parent',
  apply(c) {
    c.plugin({ name: 'child', apply() {} }) // 运行时 → 等价 installPlugin
  },
})
```

## 7. 坑与速记

1. 对象插件 `apply` 优先于 `setup`；`inject` 优先于 `deps`。
2. `apply` / `setup` 返回的 cleanup（函数或带 `dispose` 的对象）会被登记，卸载自动跑；**函数形态插件的返回值例外，被丢弃**。
3. config 校验失败 → 插件进 `failed`（抛 `ConfigError`，带字段名与期望），插件被移出可装载表，但 fiber 保留供诊断，可重装同名复用。
4. `uninstallPlugin` 返回 `false` 表示没卸到（没装 / 已卸 / **核心插件被拦**），不抛错。
5. `Service` 子类 `super(ctx, name)` 时，若这个服务名已被占用会抛 `already injected`。
6. 想装同名插件必须先卸掉旧的（重名抛错）。
