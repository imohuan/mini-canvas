# mini-canvas 开发总览与架构

> 来源：`packages/kernel/src/`、`packages/canvas-data/src/`、`packages/canvas-render/src/`、`packages/ui/src/` 的源码与注释。
> 本目录是**按包分层**的 API 手册：`kernel/`（纯插件框架）、`canvas-data/`（数据 + 画布语义）、
> `canvas-render/`（渲染宿主）、`plugins/`（成品插件）。
> 想「从零写一个插件」请看 `docs/plugin-dev/`（作者教程，照抄能跑）；本目录讲每个 API 怎么用、为什么这么设计。
> 架构决策与迁移记录见 `docs/design/core-layers-and-registry.md`。
> 🎨 **写任何 UI / 颜色前先看 `主题与配色.md`**：主题只有一个开关 `<html class="dark">`，
> 配色一律走 CSS 变量，不允许插件自造 `theme` 配置项。

## 一、五个包分别是什么

| 包 | 职责 | 依赖 |
|---|---|---|
| `@mini-canvas/kernel` | **纯插件框架**：装载 / 依赖编排 / 事件 / 作用域回收 / 配置 / 注册场原语。**零画布概念、零 Vue** | 不依赖任何 `@mini-canvas/*` 包 |
| `@mini-canvas/canvas-data` | **数据层 + 画布语义**：节点/边数据、事务与撤销、选中、存储、连线校验、节点与主题注册表、`ctx.nodes/theme/commands/slots/settings` 这几段糖 | kernel |
| `@mini-canvas/canvas-render` | **渲染宿主**：把内核接到 Vue + VueFlow 上，一行 `<CanvasHost>` 出画布；注入 `nodeLayout`/`viewport` 两个服务 | canvas-data |
| `@mini-canvas/canvas-base` | **插件作者的薄入口**：重导出 kernel + canvas-data 的类型，加 `defineNode`/`defineTheme` 等助手 | kernel + canvas-data |
| `@mini-canvas/ui` | **成品应用出口**：`mountCanvasApp()` 一行启动整个画布应用（静态清单 + 环境选装，见 `assembly.ts`） | canvas-render + 全部插件 |

`packages/plugins/*` 是 36 个**插件**（主题、节点、工具、交互），既是能力来源也是本手册的主要案例。
另有 `packages/cloud-server`（自托管云端 + MCP 控制画布）与 `packages/mcp-server`（AI 工具链后端）。

**依赖方向恒为单向**：`kernel ← canvas-data ← canvas-render ← plugins`。
kernel 不 import 任何 `@mini-canvas/*` 包、不碰 Vue、不碰 DOM，所以能在 Node 里直接跑单测。

> ⚠️ 仓库根目录的 `src/` 与 `packages/canvas-core` 是**已停用的 v1**，本手册不描述，也不要照它写代码。

```
│    nodeStore/edgeStore/graphDocument/history（doc 持有的类）     │
│    canvas/capabilities  —— ctx.nodes/theme/commands/slots/settings│
│    canvas/registry/*    —— nodeRegistry / themeRegistry         │
│    canvas/connection.ts —— 连线严格校验                          │
├──────────────────────────────────────────────────────────────┤
│  kernel（纯插件框架，零画布概念）                                │
│    Context              —— 生命周期 / 服务注入 / 事件 / 作用域    │
│    Scope / Fiber        —— 副作用自动回收 / 插件状态机           │
│    registry/registry.ts —— **通用注册场**（ctx.registryOf）      │
│    EventBus / SettingsStore / configSchema / toolRegistry / command│
└──────────────────────────────────────────────────────────────┘
```

**数据流一句话**：插件经 `ctx` 注册「我能做什么」；内核存图数据（节点/边）；
`CanvasHost` 订阅数据变化，自动把 store 灌成 VueFlow 的 nodes/edges 渲染出来，
再经 provide 令牌把内核能力递给 content 组件。**改数据就自动重画**，不用手动同步。

## 三、三根轴：装载 / 服务 / 注册

这是理解整套设计最关键的一节。内核所有扩展点归到三根轴上，**别把它们搞混**：

| 轴 | 往里放 | 读出来 | 什么时候用 |
|---|---|---|---|
| **装载** | `ctx.plugin(mod)` / `ctx.installPlugin(mod)` | `ctx.inspectPlugins()` / `ctx.registry` | 装/卸/热重载一整块功能 |
| **服务** | `ctx.inject(name, impl)` / `provide` | `ctx.get(name)` | 按**名字取一个对象**，会换实现（有状态、有方法） |
| **注册** | `ctx.registryOf(kind).add(key, value)` | `ctx.registryOf(kind).list/top/resolve` | 按**种类放一串条目**（一张表） |

一句话判据：**按名取一个能手 = 服务；按种类放一串东西 = 注册场。**

> **最常见的错误**：每加一个新功能就新增一个服务。
> 正确做法是往注册场里 `registryOf('新种类').add(...)` —— 不占服务名，还自带叠层/替换/回收/诊断。
> 历史上的 `menu` 服务就是「只服务右键菜单一个插件」而新建的服务，后来被删除并合回那个插件自己。

**自省**：`ctx.surface()` 一次把三根轴读出来（只读、零副作用）：

```ts
const s = ctx.surface()
s.services          // [{ name, source, methods? }] —— 按名可取的服务 + 谁注入的 + 方法清单
s.registries        // [{ kind, keys: [{ key, count }] }] —— 每个场有哪些键、几条
s.registryEntries   // [{ kind, key, id, order, source, fields? }] —— 每条谁放的、值有哪些字段
s.commands          // [{ id, title, keys, areas, group, origin }]
s.tools             // 生成工具 + 声明式参数（下拉/开关怎么渲染）
s.modelTools        // 模型可调用工具（description / parameters JSON Schema / outputSchema）
s.events            // 已登记的事件名（能 ctx.on 监听什么）
```

## 四、四个核心概念

1. **插件（Plugin）** —— 一个带 `name` + `apply(ctx, config)` 的对象，或一个 `extends Service` 的类，
   或一个具名函数（函数名即插件名）。节点类型、主题、命令、工具都是插件干的。
2. **Context（ctx）** —— 插件 `apply` 拿到的对象，插件的全部世界：
   `ctx.on/emit`（事件）、`ctx.get/inject/provide`（服务）、`ctx.nodes/theme/commands/slots/settings`（注册糖）、
   `ctx.registryOf/state/isDev/surface`（原语）、`ctx.effect`（副作用）、`ctx.plugin`（子插件）。
3. **Scope / Fiber** —— 每个插件一个。所有「要清理的东西」（监听、定时器、注册、上架的服务）
   自动挂到自己的 scope 上，插件卸载时一次清光。**所以插件作者永远不用写 uninstall。**
4. **服务 vs 注册场** —— 见上一节。

## 五、最快跑起来

成品应用一行起（见 `packages/ui/src/index.ts`）：

```ts
import { mountCanvasApp } from '@mini-canvas/ui'
mountCanvasApp('#app')
```

想自己装配就用渲染层宿主组件（等价于 `packages/ui/src/App.vue` 的简化版）：

```vue
<script setup lang="ts">
import { CanvasHost } from '@mini-canvas/canvas-render'
import { LocalStorageAdapter } from '@mini-canvas/canvas-data'
import { themeDefaultPlugin } from '@mini-canvas/plugin-theme-default'
import { nodeTextPlugin } from '@mini-canvas/plugin-node-text'
import { nodeImagePlugin } from '@mini-canvas/plugin-node-image'

// 顺序即装载顺序
const plugins = [themeDefaultPlugin, nodeTextPlugin, nodeImagePlugin]
const adapter = new LocalStorageAdapter()   // 存 localStorage，刷新不丢

// 首次打开（存储为空）时的默认画布
const seed = () => [
  { id: '1', type: 'text', position: { x: 120, y: 120 }, data: { text: '双击我输入' } },
  { id: '2', type: 'image', position: { x: 500, y: 160 }, data: { imageUrl: '' } },
]
</script>

<template>
  <CanvasHost :plugins="plugins" :adapter="adapter" :seed="seed" window-key="MiniCanvasUI" />
</template>
```

画布通用命令（建节点 / 删选中 / 撤销 / 重做）由 `canvas-data` 的 `canvasBasePlugin` 自带，
宿主 boot 时默认注册，**不占插件位**。拖动会落盘、拉线自动校验并存边、Delete 删选中、Ctrl+Z 撤销，全都内置。

> 开发时跑：`pnpm -C packages/ui dev` → 浏览器开 **http://localhost:5288**。
> 宿主 API 挂在 `window.MiniCanvasUI`（`getContext()` 拿 ctx、`getHost()` 拿宿主句柄、
> `installPlugin/uninstallPlugin/reloadPlugin/listPlugins/inspectPlugins` 热装卸与诊断）。

## 六、装插件的三种方式

| 场景 | 写法 |
|---|---|
| **冷启动**（页面一开始就要） | `createMiniCanvasHost({ coldPlugins: [...] })` 或 `<CanvasHost :plugins="[...]"/>`；顺序即装载顺序 |
| **热装**（运行时想加） | `ctx.installPlugin(mod)` 或门面 `api.installPlugin(mod)`；依赖满足立刻生效，副作用自动回收 |
| **装配清单 manifest**（要 disabled / 每个插件单独配 config / 同 id 换版本） | `createMiniCanvasHost({ manifest })` 或 `manager.applyManifest(manifest)`；用 manifest 时 `plugins` 忽略（manifest 优先） |

插件里再想装子插件，用 `ctx.plugin(mod)`（运行期会自动转成热装）。

**卸载保护**：插件可声明 `core: true`（对象形态）或 `static core = true`（类形态）→ 被标记者**拒绝动态卸载**，
`ctx.canUninstall(name)` 返回 `{ ok:false, reason:'core' }`，`inspectPlugins()` 的每项也带 `core: true`
（宿主据此禁用卸载按钮）。画布基础服务 `canvas-base` 就是这么护住的：它一被卸，数据层就没了。

## 七、为什么插件不用写清理代码

老的写法要在卸载时逐个 `off` 监听、`clearInterval`、注销注册 —— 总会漏。
现在的做法是**每个插件挂一个垃圾袋（Scope）**：

```ts
apply(ctx) {
  ctx.on('ctx:ready', handler)      // 卸载时自动取消监听
  ctx.effect(() => {
    const t = setInterval(tick, 1000)
    return () => clearInterval(t)   // 想更精细就返回清理函数
  })
  ctx.nodes.register({ type: 'x', label: 'X', size: { w: 10, h: 10 } })  // 卸载时自动注销
  ctx.inject('mySvc', { ... })      // 卸载时自动撤下服务
}
```

判定标准：**`on` / `effect` / `inject` / 各类 `register` / `attach` 登记进本插件 scope → 卸载即清光；
`get` / `emit` 是读操作与广播，不登记。**

## 八、依赖方向红线

- `kernel` **不 import** 任何 `@mini-canvas/*` 包、不 import 任何 `.vue`（组件句柄对内核是 opaque 的）。
- 插件 / 渲染层 → 内核，方向恒为单向；**永远不要反向 import**。
- 插件之间不要直接互相 import 实现：用 `inject: ['服务名']` 声明依赖（内核负责编排顺序），
  或经 `ctx.registryOf(kind)` 取别人放进场里的东西。
- content 组件要调服务：用 `useCanvasRender()` 拿 `ctx`（或注入令牌），再 `ctx.get('...')`。

## 九、服务名速查（`ctx.get`）

| 服务名 | 谁提供 | 是什么 |
|---|---|---|
| `tools` | kernel 自带 | 生成工具注册表（文生图/图生文等外部能力，按名调用） |
| `slots` / `settings` | canvas-data 能力层内置 | 通用 UI 槽容器 / 配置单一数据源 |
| **`doc`** | canvas-data | **数据唯一门面**：节点 + 边 + 事务 + 撤销 + 快照落盘 + 订阅 |
| `save` | canvas-data | 存储适配器（内存 / localStorage / 以后云端） |
| `resources` | canvas-data | Blob / objectURL 生命周期 |
| `nodeRegistry` / `themeRegistry` | canvas-data | 节点展示段 / 主题槽注册表 |
| `selection` | canvas-data | 选中态（节点桶 + 边桶） |
| `command` | canvas-data | 命令注册表（快捷键由渲染层统一分发） |
| `nodeFactory` | canvas-data | 建某类型节点的实现表 |
| `nodeLayout` / `viewport` | canvas-render 宿主 | 节点几何只读 / 视口读写与坐标换算 |
| `settingsPersist` | canvas-data（条件注入） | 配置落盘桥（`persistSettings` 开时才上架） |

> ⚠️ 老服务名 `nodeStore` / `edgeStore` / `graph` / `history` **已下线**（`ctx.get` 取不到，返回 `undefined`）——
> 它们合并成了 `doc` 一个服务。那几个**类**还在（由 canvas-base 建好后交给 `doc` 持有，
> 宿主句柄 `host.nodeStore` 上也仍能直接拿到实例），但**它们不是 ctx 服务名**。作者侧一律用 `ctx.get('doc')`。

## 十、节点区域词与主题槽（两个高频速查）

**节点区域词（NodeRegion，十个）** —— 决定「往节点哪个位置放东西」：

```
title         标题位
in            卡片内部（内容组件；可叠多层）
out:top       卡片上边外侧        out:bottom    卡片下边外侧
out:left      卡片左边外侧        out:right     卡片右边外侧
on:top        贴在卡片上边框线上（进度条）   on:bottom   下边框线上
over:inset    卡片内部覆盖层（编辑浮层，不超出卡片）
over:outset   盖住整张卡且允许超出边界（拖拽手柄 / 悬停放大）
```

> ⚠️ 老五段名 `content` / `top-toolbar` / `bottom-toolbar` / `overlay` **已下线**：写它们是类型错误，
> 运行时也会抛错并列出合法词（`packages/canvas-data/src/canvas/region.ts` 的 `assertRegion`）。
> 对照关系：`content`→`in`、`top-toolbar`→`out:top`、`bottom-toolbar`→`out:bottom`、`overlay`→`over:inset`。

**主题槽（ThemeSlot）** —— 决定「哪一块外观可以被顶替」：

```
nodeShell            全局节点壳（默认 BaseNode）
nodeShell:<type>     某类型专属壳（nodeShellSlot(type)）
edge                 连线组件        edgeDefaultType  默认线型键
background           画布背景        connectionLine   拖线临时线
settingsPanel        设置面板皮
                      （最外层 Dialog 由 SettingsShell 提供；槽里注册的是中间层：左导航 + 内容）
```

**单格换肤点取 `order` 最小者（winner）**；`ctx.theme.register` 同槽重复会抛错（防误覆盖），
`ctx.theme.add` 是叠加。

## 十二、给插件作者的两条新东西（2026-09 新增）

**① 组件目录（`registryOf('ui')`）** —— 别 import 主题包用按钮，按名取：

```ts
import { useUiComponent } from '@mini-canvas/canvas-render'
const NodeToolbarButton = useUiComponent('button')   // 模板里 <NodeToolbarButton/> 自动解包
```

主题插件把设计系统件登记进 `registryOf('ui')`，**换一套主题时业务插件一行不改**。
当前 theme-default 登记了 `button` / `dropdown` / `select` / `slider` / `toolParamField`。

**② 能力包（`registryOf('capability')` + `needs`）** —— 通用 hooks 不用每个组件重写：

```ts
// 插件注册一个能力（每节点一份实例）
ctx.registryOf('capability').add('展开', (node) => ({ open: false, id: node.id }))

// 往节点上挂组件时声明要哪些能力
ctx.nodes.attach('image', { region: 'out:top', component: GenButton, needs: ['展开', 'node'] })
```

```vue
<script setup>
const { node, 展开 } = useCapabilities()      // 只拿得到 needs 里声明过的
</script>
```

宿主已注册标准四件 `node` / `zoom` / `selected` / `tools`。`needs` 缺项：**dev 抛错、prod undefined + warn**。
同一节点上声明同一个 needs 的两条条目**共享同一个实例**（所以按钮和它打开的面板能共享状态）。
