# 37 · 节点组打包带上资源

- 状态：已完成
- 负责人：Codex
- 完成时间：2026-11-17

## 你的原话

> 你这里保存节点组的时候需要注意：你在打包的时候，需要将资源也打包进去，然后导入的时候重新上传对应资源，获取属于当前画布的一个ID。
>
> 我总结一下：不允许当前画布引用其他画布的内容和资源，所有资源都保存到对应的画布里面。因为我们这边一个画布就相当于是一个文件夹，画布中禁止出现第三方url和其他画布资源数据，这是硬性规定。

## 要解决的问题

节点组收藏进资产库时，组里的图片、视频、音频要跟着一起打包；拖回任意画布时，这些字节要重新存进当前画布，拿到当前画布的 ID，再建节点。不能出现“组里有图，但图指向收藏时那张画布”的情况。

## 范围与位置

- 页面：画布里的节点组收藏、资产库的“节点组”、右键菜单“资源库 ▸ 节点组”
- 参考代码：`apps/web/src/composables/groupPack.ts` 的 `GroupPack/buildGroupPack/parseGroupPack/planGroupPlacement/hydrateGroupPackMedia`、`apps/web/src/assetUploadPlugin.ts` 的 `saveGroupToAssets/syncGroupCommands`、`apps/web/src/composables/ui/useCreateNode.ts` 的 `insertGroupPackFromUrl/importGroupPackFile/insertGroupPackData/createAssetNode`、`apps/web/src/components/areas/left-drawer/useAssetCanvasDrop.ts`、`packages/plugins/plugin-cloud-client/src/cloudResourceAdapter.ts` 的 `putResource/resolveResource`、`apps/web/src/__tests__/groupPack.test.ts`

## 现在 vs 期望

| | 现在 | 期望 |
| --- | --- | --- |
| 打包结构 | 只有 `nodes/edges`，节点 data 原样抄一份 | 额外带 `media`：每个资源一份字节加元信息，节点里只留包内占位引用 |
| 收藏时 | `buildGroupPack` 直接复制 `resourceId` 和 `imageUrl` | 先按 36 的 adopt 规则把资源收进当前画布，再把字节写进包 |
| 拖回画布 | `hydrateGroupPackMedia` 用原 ID 在本机解析，解析不到就保留旧地址 | 从包里取字节，上传到当前画布，拿新 ID 再建节点 |
| 跨画布 | 组里仍指向原画布的资源 | 组里所有资源都属于新画布 |
| 文件大小 | 只有 JSON，几十 KB | 图片、视频、音频一起进包，体积随内容增长 |

## 问题原因

- 状态：已确认
- 复现步骤：一，在画布 B 里选中一组带图片的节点，右键「收藏到资产库」；二，切到画布 A，从资产库把这一组拖进画布；三，看图片请求地址或保存后的 `canvas.json`。
- 证据（日志 / 截图 / 调用路径）：`buildGroupPack` 只做 `{ ...n.data }`，资源引用原样进入包；`GroupPack` 没有资源表，`parseGroupPack` 也只认 `nodes/edges`；`insertGroupPackData` 调 `hydrateGroupPackMedia`，它只做“按原 ID 解析地址”，不会复制字节；结果是解析失败就保留原 URL，解析成功也只是把原画布的地址写进 `imageUrl`。
- 根因：节点组包被当成了纯节点 JSON，没有把资源当成包的一部分。

## 修改方案

- 改哪里：`groupPack` 的格式与读写、收藏入口、导入入口、测试。
- 怎么改：一，包格式升到 version 2，新增 `media: { id, kind, name?, mime?, bytesBase64 }[]`；节点 data 里的 `resourceId` 换成包内引用 `pack:<mediaId>`，同时删掉 `imageUrl/videoUrl/audioUrl/posterUrl` 等显示字段，其它资源引用字段（`frameResourceId`、`leftResourceId`、`rightResourceId`）同样换成 `pack:<mediaId>`。二，收藏时先按 36 的 adopt 把每个引用收进当前画布，再取字节写进 `media`；取不到字节就提示“这一组有 N 个资源没能打包”，不静默生成坏包。三，导入时先解包，把 `media` 里的字节逐个 `resources.put()` 到当前画布，建立 `pack:<id>` 到新 `resourceId` 的映射，再交 `planGroupPlacement`。四，导入后只写 `resourceId`，由组件按 ID 现取，不写显示地址。五，某个资源入库失败时，这个节点建出来是空态并汇总提示，不保留 `pack:` 前缀，也不写原画布地址。六，version 1 旧包没有 `media`，按现有逻辑导入后立刻走一次 36 的修复流程。七，打包总字节设上限（建议 200MB），超了先提示再决定是否继续。
- 为什么这样改：包必须能独立搬走，才符合“画布就是文件夹、节点组是收藏品”的语义；导入时重新入库，才能保证每个画布只引用自己的资源。
- 风险 / 影响面：资产库上传接口要接受更大的文件；下载与收藏变慢；旧包需要迁移；右键菜单与拖拽入口必须共用同一套导入实现。
- 验证方式：单测覆盖包里有 `media`、节点不再带 URL、导入后 ID 指向新画布、缺资源时有提示；真实浏览器里 B 画布收藏、A 画布拖入、刷新，再检查 `canvas.json`；旧版包导入也要验证。

## 验收标准

- [x] 收藏节点组后，包内 `media` 包含组里所有图片、视频、音频的字节
- [x] 包内节点 data 不含 `http(s)://`、别画布 ID、别画布 URL
- [x] 在画布 A 导入后，节点引用的都是 A 的资源
- [x] 导入后刷新、切走再切回，组里媒体都正常
- [x] 旧版 `.plumegroup` 仍能导入，并被修复成本画布资源
- [x] 资源缺失时给出明确提示，不产生指向别处的静默坏数据

## 不能动

- 不改节点组的交互语义：拖出来仍是一整组（组加子节点加内部连线）
- 不改子节点相对坐标、组名去重、父节点排序这些已有行为
- 不改 `.plumegroup` 后缀与资产分类 `node-group`
- 不把资源写进节点 data（禁止 base64 进节点）

## 假设与待确认

- 已确认：包内资源用 base64 存进同一个 JSON，换取“单文件、拖一次就好”的体验。
- 已确认：资源缺失时**允许收藏**，但把那几个节点的引用摘掉，并明确提示缺了几个；不生成指向别处的坏数据。
- 已确认：本轮包体积上限**暂不设硬性拦截**（先让功能可用）；大视频改 ZIP 包格式留到后续单独做。

## 执行指令

先把 `GroupPack` 升到 version 2 并加 `media`，再改收藏与导入两条入口，最后补单测和真实画布验证。导入必须重新 `put()` 到当前画布，不允许把原 ID 直接带过去。
