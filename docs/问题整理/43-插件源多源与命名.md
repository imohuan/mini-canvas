## 你的原话

> 这个中转地，相当于是我应该从哪个接口去提取信息。比如，当前我本地的这些插件，都是从 catalog.json 里面获取到的，对吗？那它的名称就不应该叫"本地"，标题也不应该叫"中转后台地址"，应该叫做"插件源"。而且，可以配置多个插件源，并给插件源配置名称。
> 配置了多个插件源之后，下面的 table 标签就需要添加指定的 table 名称。这样当我切换到对应的 table 时，它才会去请求对应的插件源后台，从而获取对应的插件。
> 这个才是正常应该有的逻辑，你觉得呢

## 要解决的问题

插件管理页的"插件源"目前是**单个**中转地址（高级折叠项，名字叫"中转后台地址（高级）"），
语义混乱：

1. "本地"页签的内容其实来自**当前插件源清单**，名字与来源对不上；
2. 只能配一个源，不能同时接多个插件仓库；
3. 页签（市场/已装/本地）不区分来源，用户看不出每页数据是谁提供的。

期望：插件源是**可命名、可多个**的清单地址列表；页签按"源"组织，切到哪个页签就请求哪个源。

## 现在 vs 期望

| | 现在 | 期望 |
| --- | --- | --- |
| 源数量 | 1 个（catalogUrl，会话内存，不持久化） | 多个，带名称，可增删 |
| 源语义 | "中转后台地址（高级）"，同源默认 /plugin-catalog.json | 每个源 = 一个插件体系（清单 + 安装/更新接口同源） |
| 页签 | 市场/已装/本地，数据只来自当前单一源 | 每个启用的源一个页签（显示源名称），页签数据来自对应源 |
| 源切换 | 手填地址 → 应用并刷新 | 点页签即请求对应源；源管理在"插件源"面板里做 |
| 本地页签 | 混入当前源清单里非 NPM 记录的行，名字有歧义 | 每个源内同样按"市场/已装/本地"三段展示 |

## 问题原因

- 状态：已排查（代码证据充分）
- 复现步骤：打开插件页 → 展开"插件源" → 看到"中转后台地址（高级）"单输入框；
  "本地"页签内容来自当前源清单中"不在 NPM 安装记录"的行。
- 证据：usePluginManagerPage.ts TabId 只有 market/installed/local；TABS 数组固定三项；
  service 所有 npm 操作都基于 state.catalogUrl 推 origin（单值）。
- 根因：最初设计只支持"当前后台 = 插件清单来源"这一层，没有多源抽象；
  "本地"页签的命名是后来补 dev 清单展示时起的，与来源语义冲突。

## 修改方案

- 改哪里：
  1. `pluginManagerService.ts`：新增 sources 状态（数组：{ name, url, enabled }），
     持久化到现有 kv 设置（沿用服务端 /api/kv/config/plugin-sources 或设置存储现通道，
     实施时确认现有 catalogUrl 的持久化通道，保持同一通道）。
     `state.catalogUrl` 改为"当前激活源"的派生值；baseOfCatalogUrl 不变。
  2. `usePluginManagerPage.ts`：市场/已装/本地三段的数据按"当前激活源"拉取并缓存
     （缓存 key 加源 url 后缀，避免不同源串缓存）；页签改为两级：
     顶部一级 = 源（每个源一个页签，显示源名称），源内二级 = 市场/已装/本地。
  3. `PluginManagerToolbar.vue`：改名"插件源"，从单输入框改为源列表管理
     （每行：名称 + 地址 + 启用开关 + 删除；新增一行按钮）。默认源 = 同源
     /plugin-catalog.json，名为"本机"。
  4. `PluginManagerTabs.vue`：一级页签渲染源列表（enabled 的源），选中源后
     渲染该源下的市场/已装/本地二级页签与卡片。
- 怎么改：先 service 层（状态与持久化）→ 页面层（数据按源隔离）→ UI 层（两级页签 + 源管理）。
- 为什么这样改：安装/更新/卸载接口都在"源"的同源下，多源天然要按源隔离请求与数据；
  命名统一为"插件源"消除"本地/中转"歧义。
- 风险 / 影响面：
  - 不同源的 NPM 安装接口前缀白名单可能不同，装错源的包会被服务端拒（现有校验兜底，可接受）；
  - 已装页签如果展示"全部源的并集"，卸载/更新要带上源 origin —— 实施时确认：
    **已装页签按"安装记录"展示（安装记录已带来源事实）**，还是按当前激活源过滤，二选一；
  - 缓存 key 变更后旧缓存作废（一次性，可接受）。
- 验证方式：pnpm -C packages/plugins/plugin-manager typecheck + test；
  Chrome 实测：默认源下三段页签与现状一致；添加第二个源（指向另一端口 dev 服务）
  后出现新页签，切页签请求对应源（看 network），卸载/更新在对应源上执行。

## 验收标准

- [ ] "插件源"面板可添加/删除/启用多个源，每个源有名称与地址，重启后仍在（持久化）
- [ ] 一级页签 = 启用的源（显示源名称），切换页签后网络请求打到对应源
- [ ] 每个源内保留 市场/已装/本地 三段，本地段命名与语义一致
- [ ] 安装/更新/卸载操作作用于卡片所属的源
- [ ] 默认（只有"本机"一个源）时 UI 与现行为等价

## 假设与待确认

- 假设：多源的安装接口仍在各源的 `/api/npm-plugins/*`（同源代理），不存在跨源安装。
- 已知限制（实测 2026-11-24）：跨源请求受 CORS 限制——目标服务必须用
  `--trusted-origin <本页地址>` 启动，否则该源的市场/已装会加载失败
  （页签显示 0 或加载中，错误进控制台）。本机源不受影响。
- 待确认：
  1. "已装"页签是**全源并集**（每张卡标注来源）还是**跟随当前选中源**？
     建议前者（真实状态一目了然），卡片操作带源 origin。
  2. 源的持久化通道：写入哪个设置 key（实施时按现有设置存储确定）。
  3. 源数量上限是否需要（建议 ≥3 即可，不设硬上限）。
