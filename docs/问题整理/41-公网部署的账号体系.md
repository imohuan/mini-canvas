## 你的原话

> 这个登录密码的问题，我认为不应该还需要让我去容器内部输入对应的密钥。
> 你看看有没有其他方法，因为发布到网络上，这里应该有一个账户的逻辑，
> 然后每一个账户他们的配置地址都应该不同（插件安装的这些也会不同），
> 所有资源保存到的地址也应该不同。如果要保留其安全性应该如何做？

## 要解决的问题

分两层，一层是**当下就能改的部署体验**，一层是**产品方向的账号体系**：

1. 部署体验：把 plume-canvas 发布到公网（Railway / VPS 等）后，首次设置密码
   还要装 CLI、配 SSH、进容器敲命令——部署门槛太高。
2. 账号体系：公网部署后只有一个全局密码，所有人共享同一份数据、同一批插件、
   同一个平台配置。期望是**每个账户有自己的数据目录、自己的插件、自己的平台配置**。

## 范围与位置

- 页面：登录面板（cloud-client）、部署文档（apps/docs/cloud-server/deploy-railway.md）
- 参考代码：

## 现在 vs 期望

| | 现在 | 期望 |
| --- | --- | --- |
| 首次设置密码 | 必须进容器调 127.0.0.1 接口 | 部署平台环境变量预置 / 面板引导，不进容器 |
| 账户数 | 全局一个密码，所有人共享 | 每个账户独立登录 |
| 数据隔离 | 所有数据都在一个 dataDir | 每个账户一个数据目录（画布/资源/KV/历史） |
| 插件隔离 | 全局插件目录，装了大家都有 | 每个账户装自己的插件 |
| 平台配置 | 全局 providers，共用 API key | 每个账户自己的平台配置 |

## 问题原因

- 状态：已确认
- 根因：
  1. setup 限本机是正确的安全设计，但部署侧没有配对的初始化通道。
     POST /api/auth/setup 要求回环 + Host 回环 + 无转发头三重判定
     （apps/server/src/static.ts:493 isLoopbackRequest），挡住的是
     「公网任何人抢先设密码」；但容器部署场景下「部署者」恰恰不在容器里，
     两条需求没打通。
  2. 整个服务是单租户架构：createCloudServer 只有一个 dataDir，
     各 store（KvStore / CanvasStore / AssetStore / ProjectStore…）都以它为根，
     插件两层目录（全局 + 随包）也不分用户。多账户不是加个登录就能支持，
     需要数据根按账户分片。

## 修改方案

### 方案 A · 先解决部署体验（改动小，立刻可做）

目标：部署者**不进容器**完成首次密码设置。三条通道，可同时提供：

**A1. 环境变量预置初始密码（推荐，最先做）**

新增环境变量 PLUME_INITIAL_PASSWORD。启动时若 auth.json 不存在且该变量有值，
直接用它完成 setup（等价容器内调用了一次 setup），并在启动日志提示
「初始密码已从环境变量设置，请登录后尽快修改」。

- 改哪里：apps/server/src/cli.ts main() 在 runBootstrap 之后、createCloudServer
  之前，加一段条件 setup；
- 为什么安全：环境变量只有能看到部署平台控制台的人（即部署者本人）能设，
  和「进容器」是同等的信任级别；公网请求者碰不到它；
- Railway 上就是服务 → Variables → 加 PLUME_INITIAL_PASSWORD=xxx，重启生效；
- 风险：变量留在平台日志/变量页里。文档写明「首次登录后立刻改密码」即可，
  改密码已有 POST /api/auth/change 接口。

**A2. 一次性设置令牌（setup token）**

新增环境变量 PLUME_SETUP_TOKEN（随机 64 位 hex，部署者生成）。启动时若未配置过
密码，服务把它注入托管页（复用现有 admin-token 注入机制，同样的三重回环判定换成
「持此令牌者视为部署者」）。登录面板在 configured=false 时改为「输入部署令牌 →
设置你的密码」两步。设置成功后 setup token 立即作废。

- 为什么安全：令牌只发一次、设置成功即作废；比固定初始密码多一层「密码永不出现在
  环境变量」；
- 代价：比 A1 多一步交互，且注入机制要改（现在只在回环注入）。

**A3. 平台控制台授权（远期，依赖平台）**

类似 Railway CLI 的 railway login 设备码流程：服务启动时打印一个一次性短码，
部署者在平台控制台（或 CLI）确认后，服务收到平台签发的「本次部署者身份」，
放行一次 setup。工程量大，等 A1/A2 不够用再做。

### 方案 B · 多账户体系（大改动，需先立项设计）

目标：每个账户独立的数据、插件、平台配置。核心思路是**数据根按账户分片**：

```
<dataDir>/
  accounts/
    <account-id>/
      canvases/ · kv/ · plugins/ · providers/ · ui-cache/ ...
```

分四步走：

**B1. 账户模型与会话**

- auth.json 升级为账户表：accounts.json（每个账户 id、密码哈希、盐、创建时间）；
- 登录接口发会话时带 accountId；会话 cookie 绑定账户；
- 第一个注册的账户默认是管理员（可邀请/禁用其它账户，后续再做）。

**B2. 数据层按账户分片**

- 各 store 构造函数从「固定 dataDir」改为「resolveDir(accountId)」——每个 store
  在请求上下文里取当前账户，拼出 accounts/<id>/... 路径；
- 插件目录同理：全局只读层（随包 assets）保留，**可写层**改为
  accounts/<id>/plugins；pluginRoots 解析时按账户返回不同可写层；
- providers / providers-config 同理按账户分。

**B3. 请求上下文贯通**

- 所有路由处理函数要从会话里拿到 accountId。实现上给 Hono 加一层中间件：
  会话验证通过后把 accountId 塞进 c.var，store 经 ctx 传入的 getter 读它；
- MCP 接口同理会话绑定账户；
- Agent 后台任务、jobs 定时器要带账户身份跑（job 属于哪个账户，产物落到哪个账户目录）。

**B4. 迁移与兼容**

- 单租户升级多租户：现有 <dataDir> 下的数据迁为默认账户（admin）目录，登录后
  行为与现在一致；
- PLUME_INITIAL_PASSWORD（方案 A1）对应默认账户的初始密码；
- 插件市场 / 安装接口按账户写入自己的 plugins 目录；
- 平台 API key 全部账户私有，互不可见（现状就是全局文件，迁进账户目录）。

**B 的安全边界（保留现有防线）**

- 来源边界（Host / Origin 白名单）不变——它是防「恶意网页跨源打接口」的，与账户无关；
- 登录密码哈希加盐存盘、HttpOnly 会话 cookie、登录限速，全部沿用现有实现；
- setup 限本机的设计保留，但配合 A1/A2 后「部署者初始化」不再需要进容器；
- 资源读取不带令牌的硬规则不变（img/video/audio 的 src 用不了自定义头），
  但要**按账户校验资源归属**：读资源时校验该资源路径在当前登录账户目录内，
  防止登录用户 A 用路径穿越读账户 B 的资源。这是 B 引入的新攻击面，必须做；
- 审计日志按账户记 actor，audit-verify 链不变。

### 不建议的路线（为什么）

| 路线 | 为什么不 |
| --- | --- |
| 关掉 setup 的本机限制，公网直接设密码 | setup 存在的意义就是防抢注。公网部署的窗口期内，任何扫到域名的人都能把密码设成自己的，部署者反而进不去 |
| 首次访问不设密码直接进 | 等于部署即裸奔，写接口（装插件/跑脚本/改画布）全暴露 |
| 直接给每个请求加 ?account= 参数 | 账户身份必须跟会话绑定，URL 参数可以被伪造/篡改/分享 |

## 为什么这样改

- A1 用部署平台的信任级别（控制台权限）替代容器的物理边界，安全等价、体验大幅简化；
- B 沿用「一个进程、多数据根」而不是「每账户一个进程」：内存与部署成本可控，
  且现有内核/store 改造集中在路径解析一层；
- 账户隔离落在**文件系统层**而不是数据库行级：现有全部存储都是文件布局
  （canvases/<id>/canvas.json 等），分目录即隔离，迁移与备份（整目录打包）都简单。

## 风险 / 影响面

| 项 | 影响 |
| --- | --- |
| A1 | 极小：只加启动时的条件 setup；不影响现有 auth.json 行为 |
| A2 | 中：动 static.ts 的注入机制，现有注入测试要跟着改 |
| B1-B4 | 大：动全部 store 构造与请求上下文，后台插件 API 面不变但行为按账户分 |
| B 的资源穿越 | 新增攻击面：账户 A 可能构造路径读 B 的资源；必须做归属校验 |
| jobs / Agent 任务 | 定时器与任务原本全局，分账户后要重新设计归属与并发 |
| MCP | 第三方 AI 客户端按会话绑定账户，连接配置要带账户凭据 |

## 验收标准

方案 A（A1 先做）：

- [ ] Railway 上加 PLUME_INITIAL_PASSWORD 变量重启，不进容器，打开网站用该密码直接登录成功
- [ ] 已配置过密码时该变量被忽略（不覆盖现有密码）
- [ ] 登录后改密码，旧初始密码失效
- [ ] 未设该变量时行为与现在完全一致（本机首次打开仍是面板设置）

方案 B（立项后另定验收清单，先给方向性的）：

- [ ] 两个账户分别登录，画布 / 资产 / 历史互不可见
- [ ] 账户 A 装的插件不出现在账户 B 的插件目录
- [ ] 平台配置（API key）按账户隔离
- [ ] 资源读取做了归属校验（账户 A 无法用路径读账户 B 的资源文件）
- [ ] 单租户老数据升级后全部归入默认账户，行为不变

## 不能动

- setup 的本机三重判定保留（isLoopbackRequest 不放宽）——它是防抢注的根；
- 资源读取不带令牌的硬规则保留（img/video/audio src 用不了自定义头）；
- 会话 cookie 的 HttpOnly、登录限速、密码哈希加盐存储不降级；
- 审计日志链结构不变（只加 actor 字段）；
- 不引入数据库（现有文件存储布局不变，B 也只是分目录）。

## 假设与待确认

- 假设：公网部署是「一个部署者 + 若干使用者」，不需要每人自建部署
  （那等价 SaaS 化，成本完全不同）；
- 待确认：B 的账户注册谁说了算——管理员邀请制还是开放注册（涉及滥用/费用归属）；
- 待确认：B 是否要做「共享画布」（跨账户协作）——做了会推翻纯目录隔离；
- 待确认：先做 A1 还是 A+A2 一起；B 是否立项排期。
