## 要解决的问题

插件应该能在「项目页」这类与画布无关的页面里提供自己的面板，不需要先打开一张画布，也不需要在项目页背后偷偷启动一整套画布运行时。

最终要达到的效果：

1. 直接刷新 `#/`（项目页）时，应用级插件就能拿到上下文并注册面板。
2. 项目页能显示这些面板，插件也能按统一方式从组件目录取按钮等通用件。
3. 只有进入 `#/canvas/:id` 时才启动画布宿主、恢复画布数据、连接当前画布。
4. 现有画布插件、节点、主题、保存、云端同步的行为不变。

## 问题原因

### 独立审计确认的现状（2026-11-04）

子代理用 codegraph 检查索引（2603 个文件，状态正常）后确认：

1. **根组件确实没有 Provider。** 真实挂载链是 `main.ts:76` → `Root.vue:19`（`RouterView`）→ `router.ts:19`（画布路由挂 `App.vue`）→ `App.vue:150`（`CanvasProvider`）→ `CanvasShell`。Provider 是 `RouterView` 的**子级**，不是父级。项目页 `ProjectsPage` 与 `App.vue` 平级，自然拿不到 Provider。
2. **`index.ts` 与 `main.ts` 不是重复入口，但命名容易误解。**
   - `index.ts` 是**库入口**：导出 `CanvasApp`、`APP_PLUGINS`、`resolveAppPlugins`、`mountCanvasApp()`；`package.json` 的 `main/types/exports` 都指向它。
   - `main.ts` 是**应用启动入口**：挂共享全局、共享 KV、插件重装器，最后 `createApp(Root).use(router).mount('#app')`；`index.html:28` 加载它，Vite 构建也以它为准。
   - 结论：两套用途都成立，但名字 `index.ts` / `main.ts` 没有表达“库入口 / 应用入口”的区别。建议改名为 `app/entry.ts`（应用启动）与 `public.ts`（库导出），或至少在文件头第一行写清用途。
3. **插件注册不是两套清单，而是三层叠加。**
   - 静态冷启动：`packages/ui/src/assembly.ts:84-105` 的 `APP_PLUGINS`（20 项），`:142-153` 按 `cloud-server` 托管追加 `cloudClientPlugin`。
   - 运行期外部安装：`plugin-manager` 从 `/plugin-catalog.json` 拉清单，安装 UMD/ESM 插件；安装意图存 `plugin-manager:installed`。
   - 热重载：`pluginReload.ts` 暴露 `window.MiniCanvasPlugin`，读同一份 catalog；`hotReloadPlugin` 在冷启动清单里。
   - 重复点：builtin 身份同时写在各插件 `package.json` 与 `APP_PLUGINS`；catalog URL 在 `pluginReload.ts:170` 与 `pluginManagerService.ts:174` 各写一次；清单类型前后端各声明一份。`hot-reload` 的元数据（非 builtin、非 installable）与冷启动清单不一致。
4. **目录确实混杂。** `packages/ui/src` 顶层有 15 个文件，`App.vue`、`Root.vue`、`main.ts`、`router.ts`、`assembly.ts`、`assetUploadPlugin.ts`、`pluginReload.ts`、`sharedGlobals.ts` 全堆在根；`components/hooks` 与 `composables` 职责重叠；`src/assets` 与 `src/components/assets` 同名不同义；`ProjectsPage.vue` 是路由页却放在 `components`；`AssetTree.vue`、`AssetManageDialog.vue` 是转发壳。
5. **没有两个内核。** `canvas-data` 的 `Context` 只是继承 kernel 的 `Context`。真正的两层是 `CanvasProvider`（外壳用的 `CanvasContext`）与 `CanvasSurface`（画布子树用的 `CanvasRenderContext`），职责不同。但 `useCanvasContextOrRender()` 会造 `api/manager` 为 `undefined` 的假上下文（`packages/canvas-render/src/contracts/canvasContext.ts:68-81`），这是实际容易踩的坑。
6. **`readyHost` 是模块级单例，卸载时没有清。** `App.vue:71` 写入，`App.vue:128-146` 卸载时没有清空；`CanvasProvider` 已经 `stop()` 后，树外组件仍会读到旧 ctx。

- 状态：已确认。
- 复现步骤：直接访问 `#/`，停在项目列表页；在项目页组件里调用 `useCanvasContext()`，或在插件里注册项目页面板并渲染 `<SlotHost>`；组件拿不到注入，抛「缺少画布上下文」，项目页也没有可渲染的插件面板槽。
- 证据（调用路径）：`Root.vue` 只渲染 `RouterView`，没有 `provide`；`router.ts` 把 `ProjectsPage` 放在 `/`、`CanvasApp` 放在 `/canvas/:id`，两者平级；`CanvasProvider` 写在 `App.vue` 里，它提供的 `CANVAS_CONTEXT_KEY` 只覆盖画布工作台子树；`SlotHost` 与抽屉页签都通过 `useCanvasContext()` 取 `ctx`，没有应用级兜底；项目页只能用 `useUiComponentOutside('Button')`，这是按名取静态组件的旁路，不是可扩展的插件上下文。
- 根因：当前只有一个上下文，而且它同时承担了两件不同生命周期的事：
  1. **应用级能力**：插件装载、UI 组件目录、通知、设置、页面插槽。这些与画布无关，应在整个应用生命周期内存在。
  2. **画布级能力**：`doc`、`selection`、`view`、节点渲染、视口、画布保存与云端同步。这些只在打开某张画布时存在。

  现在这两层被 `CanvasProvider` 合成了一层，并且 Provider 只挂在画布路由里，所以「插件」和「画布」被错误地绑定在一起。

  另外，「把 `CanvasProvider` 直接提到 `Root.vue`」并不能只解决上下文问题：`CanvasProvider` 会调用 `createMiniCanvasHost`，而它会冷启动全部业务插件、恢复 graph、恢复配置并连接云端（`createMiniCanvasHost.ts:227`、`:280`）。`plugin-cloud-client` 在 `apply` 时读取当前 URL 得到画布 id（`packages/plugins/plugin-cloud-client/src/plugin.ts` 的 `const CID = canvasId()`），在项目页会落到 `default`，造成项目页也在读写一张画布。

  依赖机制本身没有问题：`inject` 缺服务时插件停在 `PENDING`，提供方卸载会让依赖方回退 `PENDING`，服务恢复后自动重载（`packages/kernel/src/context.ts` 的 `retractUnsatisfiedActives`，测试见 `packages/kernel/src/__tests__/serviceRegistration.test.ts:70`）。问题在于**画布服务只有画布层有**，所以声明这些依赖的插件在项目页永远等不到服务。

## 修改方案

- 改哪里：`packages/canvas-render/src/host/`（根级 Provider + 画布服务挂载/卸载）、`packages/canvas-render/src/contracts/`（统一 `CanvasContext`）、`packages/vue-render/src/SlotHost.vue`（统一从根 `ctx` 取件；`canvas-render` 转发同名导出）、`packages/ui/src/Root.vue`（根级 Provider 包住 `RouterView`）、`packages/ui/src/App.vue`（改为进入画布时挂载画布服务，不再自己建第二个 Context）、`packages/ui/src/assembly.ts`（插件只登记一次，按 `inject` 决定启动时机）、`packages/ui/src/components/ProjectsPage.vue`（面板区域）、`packages/ui/src/composables/ui/hostRuntime.ts`（树外取件直接读根 Context）、`packages/plugins/plugin-theme-default/src/index.ts`（拆成通用组件插件 + 画布外观插件）、`packages/plugins/plugin-cloud-client/src/plugin.ts`（连接常驻 + `onCanvasReady` 挂同步）、`packages/plugins/plugin-style-library/src/components/StyleLibraryOverlay.vue`（缺画布能力时禁用按钮）。
- 怎么改：**一个 Provider、一个 Context**，画布只是一组在进入画布时才 install、离开画布时 uninstall 的服务。
  1. **根级 Provider**：在 `Root.vue` 里包住 `RouterView`，创建唯一的 `Context`，装上 `themeRegistry` 空容器与应用级存储。全部插件只 `ctx.plugin(...)` 登记一次：不依赖 `doc` 的 `apply` 立刻执行，声明了 `doc/selection/view` 的先停在 `PENDING`。
  2. **画布路由**：`App.vue` 在 `onMounted` 里 `await mountCanvas()`；`onBeforeUnmount` 里先 `await flushPendingSave()`，再 `await unmountCanvas()`。`mountCanvas` 通过 `ctx.installPlugin(canvasDataPlugin)` 动态装上 `canvas-data`；这个插件**不是 core、也不进静态注册表**，每次进画布都是新安装的单元。它的 `apply` 只注入画布专属服务：`doc`/`selection`/`view`/`canvas`/`nodeToolbar`，并恢复当前画布的 graph。`save`/`resources` 由根级应用底座 `canvas-base` 在应用启动时提供，`canvas-data` 不重复注入（内核会对重复服务名抛错）。离开画布时调用 `ctx.uninstallPlugin('canvas-data')`；因为它是普通插件，内核会触发 `retractUnsatisfiedActives`，声明了这些依赖的插件自动回退 `PENDING`，它们注册的节点类型、插槽、主题槽同时回收。
  3. **上下文只有一个**：`Root.vue` provide 的就是全部组件读的那一份；`App.vue` 不再新建 `Context`，也不再 provide 第二个令牌。`useRenderContext()` 返回 `{ ctx, canvas }`：`ctx` 恒在，`canvas` 是一个 `shallowRef<CanvasHostHandle | undefined>`，项目页为 `undefined`，进画布后由 `mountCanvas` 写入。`host`/`api`/`manager` 保留 getter：在画布内返回对应值，项目页访问会抛清晰错误。`useCanvasRender()` 仍只给画布渲染子树用。**`AppProvider` 在 `ctx.start()` 完成前只渲染 loading，不要先渲染 `RouterView`**，否则子组件的 `installPlugin` 会撞上 `assertState('started')` 抛错。
   4. **组件取件**：`SlotHost`、`useUiComponent`、设置面板都从根 `ctx` 取，不再区分“应用层/画布层”。`useUiComponentOutside` 改成读根 `ctx` 的 `ui` 目录，静态目录仍作为首帧兜底。设置面板外壳（`SettingsHost`/`SettingsShell`）归 `ui-shell`；通用主题变量归 `ui-components`；画布专用变量留在默认主题里。`vue-render` 只管 Provider、上下文、插槽、按名取组件。

   `canvas-render` 是 `ui-shell` 的**自带插件**，`ui-shell` 直接 import 它提供的 `CanvasHost` 等组件来渲染画布页。这条不违反“插件之间零引用”：`canvas-render` 是入口自带件，`ui-shell` 是入口，不是业务插件。业务插件之间仍然零引用。

  7. **通知宿主**：`Toaster` 挂在根级 Provider 下，项目页与画布页共用同一个。
  8. **云端插件**：保持一个身份 `cloud-client`，`inject` 改为 `[]`；`apply` 里只注册连接与历史查询。画布同步由可选导出 `onCanvasReady(ctx)` 负责，`mountCanvas` 装完服务后调用它。因为现在只有一个 Context，进入画布时 `doc` 是后装的，插件收不到“服务注入”事件，不能在 `apply` 里等它出现。

     - `theme-components`：只注册 `Button`/`DropdownMenu`/`Toaster`/`SettingsRow` 等通用 UI 目录与 `notify` 服务，根级常驻；
     - `theme-canvas`：只注册 `nodeShell`/`edge`/`background`/`connectionLine`/`settingsPanel` 等画布外观，声明 `inject: ['doc']`，进画布才启动。

### 服务与插件的真实关系

### `canvas-render` 为什么不是插件

事实核对：`canvas-render` **完全不是插件**，它只提供组件和工厂函数。

| 名字 | 是什么 | 证据 |
| --- | --- | --- |
| `canvas-render` 包 | 渲染层库：`CanvasHost`/`CanvasProvider`/`CanvasSurface`、`SlotHost`、`createMiniCanvasHost` 等 | `packages/canvas-render/src/index.ts` 全是 `export`，没有 `name`/`apply`/`inject` |
| `canvas-base` | **才是插件**（`name: 'canvas-base'`、`core: true`），负责注入 `save`/`doc`/`resources`/`selection` | `packages/canvas-data/src/canvas/canvasBasePlugin.ts:209-220` |
| `CanvasProvider` | Vue 组件，负责调用 `createMiniCanvasHost` 并 provide 上下文 | `packages/canvas-render/src/host/CanvasProvider.vue:61` |
| `CanvasHost` | Vue 组件，负责把 store 画成 VueFlow，不启动内核 | `packages/canvas-render/src/host/CanvasHost.vue:9` |

所以“`canvas-render` 不是插件”是设计如此：它是**画布功能的实现层**，插件要靠它提供的组件和上下文来渲染。如果把它也做成插件，插件之间就会出现“谁先装谁后装”的新顺序问题，而它本身又不注册任何能力。

真正需要按插件身份管理的是画布会话（现在的 `canvas-data`）：应用底座 `canvas-base` 是常驻环境（`core: true`，不能热卸），“注入画布服务”这件事收在可装可卸的 `canvas-data` 插件里。

### 切换路由时“重新注册”到底是什么

你说的“切换路由时重新注册插件”是对的，但要说清哪一层在重注册：

| 切换 | 通用插件 | 画布插件 | 为什么 |
| --- | --- | --- | --- |
| 项目页 ↔ 画布页 | 不卸载、不重新 `apply` | 回退 `PENDING`，再进画布时重新 `apply` | 它们依赖 `doc`，画布服务没了就不能继续跑 |
| 画布 A ↔ 画布 B | 不卸载 | 卸载 A 的实例、重新安装 | 画布 id 变了，旧节点数据不能复用 |

内核的行为是：插件登记一次（`ctx.plugin`）后，启动/停止由依赖满足情况决定；`installPlugin` 在已启动的 Context 上是热装，`uninstallPlugin` 会回收副作用。因此“画布插件重新注册”应当理解为：

1. 离开画布时 `uninstallPlugin('canvas-data')` → 画布服务消失 → 依赖它的插件由 `retractUnsatisfiedActives` 回退 `PENDING`；
2. 进入画布时 `installPlugin('canvas-data')` → 服务重新出现 → 依赖满足，插件重新 `apply`。

这样通用插件只启动一次，画布插件每次进画布都会重新 `apply`，`ctx.effect` 登记的副作用会重新建立、离开时完整回收。

### 目标分层：`kernel → vue-render → canvas-render → ui-shell`

各层身份不同：`kernel` 与 `ui-shell` 是启动底座；`vue-render`、`ui-components`、`canvas-render` 都是插件，其中 `canvas-render`、`ui-components` 是 `ui-shell` 的**自带插件**。**死规则：业务插件之间零引用。** 业务插件不许 `import` 另一个业务插件；取件只能走上下文（`ctx.get` / `ctx.tryGet`）、注册场（`ctx.registryOf`）、插槽（`ctx.slots.register`）、按名取组件（`useUiComponent`）。入口自带件与纯类型契约包是例外。

| 层 | 是什么 | 管什么 | 不管什么 |
| --- | --- | --- | --- |
| `kernel` | 纯插件内核（零 Vue、零画布） | 装载、依赖、事件、作用域回收、注册场 | 不认识 Vue 组件，也不认识节点 |
| `vue-render` | **新增**：Vue 渲染底座 | `Provider`、上下文令牌、`SlotHost`/`SlotComposer`、App/Canvas 通用取件、安装句柄的 Vue 绑定 | 不认识节点、连线、视口 |
| `canvas-render` | 第一个具体渲染器 | `CanvasHost`/`CanvasSurface`、VueFlow、节点区域、视口、连线、裁剪 | 不负责页面装配 |
| `ui-shell` | 前端 UI 入口（不是插件） | 项目页、画布页、设置页、通知宿主、插件注册表；写 `Provider` + `vue-router`；直接使用自带插件 `canvas-render` 的组件 | 不实现画布渲染细节 |

以后加 `rect-render`，只需要实现 `vue-render` 的同一套接口（渲染器注册、上下文、槽），`ui-shell` 不需要知道是画布还是矩形。

**哪些从 `canvas-render` 抽到 `vue-render`：**

- `CanvasProvider` / `CanvasContext` / `useCanvasContext`：改成通用的 `RenderProvider` / `RenderContext` / `useRenderContext`；画布层只扩展 `host` 等字段。
- `SlotHost` / `SlotComposer` / `SlotAnchor`：它们只依赖 `ctx.slots`，与画布无关，应归 `vue-render`。
- `useCanvasContextOrRender`：合并成 `useRenderContext`，不再造 `api/manager = undefined` 的假上下文。
- `useUiComponent` / `useUiComponentOutside` / `setUiCatalogHost`：只依赖 `ctx.registryOf('ui')`，应归 `vue-render`。
- `SettingsHost` / `SettingsShell` / `settingsSource`：外壳与设置面板的通用绑定，归 `vue-render`；具体字段控件仍由主题插件提供。
- `LAYERS` / `ui-theme.css` 的通用 token：归 `vue-render`；画布节点专用的 `--canvas-node-*` 留在 `canvas-render`。

**哪些必须留在 `canvas-render`：**

- `CanvasHost` / `CanvasSurface` / `VueFlow` 桥接；
- `createMiniCanvasHost`（它认识 `doc`/`selection`/`view`）；
- 节点区域、端口、连线、视口、裁剪、可见剔除、吸附；
- `BaseNode` 等主题外观（这些在 `plugin-theme-default`，不在 render 包里）。

迁移方式：新建 `packages/vue-render`，先把上面“通用”这几件搬过去并从 `canvas-render` 重导出，保持现有 199 个 import 不破；等所有引用清理后再删重导出。这样是增量迁移，不需要一次性改完 37 个插件。

`rect-render` 的接入方式：新增一个包，提供和 `canvas-render` 同类的渲染组件（挂载根、渲染节点、提供几何/视口）。如果它作为 `ui-shell` 的自带件，入口直接引用对应组件；如果作为可装卸插件，入口通过插槽使用它注册的组件。

### 谁决定当前模式，谁触发装卸

**`ui-shell` 就是前端 UI 入口，不是可装卸插件。** 它由 `main.ts` 启动，是启动入口本身；内部写 `Provider` 与 `vue-router`，模式切换就发生在这里。

所以责任链确定为：

| 角色 | 是什么 | 做什么 |
| --- | --- | --- |
| `main.ts` | 点火 | 创建 Vue 应用，挂载 `ui-shell` |
| `ui-shell` | 前端 UI 入口 | 写 `Provider` + `vue-router`，提供外壳插槽与服务；按路由变化调用画布装卸 |
| `App.vue`（画布页组件） | 路由到画布页时挂载的那一页 | 调 `mountCanvas` / `unmountCanvas` |
| `vue-render` | 通用渲染底座 | 只提供插槽与上下文取件，不读路由、不认识画布 |
| `canvas-render` / `canvas-data` | 画布渲染器与会话插件 | 被装上时注入画布服务，被卸下时回收 |
| 通用插件 | 只关心自己的服务 | 一直运行；需要画布时用 `tryGet` 判断 |

`ui-shell` 在自身内部注册插槽、提供服务，插件通过 `ctx.slots.register(...)` / `ctx.get(...)` 使用即可。`ui-shell` 的启动顺序与普通 Vue 入口一样，不需要先“做成插件再装进什么”，它就是入口。

触发链：

```text
进入画布页
  → ui-shell 里的路由变化
  → 画布页组件挂载
  → mountCanvas()
      → installPlugin(canvasSession)   // 注入 doc/selection/view
      → 依赖 doc 的插件自动从 PENDING 激活
  → CanvasHost 渲染
```

```text
离开画布页
  → 先 await 落盘
  → unmountCanvas()
      → uninstallPlugin(canvasSession)
      → 依赖 doc 的插件回退 PENDING，注册的节点/插槽/主题槽回收
```

`App.vue` 的调用时机：`onMounted` 里 `await mountCanvas()`；`onBeforeUnmount` 里先 `await flushPendingSave()`，再 `await unmountCanvas()`。`unmountCanvas` 要幂等；快速切换画布时用 generation token 防止旧画布的异步恢复覆盖新画布。

所以“重新安装插件”不是所有插件重装，而是：**画布会话插件被卸下/装上，依赖它的插件跟着暂停/恢复。** 通用插件（主题组件、通知、云端连接）不在这条链上，始终可用。

### “注册组件”到底是哪两种注册

现有代码已经有两条注册通道，别混用：

| 通道 | 写法 | 谁消费 | 适合什么 |
| --- | --- | --- | --- |
| 插槽 | `ctx.slots.register('槽名', { component, order })` | `<SlotHost slot="槽名" />` | 一个区域里叠加多个插件 UI（按钮、徽章、面板） |
| 组件目录 | `ctx.registryOf('ui').add('名字', 组件)` | `useUiComponent('名字')` | 按名取“可整体换皮”的通用件（Button、Dialog、Toaster） |

所以 `ui-shell` 里做的是“**在页面里放插槽**”，插件做的是“**往插槽里注册组件**”：

```vue
<!-- ui-shell：只摆位置，不写死具体插件 UI -->
<SlotHost slot="app.projects.main" />
```

```ts
// 插件：注册自己的面板，卸载时自动摘掉
ctx.slots.register('app.projects.main', { component: MyPanel, order: 100 })
```

`ui-shell` 本身作为入口组件由 `main.ts` 挂载；它不能再被作为一个“插槽组件”注册进去，否则会循环。`App.vue`、`ProjectsPage.vue` 这类页面属于入口，也不注册成插槽组件；页面里的**区域**才是插槽。

注册组件的两个必要条件（代码已支持）：

1. 组件必须是 `markRaw` 过的组件句柄，避免被 Vue 深度代理；现有 `useUiComponent` / `SlotHost` 都已处理。
2. 组件渲染时拿到的 `ctx` 来自 `ui-shell` 提供的唯一上下文；插件不要自己再造 Provider。

方向可行。审计后的结论：

**各东西在新结构里的身份：**

| 现在的东西 | 做成插件后 | 层 |
| --- | --- | --- |
| 应用底座 `canvas-base`（常驻）→ 画布会话 `canvas-data`（可装卸） | 画布 |
| `theme-default` 的画布外观部分 | `theme-canvas` | 画布 |
| `theme-default` 的通用组件部分 | `theme-components` | 常驻 |
| `packages/ui`（即 `ui-shell`） | 前端 UI 入口：写 `Provider` + `vue-router`，内部注册插槽与服务 | 启动入口 |
| `cloud-server` 的前端连接 | `cloud-client`（当前已是插件） | 常驻 |
| `cloud-server` 的后端路由 | 已经是后端插件（`serverFramework`） | 后端 |

**死规则：业务插件之间零引用。**

不允许出现 `import ... from '@mini-canvas/plugin-xxx'`（运行时或类型都不行）。例外只有两类：`ui-shell` 的入口自带件（如 `canvas-render`、`ui-components`），以及纯类型契约包。业务插件要使用别人的能力，只能通过：

- `ctx.get(...)` / `ctx.tryGet(...)` 取服务；
- `ctx.registryOf(...)` 取注册场条目；
- `ctx.slots.register(...)` 注册插槽；
- 共享的纯类型契约包（例如 `canvas-contracts`），只放类型不放实现。

这条规则同时覆盖 `package.json` 的 `dependencies`：业务插件不得把另一个业务插件列为依赖，避免“装着没引用、一装就打包”。唯一例外是 `plugin-demo-kit` 这类开发示例，以及测试文件。

| 包 | 插件身份 | 对外只提供 |
| --- | --- | --- |
| `vue-render` | 注册 `RenderProvider` 上下文、插槽宿主、UI 目录读取入口 | 插槽令牌与服务名 |
| `canvas-render` | 注册画布渲染器与视口/布局服务 | 服务名与能力名 |
| `ui-components` | 注册 `Button`/`Dialog`/`Toaster` 与 `notify` | UI 目录名 |
| `ui-shell` | 前端 UI 入口，提供页面、外壳与应用插槽；插件往它注册即可用 | 页面/插槽名、服务名 |

按审核复核，生产源码里真实的跨插件引用只有 5 个文件（其余命中是测试、注释或 `package.json`）：

| 引用方 | 被引用方 | 性质 | 改法 |
| --- | --- | --- | --- |
| `plugin-theme-default`（`ensureShortcutManager.ts:16,20`、`SettingsShortcutPage.vue:14`） | `plugin-shortcut-manager` | 运行时 | 改成 `ctx.get('shortcut-manager')` + 插槽组件 |
| `plugin-theme-default`（`ensureShortcutManager.ts:21`） | `plugin-shortcut-manager` | 仅类型 | 类型移到共享契约包 |
| `plugin-node-text`（`nodeTextPlugin.ts:41`） | `plugin-bottom-bar` | 运行时 | 改成 `ctx.get('nodeBar')` |
| `plugin-node-video`（`nodeVideoPlugin.ts:36`） | `plugin-bottom-bar` | 运行时 | 改成 `ctx.get('nodeBar')` |
| `plugin-web2api-tools`（`web2apiPlugin.ts:29-30`） | `plugin-bottom-bar` | 仅类型 | 类型移到共享契约包 |

其余如 `plugin-theme-default → node-image/node-text` 只在注释里出现；`plugin-bottom-bar` / `multi-select` / `node-3d` 等对 `theme-default` 的 import 只在测试或 `package.json` 里。所以工程量比原表估的小，但要把“类型引用也算违规”与“`dependencies` 也要清理”分开验收，否则规则无法执行。

注意 `plugin-theme-default` 内部还会引用自己包的组件，那不是插件间引用，不受这条规则限制。

**真正不能做成插件的，只有两件：**

| 东西 | 原因 |
| --- | --- |
| `kernel` | 它就是插件机制本身；插件不能在插件里定义 |
| `main.ts` + `Root.vue`（= `ui-shell` 的入口） | Vue 必须先有根组件才能挂载；它们就是前端 UI 入口，不是可装卸插件 |

所以更准确的模型是：

```text
kernel   插件装载、依赖、回收
└─ vue-render   通用渲染底座：Provider、上下文、插槽宿主、按名取组件
   ├─ ui-components   基础组件插件：Button / Dialog / notify
   ├─ canvas-render   画布渲染器（依赖 canvas-data 与 canvas-base）
   ├─ react-render    以后可并行接入
   └─ ui-shell        前端 UI 入口：Provider + vue-router + 外壳；直接使用自带插件 canvas-render 的组件
```

`ui-shell` 与 `canvas-render` 都挂在 `vue-render` 下面。`canvas-render` 是 `ui-shell` 的自带插件，入口直接 import 它提供的 `CanvasHost` 等组件；这不属于“业务插件互相引用”。业务插件之间仍然零引用，只能走服务、注册场、插槽和纯类型契约包。

**跨层依赖的事实核对：**

| 依赖 | 是否存在 | 证据 |
| --- | --- | --- |
| `canvas-render` → `canvas-data` | **有，运行时依赖** | `createMiniCanvasHost.ts:18` import `Context`/`createCanvasBasePlugin`；`canvasHostCore.ts:10` 运行时调用 `isTransient`/`isNodeRunning`。`canvas-data` 是底座库，不是插件，不受“插件零引用”限制 |
| `canvas-render` → `canvas-base` | **没有** | `rg '@mini-canvas/canvas-base' packages/canvas-render/src` 无结果 |
| `canvas-render` → `@vue-flow/core` | 有 | `vueFlowBridge.ts`、`CanvasSurface.vue` 等 |
| `ui-shell` → `canvas-render` | **有，且保留** | `App.vue:11-13` import `CanvasHost`/`CanvasProvider`/`SlotHost`。`canvas-render` 是入口自带插件，入口可直接使用；不受“业务插件零引用”限制 |
| `ui-shell` → `canvas-data` | 有，主要是类型与服务契约 | `assembly.ts` 的 `CanvasNode`/`StorageAdapter`、`sharedGlobals.ts` |

所以 `canvas-data` 必须留在 `canvas-render` **下面**，不能塞进它里面当内部实现：`canvas-render` 的运行时逻辑真的在用 `canvas-data` 的 `Context`、`Graph`、`isTransient` 等。把它藏进 `canvas-render` 会造成“渲染器内部持有数据层”的循环感，也会让 `plugins/*` 无法直接 import 数据契约。

`ui-shell` 放在 `vue-render` 下、与 `canvas-render` 平级，符合你的意思：它依赖渲染底座，画布页直接使用自带插件 `canvas-render` 的组件。它不需要经过 `canvas-base`，也不把画布渲染细节写进入口。

`canvas-render` 现在只承担画布渲染；`vue-render` 才是那个“更原始的 render 底座”。`kernel` 提供插件机制，`vue-render` 提供 Vue 渲染与插槽，`canvas-render` 是接在它下面的渲染器插件。

`packages/ui` 不需要“变成插件”：它本身就是 `ui-shell`，作为前端 UI 入口被 `main.ts` 启动。插件往它注册插槽与服务，页面在入口里组装；这是入口的职责，不是可装卸单元的职责。

`cloud-server` 不建议做成前端插件：它是独立的后端进程，和前端插件容器共用 `kernel`，但生命周期不同。它已经通过 `/plugin-catalog.json` 和 `server.js` 与前端插件配对，继续保持这个关系即可。

`packages/ui/src/assembly.ts` 已经是静态清单的唯一住址，把它升级成带元数据的注册表：

```ts
  /** 为什么装它（给维护者看，测试也用它核对注释与实现一致） */
  reason: string

export const APP_PLUGIN_REGISTRY: readonly AppPluginEntry[] = [
  // { plugin: themeDefaultPlugin, kind: 'builtin', reason: '默认主题与通用 UI 目录' },
  // …

```

由它派生：

- `APP_PLUGINS`：`kind === 'builtin'` 的数组，保持现有导出名与顺序；
- `resolveAppPlugins()`：在 builtin 之后追加 `kind === 'env'` 且当前环境满足的插件（目前只有 `cloud-client`）；
- 一个测试：扫描 `packages/plugins/*/package.json`，断言所有 `miniCanvas.builtin === true` 的插件都出现在注册表里，`installable` 的不混入；这样“package.json 和 assembly.ts 两份身份”的漂移会被测试拦住。

必须保留动态装载的三条路：

1. cloud-server 托管的 `/plugin-catalog.json`；
2. `plugin-manager` 的 UMD/ESM 安装与 NPM 安装；
3. `hot-reload` 的运行时重装。

这三条依赖 URL、持久化安装意图和运行时 `host.manager`，不能塞回静态数组。把 `DEFAULT_CATALOG_URL` 收成唯一导出，消除 `pluginReload.ts` 与 `pluginManagerService.ts` 的双份定义。

先看 `Root.vue` 的现状和目标，避免把计划当成已实现（下面第二段是**计划目标**，仓库里还没改）：

```vue
<!-- 现状：Root.vue 没有 Provider，RouterView 直接是根 -->

  <RouterView :key="route.fullPath" />
  <component :is="Toaster" v-if="Toaster" />
</template>
```

```vue
<!-- 目标：唯一 Provider 包住 RouterView，Toaster 留在 Provider 内 -->
<template>
  <AppProvider>
    <RouterView :key="route.fullPath" />
    <component :is="Toaster" v-if="Toaster" />
  </AppProvider>
</template>
```

`AppProvider` 是 `ui-shell` 的一部分：它负责创建唯一的 `Context`、登记全部插件、绑定安装句柄；`RouterView` 里的项目页和画布页都读同一份上下文。画布页额外调用 `mountCanvas` 装上画布服务。

对应的改动点：`main.ts` 仍挂 `Root.vue`，不改入口；`Root.vue` 增加 `AppProvider` 包裹；`App.vue` 从“自己建 Provider”改为“读取根上下文 + 调 `mountCanvas`”。三者合起来就是 `ui-shell`。

只有一个 `Context`。服务表是**动态**的：画布服务在进入画布时出现，离开画布时消失。

| 服务 | 什么时候有 | 谁提供 |
| --- | --- | --- |
| `slots` / `settings` / `settingsMenu` / `tools` | 应用启动到关闭 | 内核能力层与内核自带 |
| `notify` | `theme-components` 装上后 | 通用组件插件 |
| `save` / `resources` | 应用启动（用于配置与资源）；画布内复用同一实例 | 根级 Provider |
| `doc` / `selection` / `view` / `canvas` / `nodeToolbar` | 只在画布路由内 | `mountCanvas` |
| `cloud-client` / `cloud-client:history` | 应用启动 | `cloud-client` 的连接部分 |

插件只登记一次，启动由 `inject` 决定：

| 插件类型 | `inject` | 项目页 | 画布页 |
| --- | --- | --- | --- |
| 通用插件（`theme-components`、`hot-reload`、`cloud-client`、`style-library`、`agent`） | `[]` | 启动 | 继续运行 |
| 画布插件（节点、交互、`theme-canvas`、`bottom-bar`、`history`、`auto-save`） | `['doc', …]` | 停在 `PENDING` | 随 `doc` 出现自动启动 |

所以不需要“应用层清单/画布层清单”两套安装身份，也不需要同一个插件跑两次。

### 通用插件如何区分“现在能不能用画布”

通用插件只有一个入口，但可以通过 `ctx.tryGet('doc')` 判断当前有没有画布；也可以用 `ctx.on('ctx:plugin-installed', …)` 之外的显式回调（见下）。

`style-library` 的做法：

- 数据、广场、收藏、搜索一直可用；
- “使用素材”需要 `media` 能力，用 `ctx.tryGet` / 能力场探测；拿不到时禁用按钮并提示“打开画布后可使用”；
- 进画布后按钮自动恢复，因为此时 `doc` 与 `media` 都在。

这里不需要 `useHostTier()` 这类新 API。判断标准只有一条：**需要的东西在不在**。

但有一个真实边界：通用插件在应用启动时 `apply` 完，之后 `doc` 才出现，内核不会通知它。因此涉及画布的部分要写成“每次使用时现取”，不要缓存 `doc` 或 `media`。如果确实需要在进入画布时做一次性初始化（如绑定画布事件），由 `mountCanvas` 在装完服务后调用插件暴露的 `onCanvasReady(ctx)`（可选导出）。这比新增内核事件更小、更明确。

### 云端插件：一个身份，包内两块

**决定：只保留一个可安装的插件身份 `cloud-client`。** 它对应用层与画布层都可用，安装列表里只有一条“云端连接”，不会因为分层多出两个插件。

`plugin-cloud-client` 仍然是这个身份所在的包。包内按职责拆成两块**内部模块**（名字只用于代码组织，不注册成插件、不写进清单）：

| 内部模块 | 职责 | 是否依赖画布 |
| --- | --- | --- |
| `connection` | 解析服务地址、提供共享 `CloudApi`/KV 通道、`cloud-client` 状态服务、`cloud-client:history` 查询、把 `config`/`shortcut` 适配器指向云端 | 否 |
| `canvas-sync` | 把 `canvas`/`resource` 适配器指向当前画布、恢复画布、实时合并、动作清单与下单、`cloud-client/edit-guard` | 是 |

插件入口仍然导出现在的 `cloudClientPlugin`，`inject` 改为 `[]`，在 `apply(ctx)` 里先只做连接；画布同步通过可选的 `onCanvasReady` 挂上：

```ts
export function apply(ctx: Context) {
  const connection = acquireSharedConnection(configFrom(ctx.tryGet('settings')))  // 全应用一份
  ctx.effect(() => () => connection.release())                                  // 引用计数

  registerConnectionService(ctx, connection)   // cloud-client 状态 + history 查询 + config/shortcut 适配器
}

/** 由 mountCanvas 在画布服务装好后调用；返回的句柄随画布卸载调用 dispose。 */
export function onCanvasReady(ctx: Context) {
  const doc = ctx.tryGet<HostDoc>('doc')
  if (!doc) return
  return registerCanvasSync(ctx, acquireSharedConnection(configFrom(ctx.tryGet('settings'))), doc)
}
```

这样：

1. **项目页**只执行 `apply`，注册连接与历史查询；不碰画布。
2. **进入画布**时 `mountCanvas` 装完 `doc` 等服务后，调用 `onCanvasReady`，同步部分这时才注册；`unmountCanvas` 调用它的 dispose，订阅、定时器、适配器一起回收。
3. **共用一份连接**：`acquireSharedConnection` 用 `globalThis` 上的注册表按 `baseUrl` 复用同一个 `CloudApi` 与共享 KV/SSE 通道；不能只用模块级单例，因为外部 ESM 插件可能被加载成两份模块实例。
4. `cloud-client` 与 `cloud-client:history` 两个服务名保持不变，`plugin-style-library` 与 `useHistoryScope` 不用改。

需要注意的两个边界：

- 内核**没有“某个服务被注入”的广播事件**，所以不能在 `apply` 里等 `doc` 出现。这正是要显式调用 `onCanvasReady` 的原因。
- 插件 `ctx.inject('doc', …)` 返回的撤销函数只从服务表里删掉服务，**不会**主动触发依赖方回退；依赖方回退只发生在“提供该服务的插件被卸载”或整个 `Context.stop()` 时。这就是 `mountCanvas` 用 `installPlugin`/`uninstallPlugin('canvas-data')` 而不是手动 `inject`/撤销的原因。这样做还有一个前提：`canvas-data` 不能声明 `core: true`，否则 `uninstallPlugin` 会被内核拒绝。

### 服务通知事件：本次不做

**现状**：内核没有“服务被注入/撤销”的广播事件。`EventBus` 只登记了 `ctx:ready`、`ctx:plugin-installed`、`ctx:plugin-uninstalled`、`ctx:lifecycle-change` 四个事件（`packages/kernel/src/EventBus.ts:144`）。服务出现时，内核靠 `inject` 依赖调度把 `PENDING` 插件唤醒（`packages/kernel/src/Context.ts:271` 的 `wakePending`），已经在运行的插件收不到通知。

**这次为什么不做**：`mountCanvas` 已经在装完服务后显式调用插件的 `onCanvasReady`；`style-library` 在使用时现取能力，缺了就禁用按钮。两者都不需要广播。加事件会扩大内核契约：服务名很多、运行期会频繁变化，插件很容易把“通知”误当成“服务一定可用”，反而制造新的时序 bug。

**以后如果确实需要**（例如常驻插件必须在 `doc` 出现后热启用，而不想再启动一次插件），建议这样加：

- 事件名：`ctx:service-provided`、`ctx:service-revoked`，payload 为 `{ name: string; source: string }`。
- 触发点：根 `Context.inject` 成功登记后发 `provided`；撤销函数真正删掉服务时发 `revoked`；插件作用域的 `provide` 与 fiber 回收走同一对事件。
- 顺序：先改服务表，再发事件，最后 `wakePending`；不要反过来，否则监听方会拿到旧状态。
- 测试：服务注入后 PENDING 插件被唤醒；服务撤销只发事件、不自动回退依赖方（回退仍只由插件卸载或 `stop()` 触发）；同一服务重复注入/撤销各只发一次。
- 风险：事件监听方必须自己再做一次 `tryGet`，不能把事件 payload 当成服务实例；事件不能替代 `inject` 的硬依赖语义。

结论：本次只做应用层/画布层拆分，不新增内核事件；等出现“必须热启用”的真实需求再加。

### 路由切换时插件怎么处理

这里有两条路径，处理方式不同：

| 从 → 到 | 根级 Context | 画布服务 | 画布插件 |
| --- | --- | --- | --- |
| 项目页 → 画布页 | 不变 | `mountCanvas` 装上 | `inject` 满足，自动启动 |
| 画布页 → 项目页 | 不变 | `unmountCanvas` 撤销 | 依赖消失，自动回退 `PENDING` |
| 画布 A → 画布 B | 不变 | 先卸 A，再装 B | 旧实例回收，新实例启动 |

这里说的“插件做处理”不是让每个插件自己监听 router；Vue Router 切页只是让 `App.vue` 挂载/卸载，由它调用 `mountCanvas` / `unmountCanvas`。插件拿到的仍是内核的 `apply` / fiber 回收，路由不需要进插件。

改造后不再有第二个 `Context`，`readyHost` 这类“模块级宿主单例”也不再需要：组件统一从根 `ctx` 取服务。`Root.vue` 的 `route.fullPath` key 保留，负责在切画布时重建画布组件；`router.ts:32` 的 `flushPendingSave()` 守卫保留，确保离开画布前先落盘。

验收时专门走一遍：项目页 → 画布 → 项目页，确认项目页历史仍能查询、画布插件已回退 `PENDING`、再进画布时不会出现两份画布服务或两份连接。

### 先把三个“ctx”说清楚

现在代码里有三个长得像的东西，容易看混：

| 写法 | 是什么 | 举例 |
| --- | --- | --- |
| `context.ctx` | `CanvasProvider` 交给组件的**内核上下文**，插件、服务、插槽都从它取 | `context.ctx.get('doc')` |
| `context.host` | **画布宿主句柄**，里面有 `save`、`doc`、`nodeStore`、`stop()` 这些宿主能力 | `context.host.save.flush()` |
| `context.host.ctx` | 宿主句柄里的 `ctx`。它和 `context.ctx` **是同一个对象**，不是第三层上下文 | `context.host.ctx.get('settings')` |

也就是说，`context.host.ctx` 只是“同一个内核上下文，从宿主那边又写了一遍”。`CanvasProvider.vue:47` 的 `ctx` getter 直接返回 `mustBoot().host.ctx`；`CanvasSurface.vue` 的 `renderCtx.ctx` 也是 `host.ctx`，所以它们指向同一份内核 `Context`。

仓库里目前**没有**字面量 `ctx.host.ctx`（`rg 'ctx.host.ctx'` 无结果）。如果你看到的是 `host.ctx`，那就是上表第三行；如果写成 `ctx.host.ctx`，那是把内核 `Context` 当成带 `host` 字段的对象了，内核 `Context` 并没有 `host` 字段，运行时会拿到 `undefined`。

新方案统一叫法：

- 只有一份 `Context`，组件里统一从 `useCanvasContext().ctx` 取服务；项目页拿不到 `doc` 是正常的，用 `tryGet` 判断即可。
- `host` 只在画布内存在，用来落盘、停止、拿 `nodeStore`；项目页没有 `host`，不要伪造空对象。
- `host.ctx` 与根 `ctx` 是同一个对象；新代码不再写 `host.ctx`，保留它只为兼容旧调用点。
- 为什么这样改：只有一份 `slots/settings/ui` 目录，插件只登记一次；项目页不启动画布服务，画布页只是在同一个 Context 上多装几个服务。不会出现“面板注册在哪一层”的二选一问题。
- 风险 / 影响面：`mountCanvas` 必须严格成对调用，先落盘再撤服务；`theme-components` 与 `theme-canvas` 的拆分要保证所有 `NodeRegistry`/`ThemeRegistry` 注册都有对应回收。外部安装的插件登记到根 Context，依赖 `doc` 的仍会等画布；`plugin-manager` 的安装句柄要在根级 Provider 建好后绑定，项目页才能真正安装。`packages/ui/src/__tests__/appCanvasProvider.test.ts` 目前锁定旧层级，改动后要改成验证“根 Provider + `mountCanvas`/`unmountCanvas`”。
- 验证方式：浏览器直接打开 `#/`，确认项目页出现示例插件面板、控制台没有「缺少画布上下文」；打开一张画布，确认节点、连线、保存、撤销、主题、插件设置页正常；项目页切到画布再返回，确认通用插件仍在、画布插件已停止、没有遗留监听；在项目页观察网络请求，确认没有对 `default` 画布的读写请求。
