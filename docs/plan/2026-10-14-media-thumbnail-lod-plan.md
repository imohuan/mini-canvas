# 图片 / 视频节点缩略图分档显示方案（v3）

日期：2026-10-14
状态：**已按「插件只改自己」重做**（见 v4 说明）
与 v2 的差别：
- 图片与视频各自独立三档（图片第 1 档 = 原图；视频三档**全是帧图**）；
- 视频帧的落点从「节点 data 的 `posterUrl`」改成「**与图片同款的派生地址**」（`th-<源名>-t…`）；
- 明确回答「播放会不会导致重复生成」：**不会**，只有「换源 / 改档位参数 / 点重新取帧」三种情况才重做。

## 一、你的问题的答案：播放不会导致重做

用「可推导命名」后，帧图地址是**从源视频名算出来的**，不是节点上的状态：

```
源视频：  <base>.mp4
第 1 档帧：th-<base>-t0x0q72.webp     ← 原生尺寸的那一帧
第 2 档帧：th-<base>-t512x512q72.webp
第 3 档帧：th-<base>-t160x160q72.webp
```

于是：

- 播放 → 暂停 → 再播放 → 再暂停：地址一次都没变，
  浏览器对同一个地址有缓存，**不会重新生成、不会重新解码**。
- 换档（缩小/放大）：档位变了，但三张帧的地址是**固定**的，谁在缓存里就用谁；
  没生成过的那一档由后台懒生成一次，之后一直命中。
- 唯一会「重做」的三种情况：① 换了源视频（`.mp4` 变了 → 名字跟着变）；
  ② 你改了 config 里的档位尺寸（512→640 → 名字里带数字，自然算成新地址）；
  ③ 用户手动点「重新取帧」（见 §四）。

也就是说，你担心的「每次播放都来回生成」在推导式命名下**根本不会发生** ——
因为播放这个动作不改变任何地址。

## 二、为什么视频的「原图帧」也要做成图片

你的口径是「默认是视频 + 三张帧图，1 对 3」，这和图片那边正好相反
（图片第 1 档就是原图本身）。这是个好设计，原因是：

- 视频节点**不播放时不挂 `<video>`**（你的要求「只有点播放才真正加载视频」），
  所以第 1 档也必须是一张图；
- 好处很实在：一屏几十个视频节点，未播放时**零视频解码**，只有几张 webp。

实测（本机 ffmpeg 5ddab49d48，1920×1080 测试视频）：

| 产物 | 大小 |
|---|---|
| 第 1 档帧（原生尺寸） | 14.8 KB |
| 第 2 档帧（装进 512 框） | 3.8 KB |
| 第 3 档帧（装进 160 框） | 1.5 KB |

**三张一次生成，不要分三次**。实测耗时：一条命令带 `filter_complex` 同时出三张 **222 ms**；
分三条命令分别生成 **808 ms**（每次都要重新起进程 + 重新 seek + 重新解码）。
所以后台一见「`th-<base>-t0x0q72.webp` 不存在」就把三张一起做掉，
另外两张同一次落盘 —— 之后任何档位都直接命中。

## 三、帧图挂在哪个字段？（这里我改了 v2 的做法）

v2 我写的是写进节点 data 的 `posterUrl`。按你的「可推导」思路，**那个字段不用写了**：

- 帧图地址 = `videoUrl` 换个名字（源名 + `th-` 前缀 + 档位 spec）。
- 所以节点 data **一个字段都不用加**，也就没有「落盘 / 撤销栈 / 缩略图字段的回收」这些事。
- 连带的修正：`RESOURCE_URL_FIELDS` 里已有的 `posterUrl`/`thumbUrl` v2 也不动
  （那是别的功能用的，保持向后兼容）。

## 四、节点重做 / 重新取帧（这里需要一个明确的清理规则）

你说「播放之后位置不一样」我理解成两件可能的事，两种情况处理方式不同：

**(a) 如果指「图层位置/占位**：那不影响帧图。播放与否都画在同一个卡片里，
只是内容从 `<img>` 换成 `<video>`，卡片尺寸靠 `videoWidth/Height`（不变）。

**(b) 如果指「换了视频内容」**（重新上传、后台重新生成到同一个节点）：
新视频的字节是**新的内容哈希** → 新源名 → 三个新派生名 → 新帧图**自动**生成。
旧帧图变成孤儿，需要清理规则（见 §六的「孤儿清理」）。

**手动「重新取帧」**要不要留一个入口？我倾向留，但要有规矩：

- 入口放在视频的**更多菜单**里（不要做成常驻按钮，它不该是高频动作）；
- 它做的事只有一件：**删掉这三张派生帧图**，然后回到正常流程 ——
  下次渲染发现不存在 → 后台按同一个时刻重新生成。不引入任何新状态。
- 一句话：**地址不变、内容可刷新**。不要发明「帧图 + 版本号」这类命名，
  那会让缓存每次失效，反而变成你担心的「来回生成」。

## 五、什么时候会重做（汇总表）

| 事件 | 帧图要重做吗 | 说明 |
|---|---|---|
| 播放 / 暂停 / 拖进度 | **不要** | 地址不变，浏览器用缓存 |
| 档位之间来回缩放 | **不要** | 三张地址固定，各自懒生成一次后一直命中 |
| 全屏播放 | **不要** | 只是多了个 `<video>`，帧图不参与 |
| 换源视频 | 自动 | 新源名 = 新派生名，旧的成孤儿（§六清理） |
| 改档位尺寸配置 | 自动 | spec 数字在名字里，算出来是新地址 |
| 手动「重新取帧」 | 手动 | 删三张派生文件即可，无新状态 |
| 后台重启 / 刷新页面 | **不要** | 文件已在磁盘上，命中即回 |

## 六、清理规则（避免磁盘上长草）

三处会产生「没人再引用的派生文件」，一并定死：

1. **配置改名**（512→640）：旧 spec 的派生文件不再有任何地址指得到它。
   → 可选：后台启动时扫一遍资源目录，删掉「spec 不在当前配置里」的 `th-` 文件
   （**只删派生文件，永不删源文件**，判据就是 `th-` 前缀 + `parseThumbName` 认得出来）。
2. **源被删**（节点删了、资源回收了）：该源名下 `th-` 开头的文件一起删。
   现有的资源回收路径在 `ResourceStore.revoke` / `disposeUnreferenced`；
   后台侧对应的是「画布资源目录里的清扫」，两边的判据要写成同一个纯函数。
3. **源被覆盖**（槽位 `slot-<id>.mp4` 原地换内容）：**派生名不会变**（源名没变）
   → 内容却旧了。这是这套命名唯一的真坑。
   → 两选一：(a) 槽位源更新时**顺手删掉它的派生文件**（推荐，确定性最好）；
   (b) 派生文件存一个「源 mtime/大小」戳，读取时对不上就重生成（多一次 stat，但更稳）。
   我倾向 (a) + 测试锁住。

## 七、前端行为（与 v2 相同的部分不重复）

- 档位判定与地址推导都是纯函数（零 Vue、零 DOM，Node 可单测）：
  `resolveMediaTier({ zoom, tier2Zoom, tier3Zoom })`、`tierUrlFor(srcUrl, tier, spec)`。
- 只认画布资源地址（`/api/canvases/<id>/resources/<name>`）；外链 / `data:` / `blob:` /
  本地 `res-` 一律返回 `undefined` → 回落到「下一件能用的东西」。
- **回落链（视频）**：想要的档位 → 原图帧（第 1 档帧）→ `<video>`（最后手段）。
  也就是说后台没有 ffmpeg 时，视频会退化成**直接显示 `<video>`**（今天的画布行为），
  不空白、不报错。
- **回落链（图片）**：想要的档位 → 原图（今天的画布行为）。
- 编辑态（裁剪 / 扩展 / 蒙版）强制第 1 档（图片是原图、视频是原生帧）：
  浮层是按原图像素算框的，底下垫缩略图会让框对不上像素。
- 视频非播放态画帧图（`<img>`），点播放才挂 `<video>`；全屏播放同理。
  仍分两步走：第一步加帧图（`<video>` 保留但不显示），确认裁剪/截图回归后第二步摘掉。

## 八、后台要实现的东西（在 v2 基础上）

| 项 | 内容 |
|---|---|
| 派生名 | `thumbNameFor(srcName, spec)` / `parseThumbName(name)`；白名单加一条派生规则（实测现有白名单会 400，见 v2 §三） |
| 生成器 | 图片：`-i src -frames:v 1 -vf scale=W:H:force_original_aspect_ratio=decrease`；视频：`-ss at -i src -frames:v 1`；`filter_complex + split` **一次出三张** |
| 懒生成分支 | `GET /api/canvases/:id/resources/:name`：派生名 + 文件不存在 → 生成（源视频时三张一起） |
| 并发与失败记忆 | 同一张同时只生成一次 + 并发上限（推荐 2）；失败结果短期 TTL，避免坏文件被反复重试 |
| 探针 | 启动探 `ffmpeg -version` → `/health` 报 `capabilities.ffmpeg`；没有就整体降级（按你的口径） |

视频的 `spec` 里我建议**档位尺寸单独配**（视频的帧通常要比图片大一点才看得清），
也就是视频有自己一套 `tier2Width/Height`、`tier3Width/Height`（图片那套独立）。

## 十、验证方式（增补）

在 v2 那套（派生名往返、清单排除、档位判定、地址推导、懒生成分支、真机三档切换）之外，加：

1. **一次出三张**：请求第 1 档帧 → 断言磁盘上同一次出现三张；
   ffmpeg 只被调用一次（注入的假实现可断言调用次数）。
2. **播放不重做**：反复播放/暂停/切档，断言派生文件数量不变、mtime 不变。
3. **换源自动重做**：把视频换成另一段，断言三个新名字被生成、旧的成为孤儿。
4. **槽位覆盖**：覆盖 `slot-<id>.mp4` 后断言派生文件被删（或时间戳判据生效）。
5. **无 ffmpeg 降级**：把 ffmpeg 从 PATH 拿掉 → 视频回落显示 `<video>`、图片显示原图、
   `/health` 报 `ffmpeg:false`、任务照常跑。

## 十一、落地顺序（相对 v2 多了第 3.5 步）

1. 配置项 + 档位/地址纯函数（前端骨架，此时行为不变）。
2. 后台派生名 + 懒生成 + `/health`（图片先通）。
3. 视频三张帧图（复用同一条生成器，改成一次出三张）。
4. 视频非播放态画帧图（`<video>` 先留着）。
5. 摘掉非播放态的 `<video>`（确认裁剪/截图回归后）。
6.（可选）手动「重新取帧」入口 + 孤儿清理 / 槽位覆盖处理。
