# 服务清单与宿主装配总览（把画布服务一次接好）

> 来源：`packages/kernel/src/index.ts`、`packages/kernel/src/Context.ts`、
> `packages/canvas-data/src/index.ts`、`packages/canvas-data/src/canvas/index.ts`、
> `packages/canvas-data/src/canvas/canvasBasePlugin.ts`、`packages/canvas-data/src/canvas/capabilityLayer.ts`、
> `packages/canvas-render/src/host/createMiniCanvasHost.ts`

这篇把"ctx.get 能取到什么、谁放的、宿主怎么装"一次讲清，最后给一个**能跑的装配骨架**。

---

## 1. 每个包导出什么（从哪 import）

| 包 | 是什么 | 能 import 到什么 |
| --- | --- | --- |
| `@mini-canvas/kernel` | 纯插件框架：装载 / 依赖 / 事件 / 作用域回收 / 注册场 / 命令 / 配置 | `Context`、`runPlugin`、`Service`、`asPluginModule`、`topoSort/depsOf`、`EventBus/registerEventName`、`RegistryImpl`、`SlotRegistry`、`CommandRegistry`、`SettingsStore`、`ToolRegistry`、`F/resolveConfig`、各类型 |
| `@mini-canvas/canvas-data` | 数据层 + 画布语义 | 数据类（`NodeStore`/`EdgeStore`/`Selection`/`History`/`GraphDocument`）、`createDocService`、存储（`SaveServiceImpl`/`MemoryStorageAdapter`/`LocalStorageAdapter`/keys）、画布注册表（`NodeRegistry`/`ThemeRegistry`）、`registerNodeType`/`registerThemeSlot`、连接校验纯函数、`NodeFactory`、`createCanvasBasePlugin`、`Context`（画布版） |
| `@mini-canvas/canvas-render` | 渲染宿主（Vue + VueFlow） | `CanvasHost`/`CanvasSurface`/`SlotHost`/`SettingsHost`、`createMiniCanvasHost`、`assembleTheme`、`reasonText`、令牌与 `useCanvasRender` |
| `@mini-canvas/canvas-base` | 插件作者的薄入口 | 重导出 kernel + canvas-data 的类型与常用助手，加 `defineNode`/`defineThemeSlot`/`defineCommand`/`defineSlot` |
| `@mini-canvas/ui` | 成品应用出口 | `CanvasApp`/`mountCanvasApp`、插件装配清单 |

作者侧写插件**只 import `@mini-canvas/canvas-base`**（要窄接口时再补 `@mini-canvas/canvas-data` 的类型）。
宿主侧 import `@mini-canvas/canvas-data`（想一行出画布就用 `@mini-canvas/canvas-render` 的 `createMiniCanvasHost`）。

## 2. 服务清单（ctx.get 得到谁）

### 2.1 内核自带（框架里就有，不占 services 表）

| ctx.get 名 | 类型 | 说明 |
| --- | --- | --- |
| `'tools'` | `ToolRegistry` | 外部能力注册表（文生图 / 图生文…）。`ctx.tools` 与 `ctx.get('tools')` 是同一实例 |

### 2.2 能力层内置（同样不在 services 表，由**画布能力层**提供）

| ctx.get 名 | 类型 | 说明 |
| --- | --- | --- |
| `'slots'` | `SlotRegistry` | 通用 UI 槽容器（`ctx.slots` 写这里） |
| `'settings'` | `SettingsStore` | 配置单一数据源（`ctx.settings` 读这里） |

> 这两个是 `createCanvasCapabilityLayer()` 里 `new` 出来的，宿主与插件共享同一实例；`ctx.stop()` 会重建 settings、保留 slots（见 `capabilityLayer.ts`）。
> `ctx.get` 的查找顺序是：先内置（tools / slots / settings），再 services 表（`Context.ts` 的 `builtinService`）。

### 2.3 `canvas-base` 插件注入的服务（真服务）

| ctx.get 名 | 类型 | 说明 |
| --- | --- | --- |
| `'save'` | `SaveServiceImpl` | key-value 持久化（可插拔 adapter） |
| `'doc'` | `DocService` | **数据那一格只有它**：节点 + 边 + 事务 + 撤销 + 快照 + 订阅 |
| `'resources'` | `ResourceStore` | 资源生命周期（object URL 登记 / 回收） |
| `'nodeRegistry'` | `NodeRegistry` | 节点展示注册表（哪个 type 的哪个区域用哪个组件） |
| `'themeRegistry'` | `ThemeRegistry` | 主题 / 外观槽注册表 |
| `'selection'` | `Selection` | 选中集（节点 + 边两桶） |
| `'command'` | `CommandRegistry` | 命令注册表 |
| `'nodeFactory'` | `NodeFactory` | 统一建节点工厂 |
| `'settingsPersist'` | `SettingsPersistService` | **条件注入**：`persistSettings !== false` 且 ctx 有 settings 时才有 |

> 这九件由 `createCanvasBasePlugin()` 的 `apply` 用 `ctx.inject` 上架（见 `canvasBasePlugin.ts` 的 `plugin.apply`），随该插件 fiber 回收。

### 2.4 渲染宿主注入的服务

| ctx.get 名 | 类型 | 说明 |
| --- | --- | --- |
| `'nodeLayout'` | `NodeLayoutService` | 实测尺寸 / 绝对坐标（要量 DOM，数据层给不了） |
| `'viewport'` | `ViewportService` | 视口（要 attach VueFlow 后端） |

> 这两个由 `createMiniCanvasHost` 在装 `canvas-base` **之前**注入（`createMiniCanvasHost.ts` 的 `ctx.inject('nodeLayout'…)` / `ctx.inject('viewport'…)`），保证业务插件 `start` 后 `ctx.get` 立刻拿得到。

### 2.5 已经下线的旧服务名（**取不到**）

老版把数据拆成四个服务：节点表 / 边表 / 图写入口 / 撤销栈。现在这四个**名字**都下线了——
`ctx.get` 拿不到它们，数据统一走 `doc`：

- 节点表、边表、图写入口、撤销栈这四个名字 → 全并进 `'doc'`。

对应的**类**仍然存在（`NodeStore`、`EdgeStore`、`GraphDocument`、`History`），由 `canvas-base` 建好、交给 `doc` 门面持有；
宿主句柄 `CanvasHostHandle` 上也直接挂着这四个实例（渲染层要 `subscribe`、要量尺寸）。
**它们是对象，不是服务名** —— 严格来说，类名照用，服务名只有一个 `'doc'`。

## 3. 宿主装配完整 ctx（骨架）

### 3.1 只用数据层（自己组装）

```ts
import { Context, createCanvasBasePlugin } from '@mini-canvas/canvas-data'
import { LocalStorageAdapter } from '@mini-canvas/canvas-data'

// 1) 建 ctx（dev 开未声明事件的警告，生产关）
const ctx = new Context({ dev: true })

// 2) 建基础插件：它同时把服务实例建好（要在 start 前就能拿到）
const base = createCanvasBasePlugin({ adapter: new LocalStorageAdapter() })

// 3) 渲染层那两件由宿主自己建、start 前注入（顺序无所谓，但必须在 start 之前）
//    const nodeLayout = new NodeLayoutService(base.services.nodeStore)   // 这里取的是实例字段
//    const viewport = new ViewportService()
//    ctx.inject('nodeLayout', nodeLayout)
//    ctx.inject('viewport', viewport)

// 4) 装基础插件（core: true，拒绝动态热卸）+ 业务插件
ctx.plugin(base.plugin)
ctx.plugin(myTextPlugin)                       // { name, Config, apply(ctx, config) }
ctx.plugin(myThemePlugin, { edgeColor: '#0af' })  // 第二个参是装配 config

// 5) 启动（按依赖激活）
await ctx.start()

// 6) 兜底落盘
await base.services.save.flush()

// 运行时热装 / 热卸（需已 start）
ctx.installPlugin({ name: 'hot', apply() {} })
ctx.uninstallPlugin('hot')

// 停机（可再 plugin + start）
ctx.stop()
```

> `createCanvasBasePlugin` 的返回值是 `{ name, plugin, services }`：`plugin` 交给 `ctx.plugin(...)`，
> `services` 里是已建好的 12 件实例（`save`/`doc`/`resources`/`nodeRegistry`/`themeRegistry`/`selection`/
> `command`/`nodeFactory` 这 8 件进了服务表，另有 `NodeStore`/`EdgeStore`/`GraphDocument`/`History` 4 件实例只有 `services` 上有）。

### 3.2 一行出画布（渲染宿主帮你装配）

```ts
import { createMiniCanvasHost } from '@mini-canvas/canvas-render'

const { host, api, manager } = await createMiniCanvasHost({
  adapter: new LocalStorageAdapter(),
  coldPlugins: [themeDefaultPlugin, nodeTextPlugin],  // 顺序即装载顺序
  dev: import.meta.env.DEV,
})
```

想自己组织装配时用 3.1；只是想出一张画布，用 3.2（它内部就是 3.1 + 装 `nodeLayout`/`viewport` + 注册画布通用命令）。

## 4. 插件作者视角的最小示例

```ts
// my-feature.ts —— 一个把数据、换肤、命令、配置、事件串起来的插件
import { F, type Context } from '@mini-canvas/canvas-base'
import MyBlockContent from './MyBlockContent.vue'
import MyBackground from './MyBackground.vue'

export const name = 'my-feature'
// 硬依赖：框架保证 apply 执行时它们已就绪；缺提供方则本插件停在 PENDING
export const inject = ['doc', 'nodeRegistry', 'themeRegistry', 'command', 'nodeFactory']
// 配置声明：模块级导出 Config，内核校验 + 补默认后传给 apply(ctx, config)
export const Config = {
  edgeColor: F.color('#3b82f6'),
  glow: F.boolean(true),
}

export function apply(ctx: Context, config: { edgeColor: string; glow: boolean }) {
  // 注册节点类型（数据 + 展示 + 可选建节点）
  ctx.nodes.register({
    type: 'my-block',
    label: '我的块',
    size: { w: 160, h: 90 },
    in: MyBlockContent,                       // 区域词 in = 卡片内部
    create: (pos) => ctx.get('doc').createNode('my-block', pos),
  })

  // 换肤
  ctx.theme.register('background', MyBackground)

  // 注册命令（keys 由渲染层统一分发）
  ctx.commands.register({
    id: 'my:clear',
    title: '清空',
    when: () => ctx.get('selection').size > 0,
    run: () => { ctx.get('doc').removeNodes([...ctx.get('selection').ids]) },
  })

  // 订阅自己的配置，实时就地生效
  ctx.settings.onChange(name, (key, value) => console.log('配置变了', key, value))

  // 事件（注册与监听都随插件回收）
  ctx.on('ctx:ready', () => console.log('就绪'))
}
```

插件 `apply(ctx)` 里经 `ctx` 做的注册（能力段、事件、effect）**全部自动回收**：插件卸载即清，作者不用手写注销。

## 5. 自省：一次问清"这台画布装了什么"

`ctx.surface()` 只读、零副作用、随时可调（created / started 都行）：

```ts
const s = ctx.surface()
s.services        // [{ name, source, methods? }]  —— 按名可取的服务 + 谁注入的
s.registries      // [{ kind, keys: [{ key, count }] }] —— 每个注册场有哪些键、几条
s.registryEntries // [{ kind, key, id, order, source, fields? }] —— 条目明细
s.commands        // 命令清单（含 keys / areas / group / origin: 'field' | 'service'）
s.tools           // 生成工具（含声明式 params）
s.modelTools      // 模型可调用工具
s.events          // 已登记的事件名
```

> `source` 回答"谁放的"：插件名 / `'<host>'` / `'<anonymous>'` / `'<builtin>'`。
> 命令的 `origin: 'service'` 表示"走 command 服务直注册"（画布自带的建节点/删除/撤销/重做四条），不是从注册场读到的。

## 6. 坑与速记

1. **数据只有一个名字**：`doc`。旧的四条数据服务名已下线，`ctx.get` 取不到；别照老代码写。
2. `slots` / `settings` 是**能力层内置**（不在 services 表里，但 `ctx.get` 拿得到）；`tools` 是内核自带。
3. 注入必须在 `start()` 之前（服务要在插件跑起来之前上架）。`ctx.inject` 对重名会抛错。
4. **首选声明依赖的方式是模块顶层 `export const inject = [...]`**，不是到处 `ctx.get`：`ctx.get` 是给**可选依赖**用的（缺服务返回 `undefined`，不抛）。想过一下"到底有没有"用 `ctx.hasService(name)` / `ctx.tryGet(name)`。
5. `dev: true` 只影响两件事：EventBus 对未登记事件名 warn、能力包 needs 缺项时抛错（生产改为 `undefined` + warn）。库内读 `import.meta.env` 不可靠，`dev` 必须由调用方显式传（`packages/ui/src/App.vue` 传 `import.meta.env.DEV`）。
6. 加"一类新扩展点"的正规做法是 `ctx.registryOf('新种类')`，**不是**新增一个服务。kind 的权威清单见 `docs/design/core-layers-and-registry.md` §4.5。
7. 装配顺序无所谓（`start` 按依赖决定激活顺序），但**注入顺序有所谓**：服务要在用它的人之前上架。
