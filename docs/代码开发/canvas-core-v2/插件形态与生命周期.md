# 插件形态与生命周期

> 来源：packages/canvas-core-v2/src/core/types.ts、Context.ts、pluginClass.ts、service.ts、core/index.ts

讲清楚两件事：**一个插件能长成哪几种样子**、**插件从被装到被卸都经过哪些状态**。

---

## 1. 插件最终都归一成一种对象：PluginModule

不管作者怎么传，内核内部都会把"插件"看成下面这个**对象**来处理（`PluginModule`）：

```ts
interface PluginModule<TConfig extends object = object> {
  name: string            // 唯一名，必须给
  deps?: string[]         // 依赖（旧式写法）
  inject?: string[]       // 依赖（推荐写法，优先于 deps）
  Config?: ConfigSchema   // 本插件的配置 schema（可选）
  setup?(ctx: PluginScope): void | (() => void) | Disposable   // 旧式
  apply?(ctx: PluginScope, config?: TConfig): void | (() => void) | Disposable  // 推荐
}
```

字段含义：

- **`name`**：插件唯一名。全内核不能重名，否则抛错。
- **`inject` / `deps`**：这份插件**必须要等谁先就绪**。可写两类名字：
  - 一个**服务名**（别的插件 `provide`/`inject` 提供的服务）；
  - 另一个**插件名**。
  - 内核会等依赖满足才跑 `apply`（依赖不满足就停 PENDING，等提供方出现）。
- **`Config`**：本插件的配置 schema（怎么声明见《配置装配篇》）。
- **`apply`**：真正的注册函数。`apply` 优先于 `setup`，`inject` 优先于 `deps`。二者至少给一个。
- `apply(ctx, config)` / `setup(ctx)` 可以返回一个 cleanup 函数（或带 `dispose()` 的对象），内核把它登记进插件自己的 Scope，**卸载自动调用**。

> `runPlugin` 的判定顺序（源码就这么干）：`mod.apply` 有就调 `apply(ctx, config)`；否则有 `mod.setup` 就调 `setup(ctx)`；都没有返回 undefined。

---

## 2. 三种写法

### 2.1 对象形态（推荐，教程主推）

Cordis 式：`.ts` 裸导出 `name / inject / Config / apply`。

```ts
// 假设文件 my-plugin.ts
export const name = 'my-plugin'
export const inject = ['nodeStore']          // 可选，依赖别的服务/插件
export const Config = {                      // 可选，配置 schema
  speed: { type: 'number', default: 1, min: 0, max: 10 },
}
export function apply(ctx: PluginScope, config: { speed: number }) {
  // ctx 是能力台，注册都自动回收
  ctx.nodes.register({ type: 'my', label: '我的节点', size: { w: 100, h: 80 } })
}
```

装配方把它装上去：

```ts
ctx.plugin(myPluginModule, { speed: 3 })   // 第二个参是装配 config
await ctx.start()
```

### 2.2 类形态（extends Service）

把"一个类"直接当插件。类通常继承 `Service`，构造时 `super(ctx, name)` 会顺手上架一个服务（名字就叫 name），`new 类(ctx, config)` 就算把插件跑起来了。

```ts
import { Service, type PluginScope } from '@mini-canvas/canvas-core-v2'

export class GreeterService extends Service {
  // 静态可标注依赖 / Config / 默认服务名
  static inject = [] as string[]
  static Config = { greeting: { type: 'string', default: 'Hi' } }
  constructor(ctx: PluginScope, config?: any) {
    super(ctx, 'greeter')     // 上架服务名 'greeter'
  }
  greet(w: string) { return 'Hi ' + w }
}

// 装配：直接传类
ctx.plugin(GreeterService)    // 或冷启动 plugins:[GreeterService]
await ctx.start()
```

> 类形态装载的本质：内核把类归一成 `PluginModule` —— `name` = 类静态 `provide` 或类名，`apply = (ctx, config) => new 类(ctx, config)`。构造里 `super(ctx, name)` 把实例上架为服务，随本插件 Scope 自动回收。

也可以只传 `name` 走静态 `provide` 字段：

```ts
class StaticNamed extends Service {
  static provide = 'staticName'   // 不传 name 时取这个
  constructor(ctx: PluginScope) { super(ctx) }
}
```

### 2.3 函数形态

一个具名函数也能当插件。函数名 = 插件名，函数体当成 `apply(ctx, config)` 调。

```ts
export function heartbeat(ctx: PluginScope) {
  ctx.on('ping', () => console.log('pong'))
}
ctx.plugin(heartbeat)
```

> **坑**：函数形态插件必须有名字（不能是匿名函数），否则抛错 `函数形态插件需具名`，因为要靠名字做装配寻址/诊断。

## 3. Service 基类：往 ctx 上架一项能力

类形态的底座是 `Service`。继承它并 `super(ctx, name)`，就在 ctx 上架了一个叫 name 的服务，别的插件 `inject: ['name']` 或 `ctx.get('name')` 就能拿到。

```ts
export abstract class Service {
  readonly ctx: PluginScope
  readonly name: string
  constructor(ctx: PluginScope, name?: string)
}
```

- 不传 `name` 就取子类静态 `provide` 字段；再没有就抛错（`[core] Service 需传 name 或给子类静态 provide 字段`）。
- `super(ctx, name)` 内部调 `ctx.provide(name, this)`：上架服务，撤销随本插件 Scope 自动回收（插件卸载即移除）。

## 4. 生命周期状态（Lifecycle / FiberState）

内核给每个插件维护一个状态。**两套状态名词**要分清：

### 4.1 Lifecycle（业务生命周期，`ctx:lifecycle-change` 事件用）

`types.ts` 里的 `enum Lifecycle`：

```
INSTALLING → INSTALLED → ACTIVATING → ACTIVE
  ↘                                ↘
  (装载过程)                          UNINSTALLING → UNINSTALLED
                                    ERROR(失败)
```

> 说明：`INSTALLED` 这个枚举值存在，但 `Context.setLifecycle` 实际只下发
> `INSTALLING / ACTIVATING / ACTIVE / UNINSTALLING / UNINSTALLED / ERROR`，**`INSTALLED` 从不被触发**——
> 诊断/监听 `ctx:lifecycle-change` 时以实际下发的这几个为准即可。

### 4.2 FiberState（fiber 状态机，`ctx.fiber(name).state` 用，诊断主看这个）

`fiber.ts` 里的 `FiberState` 字符串常量：

```
PENDING → LOADING → ACTIVE
  ↘         ↘
 (缺依赖)   FAILED(apply/config 抛错)
卸载: ACTIVE/FAILED/PENDING → UNLOADING → DISPOSED
```

状态含义（大白话）：

- `pending`：已声明 / 在等所需服务（依赖没到齐就停这）。
- `loading`：`apply`/config 正在跑。
- `active`：加载完成、服务可用（正常跑起来了）。
- `failed`：apply 或 config 校验抛错了。
- `unloading`：正在清理。
- `disposed`：已卸载，不可再启动。

怎么查一个插件的状态、怎么诊断卡在哪，看《Fiber 状态机与诊断篇》。这里你只需要知道：**内核会自动把插件推到该在的状态，你几乎不用手改**。

## 5. 冷启动 / 热装 / 热卸 / 热重载（四大操作）

| 操作 | 方法 | 只能用在哪 | 说明 |
| --- | --- | --- | --- |
| 冷启动装载 | `ctx.plugin(mod, config?)` | `start()` **之前** | 登记，等 `start()` 一起跑 |
| 启动 | `await ctx.start()` | state=`created` | 按依赖多轮激活，依赖满足的逐个跑 apply |
| 停机 | `ctx.stop()` | state=`started` | 倒序卸光所有插件、清光副作用，可重新 start |
| 运行中热装 | `ctx.installPlugin(mod, config?)` | `start()` **之后** | 依赖满足立刻可用，否则挂 PENDING |
| 运行中热卸 | `ctx.uninstallPlugin(name)` | `start()` 之后 | 清光副作用；连带把"因此缺依赖"的 ACTIVE 依赖方回退 PENDING |
| 热重载 | 先 `uninstallPlugin` 再 `installPlugin` 同名 | `start()` 之后 | 模拟插件代码换版，同 name 可装新实现 |

### 5.1 冷启动 start() 怎么跑

`start()` 会做"确定性多轮激活"：

1. 反复扫所有插件，凡是 `inject` 依赖现已满足（有该服务、或该插件已 ACTIVE、或是内置 `slots`/`settings`）的就激活它；
2. 激活顺序 = 插件登记顺序（确定性）；
3. 全激活完广播 `ctx:ready`。

所以哪怕依赖方先登记、提供方后登记也没关系，内核会自动等提供方激活后再跑依赖方。

```ts
ctx.plugin({ name: 'consumer', inject: ['greeter'], apply() { /* 一定在 greeter 之后跑 */ } })
ctx.plugin({ name: 'greeter-plugin', apply(c) { c.provide('greeter', {}) } })
await ctx.start()   // 顺序：greeter-plugin → consumer
```

### 5.2 start 时依赖缺提供方会怎样？

**不会报错**。缺依赖的插件安静停 `PENDING`，`ctx:ready` 照常广播（`plugins` 列表只含已激活的）。之后补上提供方（热装/重新 provide）→ `wakePending` → 自动激活。

```ts
ctx.plugin({ name: 'c', inject: ['late-svc'], apply() {} })
await ctx.start()                    // 不抛错
ctx.fiber('c')?.stateName            // 'pending'
ctx.installPlugin({ name: 'p', apply(c) { c.provide('late-svc', {}) } })
ctx.fiber('c')?.stateName            // 现在 'active'（被唤醒）
```

### 5.3 热卸会"连坐"

卸掉一个插件后，内核会找"当前因它消失而不再满足声明依赖"的已激活插件，把它们也回收副作用并回退 `PENDING`（保留登记，等服务恢复后自动重载）。传递链也会一层层带下去。

> 大白话：A 依赖 B 的服务。卸 B → A 立刻跟着下线回退；重新装回 B → A 自动重跑。这就是 "cordis inject 非一次性"——依赖关系是活的。

### 5.4 热重载（reload）怎么玩

HMR / 插件代码改了，本质是"卸旧装新"：

```ts
ctx.uninstallPlugin('p')                       // 卸旧实现
ctx.installPlugin({ name: 'p', ...newImpl })   // 装同 name 的新实现
```

同名可重装是因为卸载时把旧登记清掉了；凡是依赖它的插件也会经历"回退 → 自动重载"。

## 6. 插件 apply 内部再装子插件

插件在 `apply` 里可以调 `ctx.plugin(childMod)` 装子插件（运行时自动走热装语义，不抛错），返回自身便于链式。子插件会**扁平并入根**插件/服务表。

```ts
ctx.plugin({
  name: 'parent',
  apply(c) {
    c.plugin({ name: 'child', apply() {} })  // 运行时 → 等价 installPlugin
  },
})
```

---

## 7. 坑与速记

1. 对象插件 `apply` 优先于 `setup`；`inject` 优先于 `deps`。
2. `apply`/`setup` 返回的 cleanup（函数或带 dispose 的对象）会被登记，卸载自动跑。
3. config 校验失败 → 插件进 FAILED（`ConfigError`，带字段名与期望），并往上抛错；插件被移出 plugins 表，但 fiber 保留供诊断，可重装同名复用。
4. 热卸返回 `false` 表示没卸到（没装 / 已卸），不抛错。
5. Service 子类构造里 `super(ctx, name)` 的 `name` 若被别的插件占用了会抛 `already injected`。
6. 想装同名插件必须先卸掉旧的（重名抛错）。
