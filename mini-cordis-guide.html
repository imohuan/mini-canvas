最小 Cordis 复刻 · 前后端双插件架构技术方案

从 DeepSeek Harness 设计哲学到可运行的最小实现 —— 打包后仍可安装第三方依赖

一、DeepSeek Harness 的设计哲学

DeepSeek Harness（dsh）是基于 Cordis 框架的智能体运行时，它的核心设计哲学可以浓缩为四句话：

核心理念 一切皆插件（No Privileged Core）

模型适配器、工具注册表、会话日志、甚至 agent loop 本身都是插件。不存在需要打补丁的特权内核——扩展方式是把插件挂载到其他插件旁边，而非侵入式修改核心代码。

时空可组合 Spatiotemporal Composability

时间维：插件卸载时，它产生的所有副作用（事件监听、定时器、连接）能被完整逆转。
空间维：插件间的依赖关系声明式表达，运行时响应式管理——B 依赖 A 时，系统自动保证 B 在 A 后加载、A 停止前卸载。

组合即数据 Composition as Data

代码只提供"能力"，而"能力之间怎么组合、按什么顺序、配什么参数"全部外置为 YAML 配置（cordis.yml），可以分层叠加、可以 patch。改产品 = 改配置 + 换插件。

可逆性不变量 Reversibility Invariant

所有副作用必须返回一个 disposer（清理函数）。框架保证：任何时刻都能完整地撤销任何插件做过的事。热重载、插件禁用、配置热更新全部建立在这个不变量之上。

二、Cordis 核心机制拆解

Cordis 核心只有约 2000 行代码，五个核心抽象支撑了整个插件系统：

抽象职责关键 API
Context服务容器，Proxy 对象，沿作用域链查找服务ctx.provide() / ctx.get()
Service命名的上下文键，支持 provide（提供）与 consume（消费）class X extends Service
Fiber插件实例的状态机，管理生命周期与 disposer 收集fiber.dispose()
Effect副作用注册与撤销管理，维护副作用栈ctx.effect(() => { return () => {} })
Events类型化事件系统，五种派发模式ctx.on() / ctx.emit()

2.1 插件的三种形态

Cordis 中插件本质归一为三种写法，最终都接收 ctx + config，返回 disposer：

// 1. 函数式
const myPlugin = (ctx, config) => {
  ctx.effect(() => { /* 副作用 */ return () => {} })
  return () => {} // 插件级 disposer
}

// 2. 类式（提供服务）
class Database extends Service {
  constructor(ctx, config) { super(ctx, 'database') }
  query() { /* ... */ }
}

// 3. 对象式
export default {
  name: 'my-plugin',
  inject: ['database'],
  apply(ctx, config) { /* ... */ }
}

2.2 依赖驱动的生命周期（最核心的机制）

加载顺序不由代码决定，由依赖图推导。插件通过 inject 声明依赖，fiber 创建后检查注入的服务是否"存在且 ACTIVE"，全齐了才执行 apply；缺一个就一直 PENDING。依赖消失自动 UNLOAD，依赖回归自动 RELOAD——没有任何手动 reload 代码。

2.3 五种事件派发模式

模式是否等待顺序返回值适用场景
emit否注册顺序无广播/观察者
parallel是并发无并发收集
serial是注册顺序第一个非空短路串行处理链
bail否注册顺序第一个非空短路竞标/拦截
waterfall否注册顺序中间件链数据变换/包装

三、最小 Cordis 内核实现（可运行）

以下是一个约 150 行的最小 Cordis 内核，覆盖 Context / Service / Fiber / effect / inject / events 六大核心能力，可以直接跑起来：

// mini-cordis.js —— 最小 Cordis 内核
type Disposer = () => void;
type Plugin = (ctx: Context, config?: any) => Disposer | void;

// ─── Fiber：插件实例状态机 ───
class Fiber {
  state: 'pending' | 'active' | 'disposed' = 'pending';
  name: string;
  private disposers: Disposer[] = [];

  constructor(name: string) { this.name = name; }

  addDisposer(d: Disposer) { this.disposers.push(d); }

  // 逆序 unwind —— 后注册的先清理
  dispose() {
    for (let i = this.disposers.length - 1; i >= 0; i--) {
      try { this.disposers[i](); } catch(e) { console.error(e); }
    }
    this.disposers = [];
    this.state = 'disposed';
  }
}

// ─── Context：服务容器 + 事件总线 ───
class Context {
  private services = new Map<string, any>();
  private events = new Map<string, Set<Function>>();
  private fibers = new Set<Fiber>();
  private pendingConsumers: { fiber: Fiber; inject: string[]; apply: Function }[] = [];
  currentFiber: Fiber | null = null;

  // 提供服务，返回 disposer
  provide(name: string, service: any): Disposer {
    this.services.set(name, service);
    this._checkPending(); // 新服务上线，检查等待中的消费者
    const dispose = () => {
      this.services.delete(name);
      // 服务下线：依赖它的消费者自动卸载
    };
    if (this.currentFiber) this.currentFiber.addDisposer(dispose);
    return dispose;
  }

  // 消费服务
  get(name: string) { return this.services.get(name); }

  // 可逆副作用 —— Cordis 最核心的 API
  effect(fn: () => Disposer | void): Disposer {
    const disposer = fn();
    if (disposer && this.currentFiber) {
      this.currentFiber.addDisposer(disposer);
    }
    return disposer || (() => {});
  }

  // 事件监听（自动享受卸载即清除）
  on(event: string, handler: Function): Disposer {
    if (!this.events.has(event)) this.events.set(event, new Set());
    this.events.get(event)!.add(handler);
    const dispose = () => this.events.get(event)?.delete(handler);
    if (this.currentFiber) this.currentFiber.addDisposer(dispose);
    return dispose;
  }

  emit(event: string, ...args: any[]) {
    this.events.get(event)?.forEach(h => {
      try { h(...args); } catch(e) { console.error(e); }
    });
  }

  // 加载插件（支持 inject 依赖声明）
  async plugin(pluginFn: Plugin | { inject?: string[]; apply: Plugin }, config?: any) {
    const name = (pluginFn as any).name || 'anonymous';
    const fiber = new Fiber(name);
    this.fibers.add(fiber);

    const inject = (pluginFn as any).inject || [];
    const apply = typeof pluginFn === 'function' ? pluginFn : (pluginFn as any).apply;

    // 依赖检查：全齐才激活，否则挂起等待
    const ready = inject.every((k: string) => this.services.has(k));
    if (!ready) {
      this.pendingConsumers.push({ fiber, inject, apply });
      return fiber; // PENDING 状态
    }

    this.currentFiber = fiber;
    const disposer = await apply(this, config);
    if (disposer) fiber.addDisposer(disposer);
    fiber.state = 'active';
    this.currentFiber = null;
    return fiber;
  }

  // 新服务上线时，检查等待中的消费者
  private _checkPending() {
    const ready = this.pendingConsumers.filter(c =>
      c.inject.every(k => this.services.has(k))
    );
    this.pendingConsumers = this.pendingConsumers.filter(c => !ready.includes(c));
    ready.forEach(({ fiber, apply }) => {
      this.currentFiber = fiber;
      const d = apply(this);
      if (d) fiber.addDisposer(d);
      fiber.state = 'active';
      this.currentFiber = null;
    });
  }
}

export { Context, Fiber };
export type { Disposer, Plugin };

import { Context } from './mini-cordis';

四、你的场景：前后端双插件架构

你的软件分为前后端，插件可以覆盖两个位置。核心思路是：一个插件包同时包含 server 端和 web 端代码，后端负责加载 server 部分并 serve web 部分的静态文件，前端通过动态 import 加载 web 部分。

4.1 插件包目录结构

my-plugin/ ├── manifest.json # 插件元数据（名称、版本、入口、权限） ├── package.json # 第三方依赖声明（运行时 npm install） ├── server/ │ └── index.js # 后端入口：注册服务/API路由/事件监听 └── web/ ├── index.js # 前端入口（已构建为 ESM bundle） └── style.css # 可选：插件样式

4.2 manifest.json 设计

{
  "id": "my-plugin",
  "name": "我的插件",
  "version": "1.0.0",
  "description": "示例插件",
  "entry": {
    "server": "./server/index.js",
    "web": "./web/index.js"
  },
  "permissions": ["fs.read", "network"],
  "extensionPoints": {
    "routes": ["/my-plugin"],
    "menu": { "title": "我的插件", "icon": "plugin" }
  }
}

4.3 后端插件写法（Cordis 风格）

// my-plugin/server/index.js
module.exports = {
  name: 'my-plugin',
  inject: ['http', 'database'],  // 声明依赖的核心服务

  apply(ctx, config) {
    // 1. 注册 API 路由（effect 自动管理生命周期）
    ctx.effect(() => {
      const app = ctx.get('http');
      app.get('/api/my-plugin/hello', (req, res) => {
        res.json({ message: 'Hello from plugin!' });
      });
      return () => {
        // 卸载时自动移除路由（express 需手动处理，建议用路由层封装）
      };
    });

    // 2. 注册自定义服务，供其他插件使用
    ctx.provide('myService', {
      doSomething() { return 'done'; }
    });

    // 3. 监听事件
    ctx.on('app:ready', () => {
      console.log('[my-plugin] app ready');
    });

    // 4. 插件级清理
    return () => console.log('[my-plugin] unloaded');
  }
};

五、打包后如何安装第三方依赖

这是你最关心的问题。核心原则：插件放在 userData 目录（可写），每个插件有独立的 node_modules，运行时通过编程方式执行 npm install。

5.1 为什么不能放在 asar 里

Electron 打包后，应用代码在 app.asar 中——这是一个只读的归档文件。你无法在运行时往 asar 里 npm install。所以插件和它们的依赖必须放在 app.getPath('userData') 下，这是用户数据目录，始终可写。

5.2 三种运行时安装方案

方案原理优点缺点
A. 内置 npm 把 npm CLI 打进 extraResources，运行时 spawn 子进程执行 npm install 最稳定，支持所有 npm 特性 体积大（~50MB），启动子进程慢
B. pacote 编程式 用 pacote + @npmcli/arborist 库直接下载 tarball 并解析依赖树 轻量，无进程开销，可控性强 需要处理依赖树解析，原生模块需额外处理
C. 插件自带依赖 插件发布时把 node_modules 一起打包，下载解压即用 零安装时间，最简单 插件包体积大，跨平台需预编译原生模块

5.3 方案 A 实现：内置 npm

// electron-builder 配置 —— 把 npm 打进 resources
// package.json
{
  "build": {
    "extraResources": [
      { "from": "node_modules/npm", "to": "npm" }
    ]
  }
}

// 主进程中运行时安装
const { spawn } = require('child_process');
const path = require('path');
const { app } = require('electron');

async function installPluginDeps(pluginDir) {
  const npmPath = path.join(
    process.resourcesPath, 'npm', 'bin', 'npm-cli.js'
  );

  return new Promise((resolve, reject) => {
    const child = spawn(process.execPath, [npmPath, 'install', '--omit=dev'], {
      cwd: pluginDir,
      env: {
        ...process.env,
        // 关键：让 npm 用 Electron 自带的 Node 运行时
        npm_config_prefix: path.join(app.getPath('userData'), '.npm'),
      },
      stdio: ['ignore', 'pipe', 'pipe']
    });

    child.stdout.on('data', d => console.log(d.toString()));
    child.stderr.on('data', d => console.error(d.toString()));
    child.on('close', code =>
      code === 0 ? resolve() : reject(new Error(`npm exit ${code}`))
    );
  });
}

5.4 方案 B 实现：pacote 轻量安装（推荐）

const pacote = require('pacote');
const { mkdir, writeFile } = require('fs/promises');
const path = require('path');

// 下载单个包到插件的 node_modules
async function installPackage(spec, destDir) {
  const manifest = await pacote.manifest(spec);
  const target = path.join(destDir, 'node_modules', manifest.name);
  await mkdir(target, { recursive: true });

  // 提取 tarball 内容
  await pacote.extract(spec, target);

  // 递归安装依赖（简化版，生产用 @npmcli/arborist）
  for (const [name, range] of Object.entries(manifest.dependencies || {})) {
    await installPackage(`${name}@${range}`, destDir);
  }
  return manifest;
}

原生模块注意事项：如果第三方依赖包含 C++ 原生模块（如 better-sqlite3、sharp），需要用 @electron/rebuild 针对 Electron 的 Node ABI 版本重新编译。建议在插件安装后自动执行 rebuild，或要求插件使用纯 JS 依赖。

六、前端已打包后如何接入第三方 JS

这是第二个核心问题。你的前端 UI 已经打包成静态文件了，怎么在运行时加载插件的前端代码？答案是：后端 serve 插件的 web 目录，前端用动态 import() 加载 ESM 模块。

6.1 整体加载流程

1 前端启动 → 请求 GET /api/plugins 获取已启用插件清单

↓

2 后端从 userData/plugins/ 扫描 manifest.json，返回 [{ id, name, webEntry }]

↓

3 前端对每个插件执行 import(plugin.webEntry) 动态加载 ESM

↓

4 调用插件的 register(extensionAPI)，传入扩展点 API

↓

5 插件通过 API 注册路由、菜单、面板——完成 UI 注入

6.2 后端：serve 插件静态文件

const express = require('express');
const path = require('path');
const { app } = require('electron');

const PLUGINS_DIR = path.join(app.getPath('userData'), 'plugins');

// 静态文件服务：/plugins/:id/web/* → userData/plugins/:id/web/*
server.use('/plugins', express.static(PLUGINS_DIR, {
  setHeaders(res, filePath) {
    if (filePath.endsWith('.js')) {
      res.setHeader('Content-Type', 'application/javascript; charset=utf-8');
    }
  }
}));

// 插件清单 API
server.get('/api/plugins', (req, res) => {
  const plugins = scanPlugins(PLUGINS_DIR); // 读取各目录 manifest.json
  res.json(plugins.map(p => ({
    id: p.id,
    name: p.name,
    version: p.version,
    webEntry: `/plugins/${p.id}/web/${p.entry.web}`
  })));
});

6.3 前端：动态加载插件（核心代码）

// src/plugin-loader.ts —— 前端插件加载器
import { router } from './router';
import { menuStore } from './store/menu';

// 扩展点 API —— 暴露给插件的能力
const extensionAPI = {
  addRoute(route: any) { router.addRoute(route); },
  removeRoute(path: string) { router.removeRoute(path); },
  addMenuItem(item: any) { menuStore.add(item); },
  removeMenuItem(path: string) { menuStore.remove(path); },
  addPanel(slot: string, component: any) {
    panelRegistry.register(slot, component);
  },
  // 可以继续扩展：addStore、addCommand、addSettingTab...
};

const loadedPlugins = new Map<string, any>();

export async function loadAllPlugins() {
  const res = await fetch('/api/plugins');
  const plugins = await res.json();

  for (const plugin of plugins) {
    try {
      // 关键：动态 import 远程 ESM 模块
      // @vite-ignore 告诉 Vite 不要在构建时分析这个 import
      const mod = await import(/* @vite-ignore */ plugin.webEntry);
      const pluginModule = mod.default;

      pluginModule.register(extensionAPI);
      loadedPlugins.set(plugin.id, pluginModule);
      console.log(`[plugin] ${plugin.id} loaded`);
    } catch (err) {
      console.error(`[plugin] ${plugin.id} failed:`, err);
    }
  }
}

export function unloadPlugin(id: string) {
  const plugin = loadedPlugins.get(id);
  if (plugin?.unregister) plugin.unregister(extensionAPI);
  loadedPlugins.delete(id);
}

    url: entryUrl,
    format: 'esm',
    from: 'vite'

}

七、完整启动流程与后端 Plugin Host

7.1 后端 Plugin Host 实现

// plugin-host.js —— 后端插件宿主
const { Context } = require('./mini-cordis');
const express = require('express');
const path = require('path');
const { app } = require('electron');

const PLUGINS_DIR = path.join(app.getPath('userData'), 'plugins');

class PluginHost {
  ctx = new Context();
  server = express();
  loadedFibers = new Map();

  async start() {
    // 1. 注册核心服务（HTTP、配置等）
    this.ctx.provide('http', this.server);
    this.ctx.provide('config', { get: (k) => this.config[k] });

    // 2. serve 插件前端静态文件
    this.server.use('/plugins', express.static(PLUGINS_DIR));

    // 3. 插件清单 API
    this.server.get('/api/plugins', (req, res) => {
      res.json(this.listPlugins());
    });

    // 4. 扫描并加载所有已启用插件
    const plugins = this.listPlugins();
    for (const p of plugins) {
      await this.loadPlugin(p.id);
    }

    // 5. 启动 HTTP 服务
    this.server.listen(3000, () => {
      console.log('Plugin host running on :3000');
      this.ctx.emit('app:ready');
    });
  }

  async loadPlugin(pluginId) {
    const pluginDir = path.join(PLUGINS_DIR, pluginId);
    const manifest = require(path.join(pluginDir, 'manifest.json'));
    const entry = path.join(pluginDir, manifest.entry.server);

    // 清除 require 缓存，支持热重载
    delete require.cache[require.resolve(entry)];

    // 关键：从 userData 目录 require 插件代码
    // Node 会自动在 pluginDir/node_modules 中查找依赖
    const pluginModule = require(entry);
    const fiber = await this.ctx.plugin(pluginModule);
    this.loadedFibers.set(pluginId, fiber);
  }

  unloadPlugin(pluginId) {
    const fiber = this.loadedFibers.get(pluginId);
    if (fiber) {
      fiber.dispose(); // 逆序清理所有副作用
      this.loadedFibers.delete(pluginId);
    }
  }

  listPlugins() {
    // 扫描 PLUGINS_DIR，读取每个子目录的 manifest.json
    // 返回 [{ id, name, version, webEntry }]
  }
}

module.exports = { PluginHost };

7.2 Electron 主进程集成

const { app, BrowserWindow } = require('electron');
const { PluginHost } = require('./plugin-host');

const host = new PluginHost();

app.whenReady().then(async() => {
  // 启动后端插件服务
  await host.start();

  // 创建窗口，加载已打包的前端
  const win = new BrowserWindow({
    width: 1200, height: 800,
    webPreferences: { contextIsolation: true }
  });

  if (app.isPackaged) {
    win.loadFile(path.join(__dirname, '../dist/index.html'));
  } else {
    win.loadURL('http://localhost:5173');
  }
});

八、关键问题与注意事项

8.1 安全沙箱

第三方插件代码运行在你的主进程中，拥有 Node.js 全部能力。建议：

  • 插件安装时校验签名/哈希（类似 VS Code 的 marketplace 签名）
  • 敏感 API（fs、net）通过权限声明控制，manifest.json 中声明 permissions
  • 考虑用 utilityProcess 或 vm 模块隔离插件执行环境
  • 前端插件通过 CSP 限制可加载的远程脚本来源

8.2 依赖冲突与共享

策略做法适用场景
完全隔离每个插件独立 node_modules，互不干扰插件少，体积不敏感
共享核心依赖宿主提供 vue/react/axios 等，插件通过 external 声明不打包插件多，需要控制体积
Module Federation运行时共享 singletons，版本协商复杂微前端场景

8.3 路径问题（开发 vs 生产）

// 统一路径解析工具
function getPluginsDir() {
  return app.isPackaged
    ? path.join(app.getPath('userData'), 'plugins')  // 生产：用户目录
    : path.join(process.cwd(), '.plugins');             // 开发：项目目录
}

// asar 内的前端资源
function getFrontendDir() {
  return app.isPackaged
    ? path.join(process.resourcesPath, 'app.asar', 'dist')
    : path.join(process.cwd(), 'dist');
}

8.4 热重载（开发体验）

开发时可以监听插件目录变化，自动卸载旧 fiber 并重新加载：

const chokidar = require('chokidar');

chokidar.watch(PLUGINS_DIR, { ignoreInitial: true })
  .on('change', async (filePath) => {
    const pluginId = path.relative(PLUGINS_DIR, filePath).split(path.sep)[0];
    host.unloadPlugin(pluginId);
    await host.loadPlugin(pluginId);
    console.log(`[HMR] ${pluginId} reloaded`);
  });

九、总结：最小实现路线图

1 实现 mini-cordis 内核（Context + Fiber + effect + inject + events），约 150 行

2 设计插件包格式：manifest.json + server/ + web/ + package.json

3 后端 Plugin Host：扫描插件 → require 加载 → 注册到 Cordis → serve 静态文件

4 前端插件加载器：fetch 清单 → dynamic import → register(extensionAPI)

5 运行时依赖安装：内置 npm 或 pacote，安装到 userData/plugins/<id>/node_modules

6 安全与沙箱：权限声明、签名校验、可选 utilityProcess 隔离

核心洞察：DeepSeek Harness 的"一切皆插件"不是魔法，它建立在两个简单的不变量之上——(1) 所有副作用可逆（effect + disposer），(2) 加载顺序由依赖图推导（inject）。你的最小实现只需要这两个机制，再加上"后端 require + 前端 dynamic import"的双端加载策略，就能实现打包后可扩展的插件系统。
