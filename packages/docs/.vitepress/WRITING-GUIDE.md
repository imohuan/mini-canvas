# 文档写作规范（给写文档的人 / AI 用）

> 这份文件只给**写文档的人**看，不会出现在网站里（不在 Vitepress 的 srcExclude 之外，
> 但因为它放在 .vitepress/ 下、且不是页面，读者看不到）。写新页面前先读一遍。

## 一、最高优先级：先读源码，再写

**任何一句 API 描述、任何一个方法签名、任何一处"谁在调用它"，都必须来自当前源码。**

项目里另有一份老文档 `docs/代码开发/`，可以**当参考**（结构、术语、踩过的坑），
但**不能照抄** —— 那里的很多内容对应老版本代码，已经过期。凡有冲突，**以源码为准**。

核实手段（按优先级）：

1. `codegraph`（先 `codegraph status`，再用 `codegraph explore` / `node` / `callers`）。
2. 直接读源码文件。
3. `rg` 找真实调用点（找"会在哪里用到"）。

**禁止编造**：不确定的方法、不存在的参数、臆想的调用点，宁可不写。

## 二、API 参考页的结构（`/api/`、`/services/`、`/core/`）

> API 分类是**纯参考**，只回答"有哪些 API、怎么用"，**不铺教学**。
> 禁止类比、"为什么需要它"、长故事、整包照抄的完整例子 —— 那些属于入门/示例分类。

每篇统一两~四节：

1. **一句话定位**（开篇加粗）+ **它属于哪一档**（谁提供的、源码在哪、缺了会怎样）。
2. `## 用法` —— 怎么拿（`ctx.get` / `inject` / 语法糖）+ 方法表：**真实签名** + 一句话 + 什么时候用。
3. `## 注意事项` —— 2~5 条真实限制，每条说清"为什么"。

要点：

- **方法用表格罗列**（方法 / 签名 / 干什么 / 什么时候用），别写成散文。
- **签名逐字来自源码**，不编造；形状（interface）给全字段。
- 消费点如确有必要，压成两三行或一张小表，不单开大节。
- 能合并的别硬凑。

## 二·补、入门 / 示例 / 插件分类的结构

这几类才是教学，可保留完整叙事（是什么 / 为什么 / 完整例子 / 常见坑）。
写 UI 前先读 `docs/design/ui-style-guide.md`。

## 三、代码示例的硬要求（用户最在意的一条）

> 用户原话："你的例子需要有一个完善的上下文，不能靠我猜你的这段代码写在哪里。"

- **完整可跑**：不是片段拼贴，读者照抄能用。
- **跨文件时**：每个代码块**第一行**注释标出「文件路径 + 文件格式 + 它在项目里的位置/作用」：
  ```
  // 文件：packages/my-plugin/src/index.ts
  // 格式：TypeScript 模块（插件入口，导出 name / inject / apply）
  // 位置：一个可安装插件包的源码入口
  ```
- **例子开头给目录树**，每个文件旁注释它干什么：
  ```
  my-plugin/
  ├── package.json   # 插件清单，声明 miniCanvas 元信息
  └── src/index.ts   # 插件入口
  ```
- 涉及清单/配置就给 **JSON 全文**；涉及 import 写清**从哪个包**导入。
- 关键步骤用 `// ① ② ③` 标出，正文逐条对应解释。
- 尽量贴近仓库真实写法：动手前先读一两份真实源码做参照，例如
  `packages/plugins/plugin-theme-default/src/index.ts`、
  `packages/plugins/plugin-bottom-bar/src/nodeBarPlugin.ts`、
  `packages/canvas-data/src/canvas/canvasBasePlugin.ts`。
- 如果配了示例源码，放到 `packages/docs/public/examples/<页面名>/…`，并在正文说明
  "同样的文件在仓库里也放了一份，可直接打开对照"。

## 四、语气

- 中文，大白话，**读者水平：8 岁小孩也能懂**。少用术语，必须用就当场解释。
- 每句话都要有信息量。禁止"这里很强大""灵活易用"这类空话。
- 结论先行；讲清"为什么"，不只讲"是什么"。

## 五、事实红线（这套系统里最容易写错的几条）

- `ctx.get('名字')` **缺服务返回 `undefined`，不抛**；硬依赖要用模块级 `export const inject = [...]`。
- 旧服务名 `nodeStore` / `edgeStore` / `graph` / `history` **已下线**，都并进了 `doc`。
- 注册场 `order` 方向：**越小 = 越在外层 / 优先级越高**；单赢家槽取 order 最小者。
- **"一个能手"是服务（会换实现才做服务），"一张表"是场** —— 别把注册场写成服务。
- kernel **不依赖任何其它 `@mini-canvas` 包**；它不认识画布、不认识 Vue。
- 渲染宿主的服务（`nodeLayout` / `viewport` / `pluginManager`）在**纯数据层拿不到**。
- `ctx` 上的 `nodes` / `theme` / `commands` / `slots` / `settings` 是**语法糖**，落点是对应注册场。

## 六、写完必须做

1. `pnpm -C packages/docs build` 必须通过。
2. 抽查你写的页面真的渲染了（浏览器或构建产物）。
3. 汇报：改了什么、覆盖了哪些小节、怎么验证、证据、遗留问题。
