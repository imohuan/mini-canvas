# 三层是怎么分工的

整个项目分成三层，外加一层插件。依赖是**单向**的：左边那一层完全不知道右边那一层存在。

```
kernel  ←  canvas-data  ←  canvas-render  ←  plugins
（框架）    （数据+语义）     （渲染）          （具体功能）
```

一句话记住每层：

| 层 | 包名 | 一句话 | 它眼里有什么 |
| --- | --- | --- | --- |
| 框架 | `@mini-canvas/kernel` | 装插件的规矩 | 只有插件、服务、事件。**不认识画布，也不认识 Vue** |
| 数据 | `@mini-canvas/canvas-data` | 画布的图纸和骨架 | 节点、边、选中、撤销、存档 |
| 渲染 | `@mini-canvas/canvas-render` | 把数据画到屏幕上 | Vue、VueFlow、DOM、尺寸、视口 |
| 插件 | `packages/plugins/*` | 具体功能 | 想用什么就用什么 |

## 为什么要这么切

因为"改变的东西"不一样，把它们混在一起，改一个地方会牵动全身。

- **kernel 只关心"怎么把插件装起来"**，所以它永远不需要改 —— 换画布、换界面它都不管。
- **canvas-data 只关心"数据长什么样"**，所以它不 import Vue，能被纯逻辑测试。
- **canvas-render 只关心"怎么画"**，所以换渲染方案（甚至换成别的前端框架）只动这一层。

一个硬规矩：**kernel 不依赖任何其它 `@mini-canvas` 包。** 它的依赖是零。

## 看一个真实例子，就明白分层了

用户点右键，菜单里点"删除节点"。这条请求要穿过三层：

```
插件（右键菜单）        UI 上"删除"这一项是插件放的
      ↓ 触发命令
canvas-render          命令分发给谁、快捷键怎么认
      ↓ 调用
canvas-data            doc 服务真正把节点删掉、进撤销栈、落盘
```

每一层只干自己的事：插件不知道节点怎么删，数据层不知道菜单长什么样。

再比如"节点有多大"这件事：

- **canvas-data** 存着"这个节点声明是多宽多高"（`size`）。
- **canvas-render** 才去量 DOM，知道"它**实际**渲染出来是多大"（`nodeLayout` 服务）。

数据层给不了实际尺寸，因为它不碰 DOM；渲染层量到尺寸后，通过服务把结果交回来。
这就是分层的意义：**谁擅长什么，谁来做。**

## 五个包，各自是你的什么

除了三层，还有两个"门面"包，是给人用的入口，不是新的一层：

| 包 | 给谁用 | 提供什么 |
| --- | --- | --- |
| `@mini-canvas/canvas-base` | **插件作者** | 一个薄入口：重导出 kernel + data 的常用东西，再加几个写插件的语法糖 |
| `@mini-canvas/ui` | **用画布的应用** | 一行 `<CanvasApp/>` 出一张装好的画布 |

所以写插件的规矩很简单：**只 import `@mini-canvas/canvas-base`**。
想要更窄的接口再单独依赖 `@mini-canvas/canvas-data` 的类型。

## 一句话总结

每层只解决一类问题，层与层之间靠**服务**和**注册场**说话，
而不是互相 import 内部实现。这样加功能才不用动核心。
